# 组织与权限

组织与权限用于确定“谁可以访问什么”和“可以看到哪些数据”。系统管理页面位于 `/system` 下，当前 Web 路由包含用户管理、角色管理、授权配置、部门管理、字典管理、菜单管理和行政区划等入口。

## 组织结构

### 部门

从“部门管理”维护组织层级和部门基本信息。部门列表不提供行选择框或行级拆分操作；工具栏按“新增”“部门合并”“部门拆分”的顺序提供入口。合并和拆分都在独立的三栏步骤页中完成，页面左侧显示步骤，中间显示选择、表单和影响预览，右侧显示当前步骤的规则说明。

部门合并将至少两个同一父部门下的活动部门合并到一个新部门。新部门沿用共同父级；源部门的直属下级迁入新部门并保留后代层级，源部门逻辑删除。源部门直属成员的主部门或关联部门关系迁到新部门，重复关系合并为一条有效关系。合并可能扩大访问或授权部门范围，预览会显示相应范围变化。OA 历史业务数据继续保留原部门 ID。

部分拆分从一个活动部门选择直属成员，并创建与源部门同级的新部门。选中成员的主部门或关联部门关系切换到新部门，关系类型不变；未选成员、源部门及其原有子树保持不变。拆分不修改角色边界或授权方案模板，成员范围变化可能改变 `RULES` 数据范围。OA 历史业务数据继续保留原部门 ID。

### 用户

从“用户管理”创建、编辑、导入和查看用户。用户资料、登录身份、账号状态和角色授权属于相关但独立的内容：

- 用户资料包含一个必填主部门和零个或多个可选关联部门。导入模板中的关联部门编码为可选的分号分隔列表。
- 主部门用于默认业务数据归属；关联部门表达用户的其他部门成员关系。部门成员关系本身不授予角色或操作权限，也不改写角色的数据边界。
- `RULES` 数据范围同时受 Permission 授权部门和用户主/关联部门约束；启用包含下级时两侧都扩展到下级部门。`ALL` 和 `SELF` 保持各自语义。

- 只有处于可用状态的用户可以创建新的认证会话。
- 停用、锁定和离职状态会影响登录或当前会话。
- 用户可以拥有多个角色分配；基础角色和业务角色的处理规则不同。
- 密码重置只返回本次生成的临时凭证，服务端保存的是密码哈希。

### 行政区划和字典

行政区划页面维护区域编码数据；字典页面维护供业务表单和查询使用的字典项。字典和区域数据属于系统基础数据，修改前需要确认已经有业务页面或接口使用对应编码。

## 角色和授权

从“角色管理”创建和维护角色，从“授权配置”维护角色能力及其边界。角色授予用户后，用户才能获得对应的业务权限；角色的管理边界还会限制操作者能否授予或变更目标角色。

授权判断至少包含以下信息：

- 当前用户是否处于有效状态。
- 当前 Session 是否有效。
- RoleAssignment 是否仍然有效。
- 目标 Permission 是否属于当前角色能力。
- 当前操作者的 authority level 是否允许本次授权变化。
- Access Boundary 和 Grant Boundary 是否覆盖目标资源或目标授权。
- 业务数据范围是否允许访问具体记录。

前端菜单和按钮不能替代后端授权判断。直接拼接 URL 或手工调用接口不会绕过服务端的 Permission、Session 和数据范围检查。

## 菜单权限

从“菜单管理”维护导航菜单和页面入口。菜单权限决定前端是否展示页面入口，但页面接口仍需后端权限。调整菜单后，建议重新登录并验证以下内容：

1. 目标菜单是否出现在正确的父菜单下。
2. 页面能否正常打开并完成首次数据请求。
3. 页面中的查询、新增、编辑、删除等操作是否分别受到权限控制。
4. 无权限账号访问同一路径时是否得到无权访问结果。

## 数据范围

数据范围与菜单权限是两件事。用户可能看得到一个功能页面，但只能查询本部门、指定部门、本人或其他边界内的数据。后端通过数据范围注解和拦截器在查询边界执行过滤，前端传入的筛选条件不能扩大授权范围。

## 调整授权后的验证

授权变更后按以下顺序验证：

1. 使用管理员账号确认角色、菜单、Permission 和数据范围配置已经保存。
2. 检查目标用户的 RoleAssignment 状态。
3. 让目标用户重新登录，避免使用旧会话中的权限快照。
4. 分别验证菜单可见性、页面读取、写操作和跨部门数据访问。
5. 在审计日志页面检查授权变化和异常拒绝记录。
