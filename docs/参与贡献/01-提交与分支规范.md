# 提交与分支规范

## 提交信息

提交信息使用 Conventional Commits 格式：

```text
<type>(<scope>): <description>
```

常用 `type` 包括：

- `feat`：新增能力。
- `fix`：修复问题。
- `docs`：只修改文档。
- `refactor`：不改变外部行为的重构。
- `test`：新增或调整测试。
- `build`：构建或依赖变化。
- `chore`：其他维护性变更。

`scope` 使用实际子项目或领域名称，例如 `admin`、`ui`、`flowable`、`docs`。描述使用简洁中文，说明结果，不写“临时”“补丁”或无法验证的承诺。

## 分支和提交边界

- 一个分支只处理一个可说明的主题。
- 代码、测试和受影响文档放在同一主题变更中。
- 不把本机配置、构建产物、缓存、编辑器状态和无关格式化混入提交。
- 修改 submodule 后，根仓库需要同时更新对应子模块指针，并在提交说明中写明子模块变更范围。
- 网站生成内容和网站导航变化应与源文档同步变更保持可追溯关系。

## 文档提交

文档页应有明确标题，使用当前中文目录和稳定链接。技术名词、路径、命令、类名和 API 标识符保留原文；导航文字使用中文。

文档事实来源发生变化时，先更新源仓库文档，再运行同步脚本生成网站页面。不要直接手工修改网站生成目录。

## 检查

提交前至少运行：

```bash
git diff --check
./scripts/check-docs.sh
```

代码变更按 [[00-贡献指南|贡献指南]] 执行对应子项目检查；网站文档变更还要运行同步 Preview 和网站构建。
