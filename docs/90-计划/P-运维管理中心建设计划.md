# P-运维管理中心建设计划

## 状态

**规划中（分期实施）**

> 创建时间：2026-08-14
> 适用范围：`spectra-admin`、`spectra-ui`、`spectra_core.sys_menu`、角色权限与菜单迁移。
> 总体原则：先统一超级运维安全契约，再建设三级菜单和运维页面；未接真实接口的模拟页面不得进入正式运维菜单。

## 一、问题背景

随着通知、监控、配置、文件、密钥、会话、调度和审计能力增加，只允许平台运维人员使用的功能分散在“系统管理”“系统监控”和普通业务页面中，出现以下问题：

1. 运维入口缺少统一信息架构，系统管理功能与平台运维功能混放。
2. 已有菜单模型支持多级目录，但当前初始化数据主要是“一级目录 + 二级菜单”，没有统一的三级运维结构。
3. 后端 `hasPermission(...)` 已将配置的管理员角色视为绝对权限；Root 授权快照、当前用户菜单和数据范围现已统一支持隐式全量语义，新菜单会自动对运维角色可见。
4. 前端 `v-owner` 依赖 Token 中的权限数组和 `*` 通配符；Root 授权快照现已在 Token 权限上下文中统一返回 `*`，按钮显示与后端放行结果保持一致。
5. 通知 Request、Task、Delivery、渠道状态、重试和取消已有后端接口，但没有运维前端页面。
6. 在线用户已有查询接口，但前端仍使用模拟数据；定时任务和缓存监控仍是模拟或占位页面。
7. 通知模板、受控发送、运行概览、任务调度、缓存管理和安全审计尚未形成完整的前后端闭环。

本计划建立统一的“运维管理中心”，所有叶子功能保持三级导航：

```text
运维管理 / 二级功能域 / 三级功能页
```

## 二、已确认的设计决策

### 2.1 `ROLE_DEV_OPS` 超级运维契约

`security.administrators` 默认值为 `ROLE_DEV_OPS`。该配置指向的角色必须具备以下一致语义：

1. **全部接口权限**：所有 `hasPermission(...)` 权限表达式默认放行，不要求逐项维护 `RelRoleAuthority`。
2. **全部有效菜单**：`GET /menu/current` 自动返回全部未删除且模型有效的菜单，不依赖 `RelRoleMenu`。
3. **新增菜单自动可见**：新增任意有效菜单后，运维角色下次加载菜单即可看到，无需补授权关系。
4. **全部前端操作可见**：Token 对运维角色返回 `*` 权限，前端 Store 和 `v-owner` 统一按通配符放行，不在前端重复硬编码角色名。
5. **全局数据范围**：运维角色在现有受控数据范围绕过机制中保持 GLOBAL 语义，但不能绕过租户边界、敏感字段脱敏、审计记录和业务安全校验。
6. **内置角色保护**：管理员角色编码不可修改、角色不可删除或停用；不得撤销系统中最后一个可用运维账号的该角色。
7. **菜单不是安全边界**：菜单隐藏只控制导航和前端路由，所有运维接口仍必须使用 `@PreAuthorize` 独立鉴权。

角色菜单管理页面对超级运维角色显示“隐式拥有全部菜单”，菜单树只读全选，不批量写入所有 `RelRoleMenu`。普通角色继续只保存 `MENU` 叶子关系并自动补齐祖先目录。

### 2.2 角色边界

| 角色 | 运维中心边界 |
|---|---|
| `ROLE_DEV_OPS` | 自动拥有全部权限、全部菜单和全部运维写操作 |
| `ROLE_ADMIN_SYSTEM` | 管理用户、角色、菜单、部门、字典、区域和业务配置，不进入运维专属目录 |
| `ROLE_AUDIT` | 仅访问独立审计入口和允许的脱敏只读接口，不获得运维重试、取消、配置、密钥和清理操作 |
| `ROLE_USER` | 不显示运维入口，不允许通过直接 URL 或 API 访问运维功能 |

通知 Request、Task、Delivery 的脱敏查询继续允许 `ROLE_AUDIT`，但审计员不进入“运维管理”目录；审计入口使用独立菜单和只读路由，页面组件可以复用，操作按钮必须按角色隐藏，后端继续强制拒绝写操作。

### 2.3 路由与菜单边界

- Vue Router 保持静态注册，数据库菜单只保存 `routeName` 并控制导航可见性。
- 移动已有页面时优先保留原 route name 和 URL，只修改 `sys_menu.pid`，避免书签和业务跳转失效。
- 新页面必须先注册命名路由，再写入菜单迁移；数据库 `route_name` 必须与前端 route name 一一对应。
- `DIRECTORY` 可以包含下级 `DIRECTORY`，只有 `MENU` 叶子可以绑定 route name。
- 新增路由与菜单后增加契约测试，禁止数据库存在无法解析的有效 route name。

## 三、目标菜单结构

```text
运维管理
├─ 运行监控
│  ├─ 服务监控
│  ├─ 应用健康
│  └─ 缓存监控
├─ 通知中心
│  ├─ 运行概览
│  ├─ 渠道状态
│  ├─ 通知请求
│  ├─ 投递任务
│  ├─ 投递记录
│  ├─ 模板管理
│  └─ 受控发送
├─ 任务调度
│  ├─ 定时任务
│  └─ 执行记录
├─ 系统维护
│  ├─ 系统配置
│  ├─ 加密密钥
│  └─ 文件存储
└─ 安全审计
   ├─ 在线会话
   ├─ 操作日志
   └─ 安全事件
```

以下功能继续保留在“系统管理”，不因局部按钮具有运维权限而移动整个页面：

- 用户管理
- 访问控制
- 部门管理
- 字典管理
- 菜单管理
- 行政区划
- 流程管理

用户密码重置、GLOBAL 数据范围授予、权限定义修改等高风险按钮继续在原页面按运维角色控制，并由后端接口再次鉴权。

## 四、当前能力基线

| 功能 | 后端 | 前端 | 当前结论 |
|---|---|---|---|
| 超级运维 `hasPermission` | Root 授权快照隐式返回 `*` 并全量放行 | — | 已实现并补充回归 |
| 超级运维全部菜单 | Root 菜单查询直接返回全部有效菜单，不依赖角色菜单关系 | 菜单可递归渲染 | 后端已实现 |
| 超级运维前端全部按钮 | Token 权限上下文通过 Root 快照返回 `*` | Store 已支持 `*` | 后端已实现 |
| 服务监控 | CPU/RAM/JVM 接口已存在 | 页面已真实接入 | 可直接迁移菜单 |
| 应用健康 | Spring Health Contributor 已存在部分模块 | 无统一页面 | 需要安全聚合接口和页面 |
| 缓存监控 | 无正式运维接口 | 占位页面 | 前后端均需实现 |
| 通知渠道/Request/Task/Delivery | 查询、重试、取消已存在 | 无管理 API 和页面 | 后端可复用，补前端 |
| 通知模板/受控发送/概览 | 领域模型存在，管理接口不完整 | 无页面 | 前后端均需实现 |
| 在线会话 | `/user/online` 查询已存在 | 模拟数据页面 | 需补会话脱敏和真实接入 |
| 定时任务 | 无正式通用调度管理 API | 模拟页面 | 前后端均需实现 |
| 系统配置 | 查询、更新已存在 | 页面已真实接入 | 可直接迁移菜单 |
| 加密密钥 | 生成、刷新接口已存在 | 混在系统配置页面 | 拆分独立页面并迁移 |
| 文件存储 | 运维查询、删除及上传能力已存在 | 页面已真实接入 | 可直接迁移菜单 |
| 操作日志 | Entity/Mapper/Service 已存在 | 无管理页面 | 补脱敏查询接口和页面 |
| 安全事件 | 有日志类型和认证事件基础 | 无统一查询页面 | 补模型边界、查询接口和页面 |

## 五、分期实施计划

### 第一期：超级运维安全契约与菜单基础

目标：先保证 `ROLE_DEV_OPS` 在后端权限、菜单、Token、前端按钮和数据范围上语义一致，作为后续所有运维功能的前置条件。

#### 5.1 后端权限一致性

- [ ] 为 `SpectraPermissionEvaluator` 增加管理员角色、`*`、普通角色和空权限矩阵测试。
- [ ] `MenuServiceImpl.current` 使用 `security.administrators` 判断已启用的超级运维角色，直接返回全部有效菜单树。
- [x] 超级运维菜单查询不依赖 `RelRoleMenu`，普通角色逻辑保持不变。
- [x] `TokenVO` 对超级运维隐式返回 `*` authority，登录、Token 复用和刷新 Token 行为一致。
- [x] Root 授权快照在数据范围拦截器中保持 GLOBAL 语义；租户与敏感数据保护仍由独立边界和业务校验负责。
- [ ] 内置管理员角色禁止删除、改码、停用，并阻止撤销最后一个有效运维账号。

#### 5.2 前端权限一致性

- [ ] `use-user-store` 和 `v-owner` 使用后端返回的 `*` 统一判断全部操作权限。
- [ ] 不在 Vue 组件中散落硬编码 `ROLE_DEV_OPS`；角色专属操作使用统一权限工具或封装常量。
- [ ] 超级运维在角色菜单编辑器中显示“隐式全部菜单”，禁止产生误导性的部分勾选状态。
- [ ] 增加 Store、指令、路由守卫和角色菜单编辑器测试。

#### 5.3 第一阶段验收

- [x] 未配置任何 `RelRoleAuthority` 时，`ROLE_DEV_OPS` 仍通过授权快照和实际接口验证。
- [x] 未配置任何 `RelRoleMenu` 时，`ROLE_DEV_OPS` 仍看到全部有效菜单。
- [ ] 新增一个测试菜单后，运维账号重新加载菜单即可看到。
- [ ] 普通用户、系统管理员和审计员不会因超级运维逻辑扩大权限或菜单。

### 第二期：三级菜单骨架与现成功能迁移

目标：建立“运维管理 / 功能域 / 功能页”三级结构，先迁移已经真实可用的页面。

#### 5.4 菜单与数据迁移

- [ ] 新增“运维管理”一级 `DIRECTORY`。
- [ ] 新增“运行监控、通知中心、任务调度、系统维护、安全审计”二级 `DIRECTORY`。
- [ ] 使用固定 UUID 或可重复定位的稳定键编写幂等菜单迁移。
- [ ] 按 route name 迁移 `MonitorServer`、`SystemConfigured`、`SystemStorage` 等现有叶子，保留原 route name 和 URL。
- [ ] 普通角色移除运维叶子关系；`ROLE_DEV_OPS` 使用隐式全菜单，不写全量关系。
- [ ] 更新全新数据库建表/初始化 SQL，并验证已有数据库重复执行迁移不会产生重复节点或孤儿节点。

#### 5.5 前端路由整理

- [ ] 新增 `operations.ts` 路由模块，统一注册新增运维页面。
- [ ] 已有页面迁移时保留命名路由，面包屑按新菜单树显示三级路径。
- [ ] 未实现的模拟/占位页面暂不写入正式菜单。
- [ ] 增加三级侧边栏、顶部导航、面包屑、刷新和直接 URL 的回归测试。

#### 5.6 第二阶段验收

- [ ] 运维账号看到完整三级菜单，并可访问已迁移页面。
- [ ] 系统管理员和普通用户看不到“运维管理”。
- [ ] 直接输入运维页面 URL 时，无菜单权限的用户进入 401/403 页面，API 同时返回 403。
- [ ] 现有业务跳转和书签不因菜单迁移失效。

### 第三期：通知中心基础运维闭环

目标：先基于已经存在的管理端接口完成通知运行查询和任务处置页面。

#### 5.7 前端管理 API 与类型

- [ ] 新增通知管理端类型：ChannelAvailability、Request、Task、Delivery、分页筛选和状态枚举。
- [ ] 新增管理 API：渠道状态、Request 分页、Task 分页、Delivery 分页、重试和取消。
- [ ] 所有查询展示脱敏字段，不复用面向当前用户的消息中心 Store。
- [ ] 对渠道状态并行查询 `IN_APP`、`SMS`、`EMAIL`，单个渠道失败不阻断其他渠道展示。

#### 5.8 通知运维页面

- [ ] “渠道状态”展示启用状态、可用性和脱敏原因，不展示凭据和供应商密钥。
- [ ] “通知请求”支持状态、用途、来源模块、业务类型和业务 ID 查询。
- [ ] “投递任务”支持 Request、Task、接收用户、渠道、用途和状态查询。
- [ ] 重试仅对 FAILED/BLOCKED/UNKNOWN 展示，取消仅对 PENDING/RETRYING/PROCESSING 展示。
- [ ] “投递记录”支持按 Task 和状态查询，只展示脱敏接收地址、标准错误码和截断摘要。
- [ ] Request → Task → Delivery 支持上下文跳转和保留筛选条件。

#### 5.9 角色矩阵

- [ ] `ROLE_DEV_OPS` 可以查询、重试和取消。
- [ ] `ROLE_AUDIT` 通过独立审计入口只能查询，页面不渲染重试和取消按钮。
- [ ] 其他角色的菜单、路由和接口均拒绝访问。

### 第四期：通知高级运维能力

目标：补齐通知模板、受控发送、运行概览和批量渠道健康接口，形成完整通知运维中心。

#### 5.10 通知运行概览

- [ ] 新增聚合接口，返回队列积压、各状态数量、失败率、重试数、过期数和渠道可用性。
- [ ] 指标按固定维度聚合，禁止业务 ID、手机号、邮箱等高基数或敏感标签。
- [ ] 页面提供时间范围和用途/渠道筛选，不通过多次分页接口在浏览器端拼装统计。

#### 5.11 模板管理

- [ ] 实现模板分页、详情、新建版本、启停和软删除接口。
- [ ] 已被任务锁定的模板版本保持不可变；修改模板创建新版本，不覆盖历史快照。
- [ ] 前后端共同校验占位符、HTML 白名单、渠道长度和用途×渠道唯一性。
- [ ] 模板预览使用测试变量，不允许执行 SpEL、脚本或任意表达式。

#### 5.12 受控发送

- [ ] 实现仅供 `ROLE_DEV_OPS` 使用的受控发送接口和页面。
- [ ] 强制业务键/幂等键、接收人范围、用途、渠道、模板和链接白名单校验。
- [ ] 禁止通过页面发送验证码或绕过 Security 验证码生命周期。
- [ ] 页面不接收或保存供应商凭据；真实 SMS/EMAIL Provider 未配置时明确显示 BLOCKED。
- [ ] 所有发送操作记录脱敏审计，支持根据 Request/Task 追踪结果。

### 第五期：监控、会话、缓存与任务调度

目标：移除现有模拟数据和占位页面，提供安全、可审计的真实运维能力。

#### 5.13 应用健康与服务监控

- [ ] 保留现有 CPU/RAM/JVM 页面并补充刷新频率、失败降级和超时处理。
- [ ] 新增安全的应用健康聚合接口，只返回组件状态和脱敏原因，不返回环境变量、连接串或凭据。
- [ ] 展示数据库、Redis、通知、文件存储等关键依赖状态。

#### 5.14 在线会话

- [ ] 前端移除模拟数据，真实接入在线用户/会话接口。
- [ ] 后端返回不可逆会话指纹，不返回完整 access token、refresh token 或 Redis key。
- [ ] 增加踢出单设备、踢出用户全部会话接口，并记录安全审计。
- [ ] 冻结用户继续走用户管理权限和业务校验，不与踢会话混为一个接口。

#### 5.15 缓存监控

- [ ] 提供 Redis 连接、内存、命中率、Key 数量和按已登记前缀聚合的只读指标。
- [ ] 禁止任意扫描、读取或编辑业务 Key 内容。
- [ ] 如提供清理操作，只允许清理注册过的缓存命名空间，并要求二次确认、数量上限和审计记录。

#### 5.16 任务调度

- [ ] 建立持久化任务定义、执行记录、状态和并发策略。
- [ ] 页面只能选择后端注册的 Job Handler ID，禁止输入任意 Bean、类名、方法名或表达式执行代码。
- [ ] 支持启停、手工触发、Cron 校验、超时、互斥和执行日志。
- [ ] 手工触发、停用和删除均要求运维权限并保留审计。
- [ ] 现有模拟定时任务页面在真实接口完成前不进入正式菜单。

### 第六期：系统维护与安全审计

目标：完成运维配置、密钥、文件、操作日志和安全事件的统一入口。

#### 5.17 系统维护

- [ ] 系统配置、加密密钥和文件存储拆分为独立三级页面。
- [ ] 密钥生成/刷新页面增加影响说明、二次确认、操作结果和审计记录，不展示完整私钥。
- [ ] 配置页面按敏感等级脱敏，密码、Token、Secret、Key 和连接串不得回显。
- [ ] 文件管理保持分页、预览、下载、删除和上传闭环，删除使用权限、确认和审计。

#### 5.18 操作日志与安全事件

- [ ] 为现有 OperationLog 增加脱敏分页、详情和固定条件查询接口。
- [ ] 登录、登出、密码、密钥、会话、权限、通知人工处置和缓存清理归入安全事件查询。
- [ ] 请求体、响应体、Token、验证码、手机号、邮箱和密钥按统一规则脱敏或不落库。
- [ ] 如提供导出，必须限制时间范围、行数、字段和角色，并记录导出审计。
- [ ] `ROLE_AUDIT` 使用独立“审计中心”只读菜单复用查询组件，不获得运维写操作。

### 第七期：全链路验证与计划收口

#### 5.19 自动化测试

## 六、实施顺序与依赖

```text
第一期 超级运维契约
  ↓
第二期 三级菜单与已有页面迁移
  ↓
第三期 通知基础运维
  ↓
第四期 通知高级运维
  ↓
第五期 监控/会话/缓存/调度
  ↓
第六期 系统维护/安全审计
  ↓
第七期 全链路验收与收口
```

- 第一期是所有后续阶段的阻塞前置。
- 第二期完成后即可逐个挂载后续三级页面。
- 第三期只复用现有通知管理端接口，可以优先交付。
- 第四至第六期涉及新增后端能力，应分别实施和验收，禁止以模拟数据标记完成。

## 七、完成定义

- [ ] `ROLE_DEV_OPS` 无需显式权限和菜单关系即可拥有全部权限、全部菜单和前端全部操作入口。
- [ ] 新菜单对超级运维自动可见，对其他角色仍需明确授权。
- [ ] “运维管理”形成统一三级菜单，系统管理与运维管理职责清晰。
- [ ] 通知、监控、会话、缓存、调度、配置、密钥、文件和审计均使用真实接口，不包含模拟页面。
- [ ] 运维接口具备后端角色校验、敏感数据保护、状态校验、审计和必要的二次确认。
- [ ] `ROLE_AUDIT` 仅具备独立只读审计入口，不获得运维写权限。
- [ ] 数据迁移可重复执行，新库和旧库结果一致。
- [ ] 自动化测试、真实数据库验证、四角色 HTTP 回归和浏览器验收全部通过。
