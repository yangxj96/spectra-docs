# 生产部署说明

本文是 Spectra 生产环境的部署、初始化和日常运维基线。生产配置只通过环境变量或密钥管理系统注入；不要把真实数据库密码、Redis 密码、S3 密钥、MFA 密钥、Token 或证书私钥写入仓库。

浏览器演练、移动端/多端 E2E 和完整备份恢复演练属于独立发布门禁；它们不能被本地单元测试或 Flyway 门禁替代。

## 0. 当前验证范围与 1.0.0 发布边界

当前仓库使用 API 契约 `1.0.0`，不维护旧接口兼容层。本地验证覆盖 Flyway 单一 V1 基线、安全授权集成、PostgreSQL/Redis 故障 fail-closed 和 HTTPS 运行时检查；浏览器、多端并发及完整业务流程使用独立人工验收入口。

以下项目统一作为确定 `1.0.0` 正式版本后的发布/生产门禁：

- CI 中真实 PostgreSQL Flyway gate 的首次执行；
- PostgreSQL 备份恢复、隔离恢复、全局 logout 和 Flyway 回滚演练；
- 生产 CORS allowlist、反向代理 HTTPS 信任和 Cookie/CSRF 验收；
- 独立 S3 Object Lock archive bucket、归档完整性校验和恢复演练；
- Root break-glass 凭据分权、Recovery Code 运维流程和隔离演练。

这些门禁在发布前必须逐项形成责任人、执行记录和审计证据，不能用本地开发测试结果替代。

## 1. 生产拓扑和职责

```text
浏览器 / H5 / App / 小程序
            │ HTTPS
            ▼
    Nginx / Ingress / WAF
            │ /api
            ▼
       spectra-admin
       ├─ PostgreSQL：业务事实、权限、审计热数据
       ├─ Redis：服务端 Session、Refresh Rotation、验证码运行态
       └─ S3：普通文件 bucket；独立审计 archive bucket（Object Lock）
```

生产环境至少分离以下职责：

- 反向代理/WAF：TLS 终止、域名路由、限流、受控转发头和 API 暴露面。
- 应用运行账号：只使用最小权限数据库账号和 Redis/S3 运行时权限。
- 数据库迁移账号：只在发布窗口执行 Flyway，不作为应用运行账号。
- 运维/审计账号：执行备份、恢复、归档校验、全局会话撤销和故障处置，所有高风险动作留存工单与审计证据。

生产后端使用 `application-prod.yml`，默认监听 `80`、上下文路径为 `/api`，通常由代理对外提供 HTTPS。应用不应直接暴露在公网。

## 2. CORS、Cookie 和反向代理

### 2.1 CORS 必填配置

生产配置必须显式提供精确 Origin，例如：

```text
SPECTRA_CORS_REQUIRED=true
SPECTRA_CORS_ORIGIN_ALLOWLIST=https://admin.example.com,https://h5.example.com
```

示例域名必须替换为实际域名。每个值只包含 `scheme://host[:port]`，不带路径、不带通配符、不使用 `*`。多个 Origin 用英文逗号分隔。

规则如下：

- 生产只允许 HTTPS Origin；开发机的 `localhost` HTTP 例外不能复制到生产。
- `https://admin.example.com`、`https://admin.example.com/` 和带路径的 URL 不是同一个配置值，统一填写无尾斜杠的 Origin。
- CORS 不是授权机制。业务权限仍由认证主体、Role、Permission 和数据范围共同决定。
- 带 Cookie 的请求必须使用精确 Origin。禁止“允许凭证 + 通配符 Origin”。
- 原生 App 和微信小程序不受浏览器 CORS 机制约束，但仍必须使用正确的 API 地址、客户端类型和认证策略。
- 生产没有 Origin allowlist 时应用应启动失败；不要通过关闭 `SPECTRA_CORS_REQUIRED` 绕过配置问题。

### 2.2 Refresh Cookie 与 CSRF

生产默认值应保持如下组合：

| 项目 | 环境变量 | 生产要求 |
|---|---|---|
| Refresh Cookie 名称 | `SPECTRA_SECURITY_REFRESH_COOKIE_NAME` | `__Host-spectra-refresh` |
| Secure | `SPECTRA_SECURITY_REFRESH_COOKIE_SECURE` | `true` |
| Path | `SPECTRA_SECURITY_REFRESH_COOKIE_PATH` | `/` |
| Domain | `SPECTRA_SECURITY_REFRESH_COOKIE_DOMAIN` | 留空，保持 Host-only |
| SameSite | `SPECTRA_SECURITY_REFRESH_COOKIE_SAME_SITE` | `Strict` 优先 |
| CSRF Cookie | `SPECTRA_SECURITY_CSRF_COOKIE_NAME` | `XSRF-TOKEN` |
| CSRF Header | `SPECTRA_SECURITY_CSRF_HEADER_NAME` | `X-XSRF-TOKEN` |

只有在确有跨站业务需求、所有 Origin 已精确登记、代理 HTTPS 传递已验证且 CSRF 方案完成评审后，才允许使用 `SameSite=None`，并同时设置 `SPECTRA_SECURITY_REFRESH_COOKIE_SAME_SITE_NONE_ALLOWED=true`。`SameSite=None` 必须配合 HTTPS，不能单独作为修复手段。

### 2.3 反向代理转发头

```text
SERVER_FORWARD_HEADERS_STRATEGY=framework
```

代理必须：

- 删除客户端自行携带的 `Forwarded`、`X-Forwarded-Proto`、`X-Forwarded-Host` 和 `X-Forwarded-For`，再写入受控值。
- 只把真实外部 HTTPS 请求转发为 `https`，确保应用正确生成 Secure Cookie 和绝对地址。
- 将 `/api` 路径、Host、端口和请求 ID 的传递规则固定在代理配置中，并在发布验收时留存响应头证据。
- 不把应用端口直接暴露给公网；健康检查和管理入口使用内网或受控运维网络。

## 3. 生产环境变量

### 3.1 PostgreSQL、Redis 和 Flyway

| 分组 | 环境变量 | 要求 |
|---|---|---|
| PostgreSQL | `DB_URL`、`DB_USERNAME`、`DB_PASSWORD` | 使用生产数据库和最小权限账号；应用账号不使用超级用户 |
| Flyway | `SPECTRA_FLYWAY_ENABLED` | 发布时保持 `true` |
| Redis | `REDIS_HOST`、`REDIS_PORT`、`REDIS_DB`、`REDIS_PASSWORD` | 使用独立生产 Redis DB；按平台能力启用 TLS/网络白名单 |
| 代理 | `SERVER_FORWARD_HEADERS_STRATEGY` | `framework`，并配合受控转发头 |
| 服务端口 | `SERVER_PORT` | 只监听内网或容器网络端口 |

Flyway 的固定安全约束是：`baseline-on-migrate=false`、`validate-on-migrate=true`、`out-of-order=false`、`clean-disabled=true`。生产库不能执行 `flyway clean`，不能修改已执行的旧 migration；变更必须新增版本化 migration。

当前目标库只应用 `V1__init_db.sql`。该基线一次性建立目标 schema、字段顺序、技术主键、约束、索引、完整注释、运行时角色边界、Permission Catalog、安全策略、OA/通知/流程结构和普通参考种子；旧迁移中的兼容清理步骤不再作为独立版本保留。
- 该版本是迁移基线重整：已经执行过旧 `V1`～`V34` 的数据库不能直接用当前目录启动，否则会出现历史版本缺失或 checksum 不匹配；开发库应重建，保留数据的环境必须先执行经过审查的一次性数据/结构迁移，不能只用 `repair` 修改校验和。
- 用户、密码身份、凭据、MFA 和 RoleAssignment 由系统初始化 API 创建。
- 部门变更统一走 `/security/authorization` 的 Preview/Apply API，旧部门删除写入口不进入当前基线。
- 初始化 API 只写入 BCrypt 哈希，不在代码、文档或日志中保存密码明文；系统未初始化时，应用启动日志会输出一次随机初始化令牌，Redis 只保存该令牌的 SHA-256 摘要。
- 数据库初始化后，应核对 Flyway 历史连续成功、系统初始化状态和有效 DEV_OPS 数量；首个 Root 必须通过初始化 API 创建，不要只检查表是否存在。

### 3.2 安全密钥

以下值必须由密钥管理系统注入，不能使用公共默认值：

- `SPECTRA_SECURITY_MFA_ENCRYPTION_KEY`：TOTP 密钥 AES-GCM 加密密钥，UTF-8 长度必须为 32 字节。
- `SPECTRA_SECURITY_MFA_ENCRYPTION_KEY_VERSION`：当前加密版本；轮换期间按双版本迁移流程配置 previous key。
- `SPECTRA_SECURITY_AUTHORIZATION_CHANGE_TOKEN_HMAC_KEY`：Role/Assignment/组织 Preview-Apply token 的 HMAC 密钥，至少 32 字节。
- `SECURITY_VERIFICATION_CODE_HMAC_KEY`：验证码摘要 HMAC 密钥。
- `SPECTRA_SECURITY_VERIFICATION_CODE_MAX_ATTEMPTS`：验证码失败上限，生产按风险评审设置。
- 通知地址及敏感载荷 AES-GCM 密钥：由 DEV_OPS 首次登录后的系统设置引导自动生成并保存到 `spectra_core.sys_config`，不再通过环境变量注入。
- 如启用应用层接口加解密，密钥只通过 `spectra_core.sys_config` 的受控管理流程维护，不回退到旧的已移除环境变量。

密钥轮换必须先验证新旧版本的解密窗口、审计事件和回滚策略，再切换当前版本；完成迁移后删除 previous key。

## 4. S3 与安全审计归档

后端 S3 配置来源于 `spectra.file.upload.s3`：

| 环境变量 | 用途 |
|---|---|
| `S3_ENDPOINT` | S3/MinIO API endpoint |
| `S3_ACCESS_KEY` / `S3_SECRET_KEY` | 运行时访问凭据 |
| `S3_BUCKET` | 普通业务文件 bucket |
| `S3_REGION` | S3 region |
| `S3_SECURITY_AUDIT_ARCHIVE_BUCKET` | 安全审计独立归档 bucket |
| `S3_SECURITY_AUDIT_ARCHIVE_PREFIX` | 归档对象前缀，默认 `security-audit/` |
| `SPECTRA_SECURITY_AUDIT_ARCHIVE_BACKEND` | 生产必须为 `S3_OBJECT_LOCK` |

普通文件 bucket 和安全审计 archive bucket 必须分离。archive bucket 必须启用 S3 Object Lock 的 Compliance 模式或等价的不可变/WORM 能力；应用只允许写入带保留截止时间的对象和读取校验对象，不提供删除或覆盖审计归档的应用权限。

当前本机 `spectra-admin/.mise.local.toml` 具备普通 S3 endpoint、访问凭据、bucket 和 region 配置，但没有 `S3_SECURITY_AUDIT_ARCHIVE_BUCKET` 配置项。这不影响本地普通文件配置，却意味着切换生产 `S3_OBJECT_LOCK` 前必须由运维补齐独立 archive bucket，并完成 Object Lock、生命周期、跨区域/跨账号备份和恢复读取验证。本文不复制本机 S3 值。

上线前至少核对：

- 普通文件 bucket 与 archive bucket 的 IAM 权限、网络白名单和加密策略。
- archive bucket 已启用 Compliance retention，应用凭据没有删除、覆盖或缩短保留期的权限。
- 数据库 `security_audit_retention_policy.archive_backend` 与应用配置一致。
- 归档 manifest 的 `object_uri`、`content_sha256`、行数和保留截止时间可被独立运维账号复核。

## 5. 数据库完整初始化

### 5.1 初始化顺序

1. 确认当前连接不是生产库误指向；记录数据库、Redis、S3 的目标环境标识，不在工单中记录密码。
2. 创建可恢复的 PostgreSQL custom-format 备份，保存到受控备份存储，并抽样验证备份可读。
3. 停止应用写入或进入维护窗口，使用迁移账号运行 Flyway；禁止自动 baseline。
4. 确认 V1 成功，再启动应用。
5. 核对参考种子仍存在：权限目录、系统菜单、字典、文件类型和 OA/流程参考定义；行政区划是独立 JSON 数据包，若该环境需要完整区域树，必须在受控窗口单独执行区域导入并核对行数/层级。业务用户、部门、业务单据和通知运行数据不应被迁移伪造。
6. 核对初始化后的 Root：`spectra_core.sys_system_state.state = 'INITIALIZED'`，用户为 `ACTIVE`，身份为 `PASSWORD/LOCAL/ACTIVE`，凭据为 BCrypt，MFA 为 `TOTP/ACTIVE`，Role 为 `ROLE_DEV_OPS/DEV_OPS/ACTIVE`，RoleAssignment 为 `ACTIVE`，有效 DEV_OPS 数量符合 `root_policy` 的 `minEffectiveDevOpsUsers`/`maxDevOpsUsers` 约束。

### 5.2 首个 Root 的 MFA 引导

当前 V1 不预置账号、密码、TOTP 密钥或 Recovery Code。当前实现对 `ROLE_DEV_OPS` 强制 MFA；未完成 MFA 的 Root 不得创建普通 Redis Session。首次初始化 API 只在系统状态为 `UNINITIALIZED` 时可用。

首次部署时由授权运维人员完成：

1. 通过密钥管理系统配置 `SPECTRA_SECURITY_MFA_ENCRYPTION_KEY`，确认应用审计写入可用。
2. 启动应用后从受控的后端控制台日志读取初始化令牌；通过 `POST /system/initialization/start` 提交账号和密码，并携带 `X-Spectra-Initialization-Token`。令牌只用于启动初始化，不得复制到共享日志、工单或数据库。
3. 使用返回的 TOTP provisioning URI 完成登记，调用 `POST /system/initialization/mfa/confirm`，立即离线保存一次性 Recovery Code。
4. 调用 `POST /system/initialization/complete` 激活用户并创建 `ROLE_DEV_OPS` RoleAssignment；完成后返回登录页，通过正常登录流程建立首个 Session，并确认 `SPECTRA_SECURITY_MFA_REQUIRED_FOR_DEV_OPS=true`。
5. 首次登录后完成 `/system-guide` 系统设置引导，填写根部门名称、所属区域和组织类型，并选择接口加解密、通知模块和底部版权策略；启用版权时填写版权名称及 HTTP/HTTPS 跳转地址。后端在当前 DEV_OPS 用户上下文中创建根部门并建立主部门关系，启用项的密钥自动生成并保存到 `spectra_core.sys_config`，版权配置也保存到该表。
6. 另建日常运维账号和受控 break-glass 账号，不把首次初始化 Root 作为日常共享账号。Break-glass 是仅在正常 Root/MFA/认证链路不可用时启用的紧急恢复身份，必须独立保管、短时使用、全量审计并在事件结束后轮换；它不是普通管理员绕过 MFA 的 API。

初始化流程只允许在 `sys_system_state` 为 `UNINITIALIZED` 时启动；Redis 不可用时初始化令牌读取、挑战和最终完成操作均 fail-closed。系统完成初始化后会删除 Redis 中的令牌摘要。不要把初始化令牌、TOTP 明文或 Recovery Code 写入数据库脚本、环境模板或工单。

## 6. Redis 运维

Redis 只保存服务端 Session 聚合、Refresh Rotation、验证码、登录失败窗口和首次初始化令牌摘要等运行态数据，不保存完整 SecurityUser 或明文 Token。运维规则：

- 变更用户、密码、Role、Assignment、MFA 或安全策略后，按接口/运维流程撤销相关 Session；必要时执行全局 logout。
- 不在排障日志中输出 Access Token、Refresh Token、Cookie 或完整 Redis value。
- Redis 故障时安全写操作应 fail-closed；不要通过临时绕过权限或直接修改安全 key 恢复服务。
- 生产切换、密钥泄露或 Refresh replay 事件后，按事件等级撤销 Token Family，并保留操作时间、操作者和影响范围。
- Redis 备份如包含 Session 数据，按凭据和个人数据处理；恢复前先评估是否会复活已撤销会话。

## 7. 发布、回滚和日常检查

### 发布检查

- 确认镜像/构建产物、migration checksum、配置版本和工单版本一致。
- 确认生产 CORS allowlist、反向代理 HTTPS、Cookie/CSRF、数据库、Redis、S3 archive bucket 和 MFA key 均已注入。
- 先备份 PostgreSQL，再执行 Flyway；迁移失败时保持应用下线或只读，不手工修改 `flyway_schema_history`。
- 启动后检查健康端点、数据库连接、Redis PONG、普通文件 bucket 读写和审计写入。
- 记录迁移历史、Root 有效数量、审计策略、S3 archive 配置和告警状态。

### 回滚原则

- 应用版本回滚必须与 schema 兼容性一起评估；已执行的 migration 不通过删除历史或 `clean` 回滚。
- 如果 migration 或数据变更失败，保留现场证据，按备份恢复 Runbook 在隔离环境验证后再恢复业务。
- 不恢复已撤销的 Session、Refresh Family、Recovery Code 或已标记 replay 的安全事实。
- 生产回滚和恢复必须有双人复核、维护窗口、验证步骤和最终审计记录。

### 最小监控项

- 5xx、登录失败/锁定、MFA 失败、Refresh replay、权限变更和 Root 治理拒绝。
- PostgreSQL 连接池、锁等待、Flyway 失败、审计 append 失败和 outbox 积压。
- Redis 内存、连接、Keyspace、Session 异常增长和故障切换。
- S3 普通 bucket 失败、archive bucket 写入/读取/完整性校验失败、Object Lock 配置漂移。
- CORS 拒绝、代理 HTTPS/Forwarded 头异常和 CSRF 失败突增。

## 8. 1.0.0 发布前 CI Flyway 门禁

> GitHub Actions 的 CI Flyway gate 是 `1.0.0` 发布门禁，执行结果必须在发布记录中留存。

`Security Flyway PostgreSQL gate` 是 CI 中的数据库迁移和安全 schema 回归门禁，不是线上应用启动开关，也不会连接本机业务数据库。

它在 GitHub Actions 中启动一次性的 PostgreSQL 17 service，创建两个可丢弃数据库：

- 空库：验证单一 V1 完整初始化，检查目标表、权限目录、安全策略、审计归档 manifest、数据库角色、`sys_log` 结构化字段和旧表未进入目标结构。
- 非空库：验证 `baselineOnMigrate=false` 确实拒绝把未知非空数据库自动伪装成已迁移状态。

工作流还执行 `SecuritySchemaContractTest` 和 Root 并发治理测试，用于验证新环境初始化和迁移结构一致性；生产备份恢复、S3 Object Lock 真实验证、Root/MFA 运维引导和浏览器/多端 E2E 由相应发布门禁与 Runbook 验证。

本地对应测试默认关闭；若要运行，只能提供专用、可丢弃的数据库连接：

```text
SPECTRA_SECURITY_FLYWAY_POSTGRES_TEST=true
SPECTRA_SECURITY_FLYWAY_DB_URL=jdbc:postgresql://127.0.0.1:5432/<empty-db>
SPECTRA_SECURITY_FLYWAY_DB_USERNAME=<test-user>
SPECTRA_SECURITY_FLYWAY_DB_PASSWORD=<test-password>
```

不得把这些变量指向开发或生产数据库。V1 会创建运行时数据库角色，因此测试账号需要具备相应的 `CREATEROLE` 权限。

## 9. 需要业务/运维人员完成的事项

- 填写真实生产 CORS Origin 和代理信任规则，并完成一次 HTTPS/Cookie/CSRF 验收。
- 创建独立安全审计 archive bucket，启用 Object Lock Compliance，并配置 `S3_SECURITY_AUDIT_ARCHIVE_BUCKET`。
- 通过密钥管理系统注入数据库、Redis、MFA、授权变更、验证码、通知和 S3 凭据。
- 完成默认 Root 的 MFA enrollment、Recovery Code 离线保管、首次改密和日常/应急账号分离。
