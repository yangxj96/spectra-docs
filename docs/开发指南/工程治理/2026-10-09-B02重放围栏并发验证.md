## 实现与调用方

`RefreshTokenRotationStore.claim` 在单条 Redis Lua 命令中检查一次性声明、Family 围栏、Refresh Hash 和用户会话索引。正常有期限的 Refresh 首次消费时建立有 TTL 的 claim；重复消费原子地安装或延长 `sec:replay:<familyId>` 围栏，再返回重放结果。索引检查移到 claim 之后，使已轮换的旧 Refresh 即使不再出现在用户索引中，也能触发重放撤销；正常孤儿 Refresh 仍拒绝。未知 Lua 返回值、`null` 或连接异常拒绝操作。

重放或部分签发失败先安装 Family 围栏，再清理 Access 与 Refresh Family。围栏 TTL 至少覆盖当前 Access/Refresh 策略和 Redis 中尚存的 Family 状态；签发时 `sec:family:*` 的 TTL 覆盖 Access 与 Refresh 中较长者，避免策略缩短后围栏先于此前 Access 到期。签发前后核对围栏，Reader 即使看到尚未清理的 Session Hash，也拒绝属于已围栏 Family 的 Access；携带 Token 的 SecurityContext 读取同样重新核对 Redis。接口、Cookie 和响应模型没有改动。

CodeGraph 从 Framework 的 Refresh、签发、Reader、撤销端口追到 Core `LoginServiceImpl.refresh`、`SecuritySessionPortConfiguration` 与 `SecurityUserLookupPort`。当前源码 `rg` 核对 OA/Workflow 没有直接调用 Refresh 端口，但共享 Framework 的认证入口；全 Reactor 测试编译覆盖 Core、OA、Workflow。Web CodeGraph 核对 `AuthApi.refresh`、`auth.ts`、Fetch/XHR：Refresh 失败会清理本地会话，接口形状未变；B08 页面级身份失效仍未验收。

## 验证边界

并发测试用两个独立 Redis 连接和服务对象，通过锁存器固定“重放请求已读取旧 Refresh、首次轮换已移除旧 Access、新 Access 尚未写入”的交错；它证明该交错下重放立围栏且新 Access 不可用，**不等同于两个独立 JVM/应用进程**。Reader 测试另证明围栏设立后，即使 Session Hash 尚存，Access 也不能再次认证。策略收缩测试验证围栏比此前较长的 Access 活得更久。

仍未执行独立应用进程、Redis 断连后结果未知及恢复、Core 实际 HTTP/数据库入口、OA/Workflow 业务端到端和 Web 浏览器重登录流程。`BC-BASE-001` 还包含 `BASE-006` 的多实例 `max_sessions` 原子性，不能由本专项判为整体通过。完整门禁没有通过；本记录不关闭 `DIAG-BASE-004`、`IMP-BASE-003`、B02 或集中治理周期。
