# B02 会话并发配额验证（DIAG-BASE-006，2026-10-10）

## 实现与影响

Framework 签发 Session 时，在安全 Redis 内以 Lua 原子预留用户会话名额；`REJECT_NEW` 同时计算已经提交的用户索引与尚未提交的预留，并在提交前再次检查跨客户端的总名额。全部并发模式都建立预留，同用户同客户端的 `KICK_OLD` 只在没有其他待提交会话时获得互斥租约；`ALLOW` 的同端签发仍可同时预留。写完 Session、Refresh、Family 和摘要后，第二条 Lua 在确认预留未过期、同端踢旧租约仍归本次请求、Family 未被重放围栏撤销且用户索引有 TTL 后，原子提交用户索引及在线用户。失败清理只按本次 Access 摘要删除 `USER_CLIENT` 映射，避免误删其他成功签发的映射。预留和锁均有两分钟租约，租约丢失时拒绝本次签发并清理部分状态；异常中断后的占位会到期回收。安全 Redis 连接、命令或脚本结果不可确认时拒绝签发。

CodeGraph 与当前源码核对：Framework 的 `SecuritySessionIssuer` 经 `SecuritySessionPortConfiguration` 被 Core 登录端口使用，Refresh 轮换也回到同一签发方法。Core 的密码、短信、邮箱入口共用该端口；OA/Workflow 使用相同的认证和 Session 边界，没有独立签发入口。Web 的登录与 Refresh API、Cookie、响应形状没有变化；当前 Fetch/XHR 刷新失败会清理本地身份。本项没有修改 Web、OA 或 Workflow 源码，B08 的浏览器身份失效仍需单独验收。正式影响项为 `IMP-BASE-003`，其他 B02 安全事实源问题不由本项推定解决。

新增测试固定验证：两个独立 Redis 连接并行登录时 `REJECT_NEW` 已提交数不超过 `max_sessions`；同用户跨客户端的待提交名额也参与上限，且受限预留后另一客户端 `ALLOW` 先提交时再次拒绝受限会话；`ALLOW` 同端并发预留与 `KICK_OLD` 互斥；双连接并行踢旧只留下一个可刷新的 Family；租约丢失、Family 围栏和无 TTL 用户索引均拒绝提交，修复索引后可继续；连接到不可用的合成端口时拒绝，改用健康的隔离连接后可签发。旧 Access 过期但 Refresh 有效的踢旧、拒绝新会话及失败后旧 `USER_CLIENT` 映射保留也通过回归。测试使用独立连接和合成用户，并未启动两个应用进程。

## 尚未验证与状态

两条独立连接可证明 Redis 共享原子脚本与会话边界，但不能替代两个独立应用进程的登录/刷新/踢旧验收。故障恢复用例模拟拒绝连接后切换健康连接，未实际停止和重启 Redis 服务，也未验证健康就绪状态迁移。真实 HTTP 登录、刷新、错误状态和浏览器身份失效未运行。全后端 `verify` 被 Workflow Surefire 配置及命令级绕行后的 Core Checkstyle 阻断；Core 后续 PMD/SpotBugs 与 OA/Launch `verify` 未进入。`BC-BASE-001`、`IMP-BASE-003` 和 B02 仍保持部分验证/推进状态，不能据此宣称整批验收。
