# B02 后台通知身份验证（DIAG-CORE-034，2026-10-09）

## 源码与调用范围

原 `CoreNotificationRecipientDirectory.allowedByCurrentUserScope` 在 `currentUserId == null` 时直接放行任意收件人。现将普通 `resolve` 与 `resolveByLoginNames` 的非空用户收件人查询改为先要求认证身份，再读取账号、联系方式或授权快照；已认证请求仍按 `user:read` 的有效数据范围过滤。空用户收件人列表只供直接地址的安全验证码路径使用，不产生用户目录读取。

独立系统路径使用 `NotificationSystemActor` 登记固定来源模块、用途与模板，通知服务和网关各自校验，系统入队只接受明确用户 ID，拒绝直接地址或空收件人列表。Workflow `TaskServiceImpl` 从任务操作人与待办处理人登录名解析收件人，使用 `WORKFLOW_TASK`；OA 流程结果通知使用 `OA_WORKFLOW_RESULT`，合同到期 Quartz/手动受保护扫描使用 `OA_CONTRACT_REMINDER`；Core 服务监控告警使用 `SERVICE_MONITOR_ALERT`。仅 Workflow 身份可以按明确登录名查询。OA 公告、会议和文档的用户发起通知以及 Core 受控发送仍走普通身份与数据范围；登录/绑定验证码的直接地址请求没有用户收件人 ID，继续由原安全用途校验。CodeGraph、全工作区 `rg` 和当前源码复核了 Common 端口、Core 实现、OA/Workflow 调用方、Framework 安全上下文及 Web 受控发送类型；Web API 形状未改变。

静态复核确认 `sys_user` 和 `sec_user_contact` 实体没有 `@DataScope`，系统通知的用户及联系方式查询不受该拦截器的登录上下文检查阻断；这不等于已验证真实数据库投递。OA 合同 Quartz 路径在通知前调用 `ContractServiceImpl.getById` 读取带 `@DataScope` 的 `oa_contract`，无用户上下文时仍会被拒绝，属于同一影响图的独立上游待办。
