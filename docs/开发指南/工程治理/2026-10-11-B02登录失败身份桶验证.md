# B02 登录失败身份桶验证（DIAG-CORE-020，2026-10-11）

## 当前源码与改动

按 `spectra-admin` 后端 Skill、工程标准 §7/§8、台账 `DIAG-CORE-020` / `IMP-CORE-005` / `CHECK-CORE-020` 复核当前源码。原诊断指出登录查找使用 `trim`、`Locale.ROOT` 小写后的摘要，而失败锁定使用请求原文；当前 `LoginServiceImpl` 已在锁定检查、失败累加和成功清理三个入口统一调用 `AuthenticationIdentifierHash.digest`。运维定向清理也计算摘要，但此前先经过通用 `normalizeTarget`，拒绝首尾空格、非 ASCII 和超过 128 字符的标识。用户和导入模型允许最长 255 字符的邮箱，因此运维入口可能无法清除登录链已经建立的锁定桶。

此次让 `CacheManagementServiceImpl.clearLoginFailure` 直接调用同一个 `AuthenticationIdentifierHash.digest`，并在 Common `SecurityAuthenticationPort`、Framework `SecurityLoginFailureTracker` 的参数契约中明确只传规范化摘要桶。空白标识由同一摘要函数拒绝；确认与理由校验继续在清理前执行。没有更改 HTTP 路径、`username` 请求字段、Redis Key 模板、数据库结构或锁定阈值。

从后端目录执行 CodeGraph 查询登录用例、身份摘要、失败计数端口和运维清理入口，并用 `rg` 核对当前磁盘源码。直接调用方是 Core `LoginServiceImpl` 和 `CacheManagementServiceImpl`，经 Common/Framework 端口进入 `SecurityLoginFailureStore`；OA/Workflow 无直接失败计数调用，仍共享认证边界。从 Web 目录执行 CodeGraph 查询登录与缓存维护调用，Web `AuthApi.login` 和 `CacheManagementApi.clearLoginFailure` 继续提交原始登录标识，后端字段形状不变，因此本项无需修改 Web。部分 CodeGraph 索引提示文件晚于上次同步，相关实现以当前源码补查。

## 结论与边界

当前登录身份查找、失败锁定、成功清理和运维定向清理已使用同一规范化摘要桶；真实测试 Redis 的双连接并发、阈值及恢复清理有可核对证据。`DIAG-CORE-020` 可记为已修复。`CHECK-CORE-020` 仍为部分执行：没有启动两个独立应用进程，没有运行实际 HTTP 登录和运维清理入口，也没有真实 Redis 停启后的会话/登录恢复测试。完整门禁显式排除了 `RegionServiceTest`，OA/Workflow 无测试用例。`IMP-CORE-005` 涉及其他未解决问题，B02 的 `done_when` 仍未满足。
