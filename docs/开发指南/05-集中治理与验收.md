# 集中治理与验收

本文件定义 [[开发指南/04-工作区工程标准|工作区工程标准]] 的全量建账、一个集中统一周期及整体验收方式。它是新的工程治理入口，不重建已完成的 9/28 计划。

**当前状态：标准已确认，第一步文件枚举、第二步源码诊断与公共影响建账、第三步集中整改排序已完成；统一整改与整体验收尚未完成。** 当前全局状态仍为 `inventory_complete`，诊断记录见 GOV-001 / EV-DIAG-VERIFY-20261005，Skill 对齐见 GOV-007 / EV-SKILL-20261003。文件 reviewed、静态问题成立或诊断核对通过，均不代表问题已修复、行为已验证或集中治理已 accepted；后续状态和待办记录在 ledger.json（源码仓库的 `docs/开发指南/工程治理/ledger.json`）。

## 1. 全量建账的覆盖要求

先枚举整个工作区的相关代码、测试、配置、构建部署、脚本、插件与规则文档；按文件登记职责和范围，不能仅枚举 Controller 或 Service。依赖产物、外部安装缓存、索引、临时输出、生成产物及凭据不是手写源码审查对象，记录排除理由，生成链路单独核对。

OA、Workflow 与流程业务的独立治理记为暂缓。公共变更的影响分析继续覆盖它们，受影响文件登记为公共一致性范围，不能以整目录暂缓掩盖调用或运行影响。公私边界以职责及调用分析确定，不只根据文件夹名。

| 台账集合 | 必需信息 |
|---|---|
| coverage | 路径、职责、范围、审查状态、实际读取/分析时的内容摘要、已核对规则、问题及证据引用 |
| issues | 稳定 ID、规则/行为、文件或符号、问题与影响、优先级、处置、状态、例外及证据引用 |
| impacts | 变更源、直接与间接依赖/数据/协议/运行影响、共同改造范围、暂缓边界和验证 |
| exceptions | 具体规则与符号、实测值、必要性、风险、验证、责任区域、复评触发及状态 |
| evidence | 命令或场景、环境与工具版本、适用范围、时间、结果、产物与实际验证边界 |
| work_items | 规则和验证链路等治理工作、范围、处置及实现状态 |

使用结构化 ledger.json（源码仓库的 `docs/开发指南/工程治理/ledger.json`） 作为这些记录的事实源，说明文档和报告引用稳定 ID，避免不同文档各自维护相互冲突的状态。原始大型工具输出留在 `.temp/`；正式证据记录摘要、版本与可复现步骤，不依赖本机临时文件长期存在。

文件只有元数据或名称统计时标记为 enumerated，不标记 reviewed。读取、关系分析、行为验证分别记录，不能由“读过文件”推导“行为已验证”。源码变化后相应审查和证据应失效或复核。

## 2. 公共变更的完整影响分析

从目标项目运行 CodeGraph 查询定义、实现、调用和依赖，跨项目逐个查询；精确代码、配置、文档与遗漏候选使用 rg 核对。索引不完整或查询未命中需要记录并补查，不以无搜索结果证明没有影响。

每项公共变更至少核对以下关系，按实际职责补充：

1. 定义、序列化/持久化、入口及所有直接、间接调用方。
2. 授权上下文、事务参与、异步和生命周期，异常及失败结果。
3. 数据库迁移、Mapper/转换、缓存键和失效、任务状态、共享文件和多实例行为。
4. Web 生成协议、薄 API、页面模型、状态和用户反馈，插件公开导出及宿主依赖。
5. 装配、构建、配置、脚本、质量规则、测试及知识库。

先形成可核对的影响记录，再决定共同改造范围与验证。局部构建只能证明其实际范围，不能替代整个装配或跨端行为。暂缓区域需要的一致性改造同样建账；业务目标或已确认基线发生变化时重新讨论。

## 3. 复杂度与例外的自动核对

已确认阈值见主标准。落地先确认 PMD 实际解析版本、ESLint 实际适用配置和选项，为“等于/超过”及 mixed control flow、函数作用域、可选参数等建立边界样例；普通业务目标不能沿用旧 PMD 30/10000 或参数 10 的配置作为达标依据。

B00 已用固定 PMD 7.17.0 与 ESLint 9.39.2 的可重复样例校准普通方法/函数边界：圈复杂度 15 不报、16 报；Java NPath 200 不报、201 报；显式参数 5 不报、6 报（Web 样例包含可选和剩余参数）；Web 混合控制流嵌套 3 层不报、4 层报。PMD 的 `AvoidDeeplyNestedIfStmts` 对纯 `if` 的第 4 层报警，但对 `if`/`while`/`switch`/`if` 混合第 4 层不报警，后者仍需评审核对；不能以该规则通过推定 Java 混合嵌套达标。样例及复验入口为 `scripts/tests/complexity-calibration.tests.ps1`。本次阈值配置已对齐，存量违规仍待逐项整改或登记有效定点例外，不能声称复杂度治理完成。

定点抑制必须引用 exception ID，台账记录工具规则名称、路径和符号；记录测量工具版本与值。自动核对至少检查以下可核对事实：

- ID 唯一、必填字段、路径、符号、规则及证据引用存在且有效。
- 源码或工具配置的抑制范围与台账相符，没有未登记、扩大或整域抑制。
- 符号已移除、指标已达标、实质修改或工具口径变动时，记录及时失效或进入复评。
- 超标问题已按职责调整或对应有效例外，不能以调整阈值清空问题。

自动核对不能证明必要性和风险理由充分，也不能证明行为正确；这部分由评审和实际验证提供证据。现有工具覆盖不到的规则明确列为评审项，不虚构自动检查能力，不默认新增通用治理平台。

## 4. 一个集中统一周期

按完整范围建立清单后，可按公共契约、基础设施、应用用例及 Web 调用依赖组织内部工作顺序。每批执行目标检查，保持装配与契约一致；整体验收覆盖全部纳入范围，不能以少数批次完成替代整个周期。

每项问题最终处置为：完成并有验证证据；有效定点例外并有理由、风险与证据；或明确暂缓/阻塞且保持整体状态未验收。暂缓区域边界已由主标准定义，不能自行扩大。

全量文件和待行为清单已按第二步建账；待落实工作包括复杂度口径配置、例外自动核对、OpenAPI/TypeScript 契约链路、公共错误/时间/用例规则的整体迁移、真实依赖与多实例验证，以及规则入口的一致性。具体源码问题依据当前审查证据登记，不能由治理模板虚构。

2026-10-05 第二步诊断已将当前纳入文件审查、公共影响、旧 R1–R6 归并及待行为场景写入正式台账。GOV-001 关闭的是清单和诊断建账；GOV-005 的分析已完成，统一实现仍待实施，其余检查与验收工作继续按实际状态登记。文件 reviewed、静态问题成立或诊断辅助核对通过，均不代表问题已修复或行为已验收。当前阶段状态及复核方法见 [[开发指南/工程治理/README|工程治理台账]]，集中治理全局仍未 accepted。

第三步已在 `ledger.json` 的 `remediation_cycle` 排定 B00–B10：先建立可靠检查和隔离验证入口，再处理脚本安全、安全事实源与必需依赖；随后统一协议/时间/编辑版本，按共同影响整改上传、通知及共享任务、应用用例、Web 和插件宿主，最后整体验收。各批记录稳定问题/影响 ID、修改范围、依赖、检查与完成条件。B01 与 B02 可在 B00 后并行；共同接口的仓库内调用方及受影响暂缓区域随批一致迁移。此排序不改变问题 pending、行为 not_run 或全局 inventory_complete 状态。

## 5. 验证与验收证据

规则与状态采用行为验证；真实数据库及 Redis 隔离验证事务、乐观锁、并发、缓存/安全故障、领取和恢复；契约检查实际 HTTP、序列化及生成漂移；关键 Web 路径验证 loading、失败、版本冲突、会话和旧请求覆盖；脚本与插件按纳入职责验证。

覆盖率提供遗漏线索，不代替这些行为和风险要求。异步/时间场景使用可控时间及明确竞争条件，验证开始、失败、恢复及结果未知路径，不依靠固定等待。

以下是当前已有检查入口，**列出命令不表示已经执行或通过**；完整门禁还包括待落实的契约、例外及真实依赖验证。均在对应项目目录使用 mise 执行：

| 项目 | 已有适用入口 |
|---|---|
| 后端 | `mise exec -- .\mvnw.cmd verify '-Dspotless.ratchetFrom=NONE'`；不以跳过测试作为完整验收 |
| 插件 | `mise exec -- pnpm run format:check`、`mise exec -- pnpm run build`；核对 ESM/CJS/类型/样式及宿主 |
| Web | `mise exec -- pnpm run format:check`、`lint`、`type-check`、`test`、`build`，逐项调用项目脚本 |
| 文档 | 内容、相对链接、规则入口与状态；网站发布另按网站同步流程执行 |

检查与自动修复分开；前端 `prestart` 目前会修复源码，不能作为 CI 只读检查入口。常见命令见 [[开发指南/01-常见命令|01-常见命令]]。数据导入、迁移与故障验证只使用隔离依赖。

## 6. 整体完成条件

集中治理仅在以下条件全部满足后标记 accepted：

1. 全部纳入文件有覆盖记录，缺失、未审查及源码变更后的失效记录已处理；暂缓/排除理由明确。
2. 问题逐项完成或对应有效例外；影响图覆盖仓库内调用方及跨项目运行关系。
3. 架构、协议、类型、时间、空值及错误等基线一致，生成和例外链路能够核对漂移。
4. 关键行为、失败路径、真实依赖、多实例及恢复要求有实际证据。
5. 适用的完整格式、静态、类型、测试、构建和契约门禁通过，规则与文档入口一致。
6. 记录发布/恢复或数据迁移相关边界，交付说明如实区分已经验证和未验证内容。

未扫描、未验证、检查未执行及尚未实现的门禁都不能记为 passed；也不能据旧计划文件缺失否定已完成的工作。
