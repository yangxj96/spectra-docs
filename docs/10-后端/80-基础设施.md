## 服务监控、告警与运行时诊断

服务监控由统一调度内核的 `system.monitor.collect-snapshot` LOOP 适配器采集，默认每 10 秒记录 CPU、系统内存、JVM 堆/非堆、线程、GC 和 HTTP 请求指标，进程内保留最近 180 个采样点；`system.monitor.diagnostic-cleanup` 负责诊断文件过期清理。`CoreHealthRegistry` 收集已装配的 `DependencyHealthContributor`，`CoreHealthAggregator` 负责超时、异常、重复归属校验和 `UP/DEGRADED/DOWN/UNKNOWN` 聚合；`ServiceMonitorServiceImpl` 与 framework 的 `ActuatorHealthContributorAdapter` 共享同一聚合入口。PostgreSQL、Redis、Flowable、Core 通知 Provider 和 Core 对象存储检查分别由对应 contributor 提供，不在 Core 复制第二份连接检查。`GET /api/service/monitor/overview` 返回当前摘要、数据新鲜度、运行时信息和依赖健康状态；历史趋势持久化到 PostgreSQL，支持 30 分钟、6 小时和 24 小时范围查询、服务端数量限制、保留时间配置和过期清理。依赖检查只返回状态、耗时、最近检查时间和脱敏说明，不暴露连接串、环境变量、异常原文或凭据。

告警规则支持启停、比较方式、阈值、级别、连续触发次数、通知冷却和乐观锁，覆盖 CPU、系统内存、JVM 堆、HTTP 错误率、P95、PostgreSQL 和 Redis 状态；每条规则只保留一个活动事件，恢复后进入历史状态。告警通过统一站内消息网关只通知当前有效的 `ROLE_DEV_OPS` 用户，消息内容不包含连接信息、路径、异常原文或凭据。

## 调度内核基础设施

`SchedulerBootstrapService` 以 `SmartLifecycle` 管理内部 tick，tick 使用 JDK 25 虚拟线程执行器，但调度入口仍保持单线程串行，以确保 PostgreSQL 状态机、租约和控制命令边界可审计。启动前读取并校验 PostgreSQL 中的 V4 调度定义和代码注册表，按 `system.default-timezone` 初始化 Cron 计划；应用正常停止时按实例身份和会话版本 CAS 回收本实例活动 LOOP 会话，异常退出则等待租约过期；数据库不可用时保持 `NOT_READY`，不领取执行、不应用 LOOP 控制命令、不确认结果。Redis 不承载调度锁、租约或结果状态。

运行时诊断为只读能力，提供内存池、GC、线程状态、数据库连接池、Redis 延迟和 HTTP 慢接口信息；线程转储和堆转储通过异步任务执行，文件写入系统临时目录下的受控子目录，数据库只保存随机相对文件名，下载前重新校验任务状态、过期时间和目录边界。堆转储默认关闭，线程/堆转储分别限制文件大小、磁盘空间、并发数和保留时间，过期文件自动清理。

## 数据库 (PostgreSQL + MyBatis-Plus)

- **BaseEntity** 提供统一的审计字段和软删除支持
- MyBatis-Plus 提供分页插件、乐观锁插件、自动填充
- 软删除通过 `deleted` 字段实现（NULL = 未删除）
- 主键使用 UUID v7（时间有序），通过 `uuid-creator` 生成

### Schema 分配

| Schema | 表前缀 | 模块 | 说明 |
|---|---|---|---|
| `spectra_core` | `sys_*` | spectra-core | 用户/角色/权限/菜单/部门/字典/日志/通知 |
| `spectra_oa` | `oa_*` | spectra-oa | OA 办公（资产/考勤/日历/通讯录/合同/文档/会议/公告/报表） |
| `spectra_core` | `file_*` | spectra-core/core.upload | 文件上传（类型、资产、会话、分片、业务引用） |
| `spectra_workflow` | `wf_*` + `act_*`/`flw_*` | spectra-workflow | 工作流业务表 + Flowable 引擎表 |

- 每个实体通过 `@TableName(value = "xxx", schema = "spectra_xxx")` 显式指定 schema
- 不使用 MyBatis-Plus 全局 `db-config.schema` 配置
- Flowable 引擎通过 `flowable.database-schema: spectra_workflow` 独立配置

## Redis

- 用途：普通缓存、Session 共享、分布式锁、验证码存储
- 配置类：`RedisConfiguration`
- 配置日志不输出连接 URL、密码或其他连接凭据

### 安全 Redis 强依赖

安全模块的 Redis 是 Token、Session、Refresh Token 轮换、防重放、验证码、登录失败锁定和请求 nonce 的事实源，不采用缓存降级语义。安全 Redis 连接失败、超时、命令异常，或 Lua 脚本返回 `null` 等无法确认状态的情况，统一抛出 `SecurityRedisUnavailableException`：

- Token 鉴权过滤器清理上下文并停止请求链，返回 HTTP 503；
- MVC 中的认证、验证码和会话操作返回 HTTP 503 `安全会话服务暂不可用`；
- 不把 Redis 故障解释为 Token/验证码不存在或校验失败；
- 不允许本地快照、内存回退或继续向业务层传递 Token。

所有安全 Redis 操作通过 `SecurityRedisExecutor` 统一执行。普通业务缓存仍可按缓存规范采用缓存特有的容错策略，但不能复用到安全事实源。

安全运行态统一使用 `sec:*` 命名空间，Key 中只允许摘要或非敏感标识，不允许出现明文 Token：

| Key 前缀 | 用途 |
|---|---|
| `sec:sess:*` | Access Session 事实源 |
| `sec:uc:*` / `sec:ut:*` / `sec:online` | 用户-客户端索引、用户 Token 集合和在线用户集合 |
| `sec:family:*` / `sec:rt:family:*` | Access/Refresh Token Family |
| `sec:rt:*` / `sec:rt:claim:*` / `sec:replay:*` | Refresh 映射、一次性消费声明和重放撤销围栏 |
| `sec:fail:*` | 登录失败锁定 |

旧 `auth:*`、`sec:v2:*` 和兼容 Key 不再由运行时读取或写入；运行时不维护双命名空间迁移逻辑。

## 统一审计与日志安全

- 业务入口统一使用 common 的 `@Audit` 或 `AuditService`；Core 的 `AuditAspect` 只收集调用元数据并同步提交统一审计服务。
- Core 的 `CoreAuditService` 是统一路由入口：普通操作事件在当前 PostgreSQL 事务中进入 operation-log outbox，worker 再幂等写入 `sys_log`；安全事件进入 `SecurityAuditWriter`，安全 sink 仍保持同步失败阻断。
- `spectra-log-base` 和 `spectra-log-spring-boot-starter` 已从 Maven 聚合和源码树移除，不再维护第二套日志技术入口。
- framework 的 `RequestCorrelationFilter` 统一清洗或生成 `X-Request-ID`、`X-Correlation-ID`，将最终值写入 MDC 和 common 的 `RequestCorrelationContext`；响应始终返回清洗后的值，请求结束后清理线程上下文。
- `@Audit`、安全审计、普通操作日志 outbox 和通知请求共用关联 ID；通知请求保存到 `ntf_request.trace_id`，后台 worker 使用任务级 correlation ID，不用空字符串冒充链路值。
- Prometheus 只使用固定低基数业务标签；`/actuator/prometheus` 在开发和生产均不进入匿名白名单，生产应放在受控管理网络入口，不暴露 `env`、`beans` 等敏感管理端点。
- `DefaultAuditSanitizer` 在统一入口前递归处理对象、Map、集合和数组；密码、Token、Authorization、Cookie、API Key、私钥、验证码等字段统一替换为 `***`
- Bearer Token、URL 查询参数中的签名和凭据也会被脱敏，之后才执行长度截断，避免长值绕过字段级保护
- 单元测试覆盖统一审计契约、嵌套结构、Bearer Token 和预签名 URL；运行态 canary 已验证原始刷新令牌不会进入 MyBatis SQL 参数日志
- 安全变更成功事件在同一 PostgreSQL 事务中写入 `spectra_security.sec_security_change_outbox`，使用内容幂等键、`SKIP LOCKED`、租约续期、退避和 `DEAD_LETTER`；它只服务归档、索引、通知或外部同步，不替代同步安全事实表。
- 安全审计归档由 Core manifest/worker 驱动，必须完成对象存在性、SHA-256、字节长度、源分区范围和行数校验才进入 `VERIFIED`；开发环境无对象存储时保持 `PENDING`，不伪造归档成功。生产后端必须与活动保留策略的 `archive_backend` 一致。

## Spring Security

集成方式：
- `spectra-framework` 的 `FrameworkModule` 注册安全自动配置
- `spectra-common` 提供认证主体、Token、Session、验证码和安全上下文端口；`spectra-framework` 提供对应技术实现
- `spectra-core.security.authentication` 下的 `AuthenticationController`、`LoginServiceImpl` 和 `VerificationCodeServiceImpl` 处理认证用例
- 多种登录 Provider 策略模式
- Token 基于 Spring Security 实现
- 当前请求时区按“用户时区 → `system.default-timezone` → UTC”解析，供 `TimeMapper` 和其他时间工具统一使用

### 异常处理优先级

所有 `@RestControllerAdvice` / `@ControllerAdvice` 需显式设置 `@Order`，优先级递减：

| @Order | Advice | 异常类型 |
|---|---|---|
| `-100` | `KaptchaExceptionAdvice` | 验证码过期/不匹配 |
| `-100` | `SqlExceptionAdvice` | 数据库（唯一键冲突、SQL语法、完整性违规） |
| `-50` | `LoginExceptionAdvice` | 登录失败 |
| `-10` | `CommonExceptionAdvice` | 方法级权限不足（403）、参数校验、运行时异常、Exception 兜底 |

**注意事项**：
- `@Order` 越小优先级越高，**必须 < 0** 才能排在 Spring 默认错误处理（`BasicErrorController`）之前，否则异常会被 HTML 错误页吞掉
- 新增 Advice 时选择合适的 `@Order` 值插入，同值的不同 Advice 处理不同类型异常时互不干扰
- `ResponseModifyAdvice` 是 `ResponseBodyAdvice`，不受异常处理优先级影响
- 方法级 `@PreAuthorize` 抛出的 `AccessDeniedException` 发生在 MVC 调用链内，由 `CommonExceptionAdvice` 映射为 HTTP/业务码 403；过滤器链权限异常仍由 `RestAccessDeniedHandler` 处理
