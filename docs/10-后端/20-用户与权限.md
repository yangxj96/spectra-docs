# 用户与权限

> 基于目标 Role/Permission/RoleAssignment 模型的用户认证与授权体系，模块路径：`spectra-core`。

## 当前实现状态与版本边界

安全认证授权重构已完成开发阶段的代码和本地集成验收，当前运行时以 `spectra_security` 目标模型为唯一事实源，干净数据库由 Flyway 单一 `V1__init_db.sql` 初始化。所有 API 版本统一为 `1.0.0`，开发阶段不保留旧 API 兼容层、双写逻辑或旧授权入口。

当前模型的强制不变量如下：

- `RoleAssignment` 是用户获得角色和授权的唯一运行时入口；角色能力、可授予能力、Access Boundary 和 Grant Boundary 分离维护。
- Boundary 必须绑定到 `(RoleAssignment, Permission)`；不同 Permission、不同 Assignment 不得借用范围。
- 认证 Token 为 Opaque Token，Redis 只保存摘要和安全运行态；安全 Redis 不可用时认证、刷新、MFA 和会话操作 fail-closed。
- `ROLE_DEV_OPS` 按配置要求首次登记 MFA；任何用户都可以自行启用 TOTP MFA，显式停用后保留 `REVOKED` 登记且不强制重复绑定。Recovery Code 只保存 Hash，Root 治理受最后有效 Root 和 `maxDevOpsUsers` 约束。
- 前端菜单和按钮只负责展示，后端独立执行 Permission、authorityLevel、Boundary、账号状态和 Session 校验。
- 安全表统一使用 `id UUID`、`created_by`、`created_at`、`updated_by`、`updated_at`、`deleted`、`version` 公共字段；关系表保留业务唯一键，审计表保留分区追加写入例外。

本地 PostgreSQL/Redis 故障注入、cross-assignment、Flyway 单一 V1 基线和 HTTPS 运行时检查已完成；浏览器、多端并发和完整业务流程仍由人工逐项验收。CI、备份恢复、生产 CORS/代理、S3 Object Lock 和 break-glass 演练属于 `1.0.0` 发布及生产运维门禁，详见 [[../60-部署运维/50-生产部署说明]]。

## `core.security` 包结构

认证和授权属于同一安全能力边界，但保持独立子域，避免认证凭证与授权决策相互耦合：

- `core/security/authentication`：认证身份、密码凭证、登录 Provider、认证身份绑定和 MFA；内部统一按 `controller`、`javabean`、`mapper`、`service`、`service/impl`、`util` 组织。
- `core/security/authorization`：角色、Permission Catalog、RoleAssignment、Access/Grant Boundary、Scope 和授权变更 Preview/Apply；内部按 `controller`、`javabean`、`mapper`、`service`、`service/impl`、`domain` 组织。
- `core/security/audit`：安全审计查询、归档和指标；内部按 `controller`、`javabean`、`domain`、`repository`、`service`、`policy`、`observability`、`util` 组织。
- `core/security/policy`：登录端 Session 策略和密码策略；内部按 `controller`、`javabean`、`service`、`service/impl`、`repository` 组织。
- `core/security/change`、`root`：变更治理和 Root 治理等横向安全能力；实现类按 `service/impl` 或 `repository` 归位。
- `core/security/initialization`：首次系统初始化状态、DEV_OPS 用户创建、MFA 登记和首个 RoleAssignment。

因此，代码统一位于 `com.devops00.spectra.core.security` 命名空间下，但认证与授权仍按职责分开演进；每个子域内部遵循统一分层包结构，禁止将 Controller、DTO/VO、Service 实现或持久化适配器直接堆放在子域根包。

## 核心实体

### AuthenticationIdentity / PasswordCredential（认证身份与凭证）

| 字段 | 类型 | 说明 |
|---|---|---|
| `identifierHash` | String | 规范化登录标识摘要，不保存原始标识 |
| `methodCode` / `providerCode` | String | 认证因子与提供方；密码为 `PASSWORD` / `LOCAL` |
| `state` | String | 身份状态 |
| `passwordHash` | String | 密码哈希 |
| `expiresAt` | Instant | 临时密码过期时间；普通密码为 `null` |
| `mustChange` | Boolean | 是否必须修改密码 |
| `failedAttempts` / `lockedUntil` | Integer / Instant | 凭证失败锁定信息 |

旧 `Account/sys_account` 仅作为一次性迁移输入，目标 V1 运行时不再读取。

### User（用户）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | UUID | 主键 |
| `employeeNo` | String | 工号/员工编号，企业内唯一 |
| `avatar` | String | 头像 URL |
| `status` | UserStatus | `ACTIVE`、`LOCKED`、`DISABLED`、`DEPARTED` |
| `statusReason` | String | 最近一次生命周期变更原因 |
| `departedAt` | Instant | 离职时间 |
| `realName` | String | 姓名 |
| `phone` / `email` | String | 手机号码和邮箱；邮箱同时作为默认登录账号 |
| `language` / `timezone` | String | 用户语言和时区 |
| `primaryDepartmentId` | UUID | 主部门；组织 membership 与 DataScope 正交 |
| `securityVersion` | Long | 安全相关变化版本 |

只有 `ACTIVE` 用户可以创建新的认证 Session。`LOCKED` 是安全策略临时锁定，`DISABLED` 是管理员停用，`DEPARTED` 是离职终态；重新入职不自动恢复历史授权。用户管理页面的新增/编辑通过用户开通提交接口同时保存资料、多角色 RoleAssignment 以及被移除的授权实例，任一环节失败都会回滚本次事务。用户列表的授权状态只评估当前未撤销的 RoleAssignment，角色替换或移除后保留的 `REVOKED` 历史记录不会使当前完整授权显示为“部分失效”。角色删除后仍保留的历史 RoleAssignment 不参与运行时授权视图。

管理员调用 `PUT /user/password/reset/{uid}` 时，服务端生成 24 小时有效的随机临时密码，仅在本次响应中返回明文；数据库只保存密码哈希，审计记录不包含明文。临时密码登录后会携带“必须修改密码”标记，服务端只允许查看必要的用户页面、修改密码或退出，修改成功后撤销该用户全部 Session；临时密码过期后必须重新重置。

### SecurityRole（目标角色）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | UUID | 主键 |
| `name` | String | 角色名称，角色目录内唯一 |
| `code` | String | 稳定角色编码（ROLE_xxx）；新增未指定时生成 `ROLE_` 加 8 位大写十六进制后缀，编辑不可修改 |
| `authorityLevel` | Integer | 管理边界等级；用于限制授权操作者可授予的目标角色，不代表业务角色级别或排序 |
| `roleKind` | String | 角色种类：`BUSINESS`、`DEV_OPS`、`SYSTEM_ADMIN`、`AUDITOR`；后三类各只有一个内置角色 |
| `state` | String | `ACTIVE` 或 `DISABLED` |
| `systemManaged` | Boolean | 是否系统托管 |
| `remark` | String | 角色备注 |
| `version` | Long | 并发版本 |

角色名称由服务层和数据库共同保证唯一；新增角色固定为 `BUSINESS` 类型、管理边界等级 `1`、非内置，业务角色可以创建多个。`DEV_OPS`、`SYSTEM_ADMIN`、`AUDITOR` 分别对应唯一的 `ROLE_DEV_OPS`、`ROLE_ADMIN_SYSTEM`、`ROLE_AUDIT` 内置角色，类型、编码、名称、等级和生命周期不可修改。管理边界等级越高，越有资格为更低等级的目标角色授予权限；Root 运维角色基线为 `1000`，普通业务角色为 `1~999`。普通角色的等级在角色授权 Preview/Apply 流程中调整，必须经过等级权限、Grant Boundary、版本校验、影响预览、审计和会话撤销；角色编辑页只允许普通业务角色修改名称和备注。角色状态通过独立的启用/禁用接口变更，禁用前必须确认没有活动授权实例；删除使用逻辑删除，内置角色不可编辑、启用、禁用或删除。

### Permission（Permission Catalog）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | UUID | 主键 |
| `resource` | String | 资源标识 |
| `action` | String | 动作标识 |
| `code` | String | 稳定权限编码 |
| `allowedScopeModes` | Set | 该 Permission 允许的 Scope 模式 |

### RoleAssignment / Boundary

`RoleAssignment` 是用户获得角色和权限的唯一运行时授权入口。角色能力、可授予能力、Access Boundary 和 Grant Boundary 分开维护；授权写入必须经过 Impact Preview/Apply、版本校验和安全变更审计。

`AuthorizationProfile` 是可复用的授权方案模板，不是运行时授权对象。方案使用稳定的 Role/Permission 编码、Role version 和部门业务编码保存配置；应用到用户时仍必须重新通过 RoleAssignment Preview/Apply、目标用户安全版本和 Grant Boundary 校验。方案版本变化不会修改已经生成的 RoleAssignment，启用/停用只控制后续使用，删除方案模板也不会撤销已经生成的 RoleAssignment。

用户批量导入是独立的 Preview/Apply 任务：Preview 只保存固定模板行、文件摘要和校验结果，工号由后端按任务幂等键和行号生成并写入规范化暂存行，Apply 校验通过后立即返回 `APPLYING` 任务，并在有界后台执行器中逐行复用用户创建及 RoleAssignment Preview/Apply；前端通过任务详情查询已处理行数和最终状态。任务使用操作人 + 幂等键、规范化请求摘要、授权方案版本摘要和一次性短时 token 防止重复应用；后端不接受内部 Role、Assignment、Permission 或 Scope UUID。

用户开通已收口为连续流程：Web 新增和编辑分别使用完整页面路由，按“基本信息 → 授权方案 → 角色授权”组织；已有角色在授权方案步骤加载，角色新增和移除只在该步骤完成，角色授权步骤用 `3.1`、`3.2` 等子节点逐个配置 Boundary。步骤切换只保存在页面状态，最终由用户开通接口一次性提交用户资料、多角色授权和移除列表，失败时由事务回滚，不留下半成品用户。

`SecurityRoleMenu` 只负责菜单 UX 配置，不代替接口上的 `@PreAuthorize` 与 Permission 校验。当前用户菜单从活动 RoleAssignment 和角色菜单关系合并，并自动补齐导航所需祖先目录。

## 内置角色权限基线

权限编码采用树形 `MODULE:*` + 动作叶子节点 `MODULE:QUERY/INSERT/UPDATE/DELETE`。权限判断使用叶子节点，父节点仅用于管理树展示。已完成的超级运维契约是：`security.administrators` 配置的有效 `ROLE_DEV_OPS` 无需维护角色权限关系，即可在后端权限判断中隐式获得 `*`，Token 权限上下文返回 `*`，`GET /menu/current` 返回全部有效菜单；前端 Store、按钮指令和菜单树统一消费这一通配符语义。Root 的 GLOBAL 数据范围、租户边界、敏感字段脱敏、MFA 和审计仍由独立安全校验负责。

| 角色 | 权限边界 |
|---|---|
| `ROLE_DEV_OPS` 运维管理员 | 默认管理员角色；目标为隐式 `*` 全权限和全部有效菜单，可执行系统配置、密钥、监控、密码重置、文件信息、权限树和消息发送等运维专属接口 |
| `ROLE_ADMIN_SYSTEM` 系统管理员 | 用户/角色/菜单/部门/字典等系统管理 CRUD、OA 基础 CRUD、工作流业务操作；不可执行运维专属接口 |
| `ROLE_USER` 用户 | 本人数据范围内的 OA 查询/新增/修改、流程办理、消息、文件上传等业务操作；不含系统管理和删除权限 |
| `ROLE_AUDIT` 审计员 | 跨模块只读查询，不含任何写权限 |

角色菜单树按权限边界同步：`ROLE_DEV_OPS` 应隐式显示完整导航，新菜单无需逐项授权；`ROLE_ADMIN_SYSTEM` 显示系统管理、OA、工作流和示例菜单，但隐藏监控、系统配置、文件信息等运维菜单；`ROLE_USER` 显示首页、OA 业务和示例菜单；`ROLE_AUDIT` 显示首页及审计所需的只读菜单。关联表只保存普通角色的 `MENU` 叶子节点，当前用户菜单接口自动补齐父级目录。

当前后端已将 Permission Catalog、RoleAssignment、菜单 UX 和 `/security/context` 接到目标授权模型；接口权限仍以 Permission-specific AuthorizationSnapshot 和 `@PreAuthorize` 为准，菜单仅用于导航和按钮展示。

## 认证流程

支持 **三种登录方式**：

| Provider | 类名 | 说明 |
|---|---|---|
| 用户名密码 | `LoginUsernamePasswordProvider` | 标准账号密码登录 |
| 邮箱验证码 | `LoginEmailProvider` | 邮箱验证码登录 |
| 短信验证码 | `LoginSmsProvider` | 手机短信验证码登录 |

认证入口：`core.security.authentication.controller.AuthenticationController` → `LoginServiceImpl` → Provider 策略；验证码发送由同一认证子域的 `VerificationCodeServiceImpl` 负责。

当 `SPECTRA_SECURITY_MFA_REQUIRED_FOR_DEV_OPS=true` 时，尚未登记过 TOTP 的 `ROLE_DEV_OPS` 密码登录采用二阶段流程；完成过登记但已显式停用的 DEV_OPS 保留 `REVOKED` 记录，不会再次强制绑定。其他角色和普通用户默认不强制 MFA，但可以在个人中心的安全设置中自主登记 TOTP。任何已登记 ACTIVE TOTP 的用户，无论使用密码、短信还是邮箱完成第一阶段登录，都会返回 5 分钟短期 MFA challenge，且不会创建普通 Session；随后调用 `/security/authentication/mfa/verify` 校验 TOTP 或一次性 Recovery Code。DEV_OPS 首次登录或尚未登记 TOTP 的用户通过 `/security/mfa/setup/totp/enroll`、`/security/mfa/setup/totp/confirm` 完成登记后调用 `/security/authentication/mfa/complete`。已登录用户可通过 `/security/mfa/status` 查询状态，使用 `/security/mfa/totp/enroll`、`/security/mfa/totp/confirm` 登记，使用 `/security/mfa/totp/disable` 在再次验证后停用。challenge 只存储在 Redis 的 `sec:mfa:challenge:*` 命名空间中，成功消费、过期或达到失败次数上限后失效。
