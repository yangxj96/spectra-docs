# 用户与权限

> 基于目标 Role/Permission/RoleAssignment 模型的用户认证与授权体系，模块路径：`spectra-core`。

## 当前实现状态与版本边界

安全认证授权重构已完成开发阶段的代码和本地集成验收，当前运行时以 `spectra_security` 目标模型为唯一事实源，干净数据库由 Flyway 单一 `V1__init_target_schema.sql` 初始化。所有 API 版本统一为 `1.0.0`，开发阶段不保留旧 API 兼容层、双写逻辑或旧授权入口。

当前模型的强制不变量如下：

- `RoleAssignment` 是用户获得角色和授权的唯一运行时入口；角色能力、可授予能力、Access Boundary 和 Grant Boundary 分离维护。
- Boundary 必须绑定到 `(RoleAssignment, Permission)`；不同 Permission、不同 Assignment 不得借用范围。
- 认证 Token 为 Opaque Token，Redis 只保存摘要和安全运行态；安全 Redis 不可用时认证、刷新、MFA 和会话操作 fail-closed。
- `ROLE_DEV_OPS` 强制 MFA；Recovery Code 只保存 Hash，Root 治理受最后有效 Root 和 `maxDevOpsUsers` 约束。
- 前端菜单和按钮只负责展示，后端独立执行 Permission、authorityLevel、Boundary、账号状态和 Session 校验。
- 安全表统一使用 `id UUID`、`created_by`、`created_at`、`updated_by`、`updated_at`、`deleted`、`version` 公共字段；关系表保留业务唯一键，审计表保留分区追加写入例外。

本地 PostgreSQL/Redis 故障注入、cross-assignment、Flyway 单一 V1 基线和 HTTPS 运行时检查已完成；浏览器、多端并发和完整业务流程仍由人工逐项验收。CI、备份恢复、生产 CORS/代理、S3 Object Lock 和 break-glass 演练属于 `1.0.0` 发布及生产运维门禁，详见 [[../60-部署运维/50-生产部署说明]]。

## `core.security` 包结构

认证和授权属于同一安全能力边界，但保持独立子域，避免认证凭证与授权决策相互耦合：

- `core/security/authentication`：认证身份、密码凭证、登录 Provider、认证身份绑定和 MFA；内部统一按 `controller`、`javabean`、`mapper`、`service`、`service/impl`、`util` 组织。
- `core/security/authorization`：角色、Permission Catalog、RoleAssignment、Access/Grant Boundary、Scope 和授权变更 Preview/Apply；内部按 `controller`、`javabean`、`mapper`、`service`、`service/impl`、`domain` 组织。
- `core/security/audit`：安全审计查询、归档和指标；内部按 `controller`、`javabean`、`domain`、`repository`、`service`、`policy`、`observability`、`util` 组织。
- `core/security/policy`：登录端 Session 策略和密码策略；内部按 `controller`、`javabean`、`service`、`service/impl`、`repository` 组织。
- `core/security/change`、`root`：变更治理和 Root 治理等横向安全能力；实现类按 `service/impl` 或 `repository` 归位。
- `core/security/initialization`：首次系统初始化状态、DEV_OPS 用户创建、MFA 登记和首个 RoleAssignment。

因此，代码统一位于 `com.devops00.spectra.core.security` 命名空间下，但认证与授权仍按职责分开演进；每个子域内部遵循统一分层包结构，禁止将 Controller、DTO/VO、Service 实现或持久化适配器直接堆放在子域根包。

## 核心实体

### AuthenticationIdentity / PasswordCredential（认证身份与凭证）

| 字段 | 类型 | 说明 |
|---|---|---|
| `identifierHash` | String | 规范化登录标识摘要，不保存原始标识 |
| `methodCode` / `providerCode` | String | 认证因子与提供方；密码为 `PASSWORD` / `LOCAL` |
| `state` | String | 身份状态 |
| `passwordHash` | String | 密码哈希 |
| `mustChange` | Boolean | 是否必须修改密码 |
| `failedAttempts` / `lockedUntil` | Integer / Instant | 凭证失败锁定信息 |

旧 `Account/sys_account` 仅作为一次性迁移输入，目标 V1 运行时不再读取。

### User（用户）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | UUID | 主键 |
| `username` | String | 用户名 |
| `avatar` | String | 头像 URL |
| `status` | UserStatus | `ACTIVE`、`LOCKED`、`DISABLED`、`DEPARTED` |
| `gender` | Short | 性别 |
| `primaryDepartmentId` | UUID | 主部门；组织 membership 与 DataScope 正交 |
| `securityVersion` | Long | 安全相关变化版本 |

只有 `ACTIVE` 用户可以创建新的认证 Session。`LOCKED` 是安全策略临时锁定，`DISABLED` 是管理员停用，`DEPARTED` 是离职终态；重新入职不自动恢复历史授权。

### SecurityRole（目标角色）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | UUID | 主键 |
| `name` | String | 角色名称 |
| `code` | String | 稳定角色编码（ROLE_xxx） |
| `authorityLevel` | Integer | 授权等级 |
| `roleKind` | String | 角色种类 |
| `systemManaged` | Boolean | 是否系统托管 |
| `version` | Long | 并发版本 |

### Permission（Permission Catalog）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | UUID | 主键 |
| `resource` | String | 资源标识 |
| `action` | String | 动作标识 |
| `code` | String | 稳定权限编码 |
| `allowedScopeModes` | Set | 该 Permission 允许的 Scope 模式 |

### RoleAssignment / Boundary

`RoleAssignment` 是用户获得角色和权限的唯一运行时授权入口。角色能力、可授予能力、Access Boundary 和 Grant Boundary 分开维护；授权写入必须经过 Impact Preview/Apply、版本校验和安全变更审计。

`SecurityRoleMenu` 只负责菜单 UX 配置，不代替接口上的 `@PreAuthorize` 与 Permission 校验。当前用户菜单从活动 RoleAssignment 和角色菜单关系合并，并自动补齐导航所需祖先目录。

## 内置角色权限基线

权限编码采用树形 `MODULE:*` + 动作叶子节点 `MODULE:QUERY/INSERT/UPDATE/DELETE`。权限判断使用叶子节点，父节点仅用于管理树展示。目标契约是 `security.administrators` 配置的超级运维角色无需维护角色权限关系，即可在后端权限判断、Token、前端按钮和菜单树中获得一致的全量权限；实现收口见 [[90-计划/P-运维管理中心建设计划]]。

| 角色 | 权限边界 |
|---|---|
| `ROLE_DEV_OPS` 运维管理员 | 默认管理员角色；目标为隐式 `*` 全权限和全部有效菜单，可执行系统配置、密钥、监控、密码重置、文件信息、权限树和消息发送等运维专属接口 |
| `ROLE_ADMIN_SYSTEM` 系统管理员 | 用户/角色/菜单/部门/字典等系统管理 CRUD、OA 基础 CRUD、工作流业务操作；不可执行运维专属接口 |
| `ROLE_USER` 用户 | 本人数据范围内的 OA 查询/新增/修改、流程办理、消息、AI、文件上传等业务操作；不含系统管理和删除权限 |
| `ROLE_AUDIT` 审计员 | 跨模块只读查询，不含任何写权限 |

角色菜单树按权限边界同步：`ROLE_DEV_OPS` 应隐式显示完整导航，新菜单无需逐项授权；`ROLE_ADMIN_SYSTEM` 显示系统管理、OA、工作流和示例菜单，但隐藏监控、系统配置、文件信息等运维菜单；`ROLE_USER` 显示首页、OA 业务和示例菜单；`ROLE_AUDIT` 显示首页及审计所需的只读菜单。关联表只保存普通角色的 `MENU` 叶子节点，当前用户菜单接口自动补齐父级目录。

当前后端已将 Permission Catalog、RoleAssignment、菜单 UX 和 `/security/context` 接到目标授权模型；接口权限仍以 Permission-specific AuthorizationSnapshot 和 `@PreAuthorize` 为准，菜单仅用于导航和按钮展示。

## OA P0 权限点

通用申请与请假接口使用独立权限域，保持与既有 `MODULE:ACTION` 约定一致：

| 权限 | 用途 |
|---|---|
| `OA_APPLICATION:QUERY` | 申请分页、详情、类型和工作台摘要查询 |
| `OA_APPLICATION:UPDATE` | 通用申请撤回、取消 |
| `OA_LEAVE:QUERY` | 请假分页与详情 |
| `OA_LEAVE:INSERT` | 新建请假草稿 |
| `OA_LEAVE:UPDATE` | 修改、提交、撤回、取消请假 |
| `OA_WORKBENCH:QUERY` | Dashboard 工作台摘要 |
| `OA_NOTICE:QUERY` | 公告分页、详情和可见范围查询 |
| `OA_NOTICE:INSERT` | 创建公告草稿 |
| `OA_NOTICE:UPDATE` | 发布、撤回、标记已读 |
| `OA_CALENDAR:QUERY` | 查询本人及共享日程 |
| `OA_CALENDAR:INSERT` | 创建个人日程 |
| `OA_CALENDAR:UPDATE` | 修改个人日程 |
| `OA_CALENDAR:DELETE` | 删除个人日程 |
| `OA_MEETING:QUERY` | 查询会议 |
| `OA_MEETING:INSERT` | 创建会议和参会邀请 |
| `OA_MEETING:UPDATE` | 参会响应、签到和纪要 |
| `OA_REIMBURSEMENT:QUERY` | 报销分页、详情和状态查询 |
| `OA_REIMBURSEMENT:INSERT` | 新建报销草稿 |
| `OA_REIMBURSEMENT:UPDATE` | 修改、提交、撤回和取消报销 |
| `OA_REIMBURSEMENT:PAYMENT` | 审批通过后登记付款 |

报销、采购权限树和内置角色授权已经完成迁移，并包含在全库备份 `docs/sql/db.dump` 的 `spectra_core` schema 中，不再保留或重复执行独立迁移 SQL；未从数据基线初始化的环境如缺少菜单节点，应通过菜单和角色管理功能补齐授权。

敏感接口统一使用 `hasRole('ROLE_DEV_OPS')`：服务监控、系统配置、RSA 密钥读写、用户密码重置、权限树增删改、文件信息删除、内部消息发送和区域基础数据写入。普通接口按模块动作权限校验，个人资料/菜单当前用户等自服务接口仅要求已认证。

## 认证流程

支持 **三种登录方式**：

| Provider | 类名 | 说明 |
|---|---|---|
| 用户名密码 | `LoginUsernamePasswordProvider` | 标准账号密码登录 |
| 邮箱验证码 | `LoginEmailProvider` | 邮箱验证码登录 |
| 短信验证码 | `LoginSmsProvider` | 手机短信验证码登录 |

认证入口：`core.security.authentication.controller.AuthenticationController` → `LoginServiceImpl` → Provider 策略；验证码发送由同一认证子域的 `VerificationCodeServiceImpl` 负责。

当 `SPECTRA_SECURITY_MFA_REQUIRED_FOR_DEV_OPS=true` 时，`ROLE_DEV_OPS` 的密码登录采用二阶段流程：第一阶段只校验账号密码并返回 5 分钟短期 MFA challenge，不创建普通 Session；已有 TOTP 登记的账号调用 `/security/authentication/mfa/verify` 校验 TOTP 或一次性 Recovery Code，首次登录的账号通过 `/security/mfa/setup/totp/enroll`、`/security/mfa/setup/totp/confirm` 完成登记后调用 `/security/authentication/mfa/complete`。challenge 只存储在 Redis 的 `sec:mfa:challenge:*` 命名空间中，成功消费、过期或达到失败次数上限后失效。
