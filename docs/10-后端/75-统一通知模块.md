# 统一通知模块

`spectra-notification` 是通知领域的独立 Maven 模块，包名为
`com.devops00.spectra.notification`，由 `spectra-launch` 装配。业务模块通过
`spectra-common.notification.NotificationService` 快捷发送通知，不直接写通知表或依赖渠道实现；
`NotificationGateway` 仅作为通知模块内部的底层网关契约。

## 当前边界

- PostgreSQL schema 为 `spectra_notification`，表前缀为 `ntf_`。
- `ntf_request` 表示一次逻辑通知，`ntf_task` 表示“接收人 × 渠道”任务，`ntf_delivery` 保存投递尝试。
- `ntf_inbox_message` 是消息中心的站内收件箱，`ntf_user_preference` 保存用途 × 渠道偏好，`ntf_template` 保存带名称的模板版本，`ntf_send_preview` 保存受控发送的短时非敏感 Preview 快照；模板版本使用 `version_digest` 固化内容摘要，Request 记录实际渠道模板快照，Task/Delivery 记录模板版本和渲染快照。
- `IN_APP` 由定时 Worker 投递，并使用 `task_id` 幂等写入收件箱；SMS/EMAIL 支持阿里云短信、腾讯云短信、SMTP、通用 HTTP JSON 和内置 MOCK Provider，具体供应商投递在 Provider 健康检查通过前仍由安全门禁阻断，不会伪装成成功。运维端测试发送必须显式提供测试地址和 `SEND_TEST` 确认词，测试目标只在内存中使用，不写入业务通知链路；MOCK 只在最终发送点输出脱敏日志，其他流程仍写入真实 Delivery。
- Provider 配置通过 `/notification/admin/providers` 管理，非敏感配置写入 `spectra_core.sys_config` 的 `notification.provider.sms/email`，AccessKey Secret、SecretKey、SMTP 密码或 HTTP Token 单独以 AES-GCM 密文写入 `.secret` 配置键；管理端只返回配置状态、Key ID、更新时间、最近健康检查时间和脱敏原因，页面切换查询时复用当前进程的健康检查结果；配置变更或服务重启后仍按 fail-closed 规则要求重新检查。短信配置包含地域、凭据标识、已审核签名、模板编码，腾讯云额外包含 `SmsSdkAppId` 和模板参数顺序；邮件配置包含 SMTP 主机、端口、用户名、发件地址、SSL/STARTTLS 和发件人名称。`NotificationProvider` SPI、供应商适配器、`SmsNotificationSender`、`EmailNotificationSender` 和 Provider Runtime 已隔离 HTTP/供应商细节；只有通过 `POST /notification/admin/providers/{channel}/health` 的渠道才允许 Worker 调用外部网络，`POST /notification/admin/providers/{channel}/test` 只用于明确测试地址的受控测试发送。外部回执使用 `POST /notification/provider/callback/{channel}` 接入，匿名入口必须携带 `X-Notification-Signature: sha256=<HMAC-SHA256(raw body)>`，复用当前渠道 Secret 验签；只按 Provider+消息 ID+渠道查找既有 Delivery，回执只更新 Delivery/Task，正文仅保存摘要和白名单错误码，重复正文返回 `DUPLICATE`，未知消息 ID、未配置 Secret 或签名错误均拒绝处理。
- 模板渲染器对标题、正文和 HTML 模板统一执行变量声明校验：只允许安全变量名占位符，正文不能直接透传单个占位符，缺失、多余或非法双大括号均拒绝保存/预览/发布；HTML 额外拒绝脚本、事件属性以及 `javascript:`、`vbscript:`、`data:`、`file:` URL scheme。参数 Schema 的 `properties.<name>.sensitive` 可声明敏感参数；模板声明为敏感的字段必须从 `sensitiveParameters` 传入，普通参数不能代替，未声明的敏感参数也会被拒绝。`NotificationPolicy` 固化用途 × 渠道矩阵：绑定手机号验证码仅允许 SMS，绑定邮箱验证码仅允许 EMAIL，登录/重置密码验证码允许 SMS/EMAIL，普通用途允许 IN_APP/SMS/EMAIL；模板服务、Gateway 按同一矩阵校验并按用途选择模板。
- 内置 `MOCK` Provider 位于生产运行时；健康检查通过后由 Worker 正常投递并写入 Delivery，只在最终发送点输出脱敏的渠道、收件人、标题和正文快照，不访问第三方服务。
- Core 提供收件人目录适配器，只返回启用用户和已验证的手机号/邮箱；直接地址只允许安全用途，并在 Request/Task 中使用 AES-GCM 密文存储。
- 收件人目录在展开业务受众前执行当前用户数据范围：`SELF` 只允许本人，`GLOBAL` 允许显式收件人，部门/自定义范围只允许解析到范围内的用户；系统任务无认证上下文时仅接受调用方显式用户 ID，不把全局或部门范围扩展为私人收件箱可见性。
- Worker 使用 `FOR UPDATE SKIP LOCKED`、处理租约超时恢复、CAS 抢占、指数退避、过期跳过和 Request 状态汇总。
- Worker 对每次 Provider 结果写入 `ntf_delivery`；仅明确的 `PROVIDER_RATE_LIMITED` 按任务最大尝试次数退避，Provider 异常和 `UNKNOWN` 记录为未知结果并停止无条件重试，避免把不确定结果伪装成失败后重复发送。
- 提供低基数 `NotificationMetrics` 指标门面、`notification` 健康检查和批量敏感密文清理任务；清理只处理终态/过期记录，不输出业务正文、地址或用户标识。
- `NotificationPostgresIntegrationTest` 提供 9 项真实 PostgreSQL 回归（事务回滚、并发幂等、任务/站内信唯一约束、双 Worker 锁领取、租约恢复 CAS、过期过滤、敏感密文清理和关键索引）；当前目标库不保留旧 Core 通知表，不再执行旧消息/偏好迁移测试。仅在设置 `SPECTRA_NOTIFICATION_POSTGRES_TEST=true` 并提供 `DB_URL`、`DB_USERNAME`、`DB_PASSWORD` 时启用。
- 免打扰窗口由 `NotificationDoNotDisturbPolicy` 按用户本地时间判断，支持跨午夜；Core 收件人目录同步提供用户时区，偏好 API 按当前用户时区解析和回显开始/结束时间。
- 管理端提供通知运行概览、Request/Task/Delivery 脱敏分页、Request/Task 详情、失败任务重试、未完成任务取消和渠道可用性查询。运行概览通过 `GET /notification/admin/overview?hours=24` 返回 1–168 小时窗口内的渠道可用性、队列摘要、投递失败率、UNKNOWN 数量、连续小时趋势和最近脱敏错误；管理分页默认最近 31 天，Request/Task 精确 ID 关联查询不受默认时间窗口影响。
- 管理端受控发送通过 Preview/Apply 接口联通模板、明确用户/部门下级/角色受众、当前数据范围、用户偏好和渠道可用性；Preview 只返回统计、跳过原因、脱敏样例和 10 分钟一次性令牌，快照绑定操作人、请求摘要和受众解析摘要，不保存完整用户清单、地址或敏感参数；Apply 重新校验后只调用统一 `NotificationGateway`。
- 模板管理按 `templateGroupCode` 聚合展示，一个逻辑模板可以绑定多个渠道；底层 `ntf_template` 仍按“渠道 × 版本”保存记录，版本号按渠道独立维护。每个模板渠道最多一个 `DRAFT`、最多一个当前发布记录（`PUBLISHED` 或 `DISABLED`），可以有多个 `ARCHIVED` 历史版本。草稿没有启用/禁用状态，`PUBLISHED` 表示已发布且启用，`DISABLED` 表示已发布但禁用；发布新草稿时旧的当前发布版本自动归档，禁用渠道可以重新启用。
- 包结构按职责扁平分层：Controller 位于 `controller`，Entity/From/VO/Converter/领域枚举位于 `javabean` 对应子包，Mapper 位于 `mapper`，应用 Service 接口与实现位于 `service`、`service/impl`；Provider SPI 与实现位于 `provider`、`provider/impl`，渠道 Sender 位于 `sender`、`sender/impl`，Worker 和请求状态推进位于 `dispatch`，纯脱敏等工具位于 `utils`，配置与属性分别位于 `configuration`、`properties`。
- 七个通知实体统一继承 `BaseEntity`，所有 JSONB 字段显式使用 `PgJsonbTypeHandler`；表结构以 `docs/sql/spectra_notification/建表.sql` 为唯一契约，包含审计字段、软删除、乐观锁和标准约束/索引命名。

## 快捷发送服务

业务模块统一注入 `com.devops00.spectra.common.notification.NotificationService`，使用
`NotificationSendRequest` 构造请求。常用的站内通知只需要模板、渠道、收件人和模板参数，幂等键、业务引用、来源模块和链接按场景补充：

```java
notificationService.send(NotificationSendRequest.inApp(
                "oa:notice:" + noticeId + ":publish",
                NotificationPurpose.OA_NOTICE,
                receiverIds,
                NotificationTemplateCode.OA_NOTICE_PUBLISHED)
        .parameter("title", title)
        .parameter("content", content)
        .businessReference("OA_NOTICE", noticeId.toString())
        .sourceModule("OA")
        .link("/oa/notice?id=" + noticeId)
        .build());
```

模板参数默认为空集合，因此无参数模板可以直接调用 `build()`；参数值不能为 `null`，需要空文本时由调用方传入空字符串。安全验证码等直接地址场景使用
`NotificationSendRequest.direct(...)`，验证码放入 `sensitiveParameter`，不可放入普通参数。

`NotificationService` 提供三种单渠道快捷入口：`sendInApp`、`sendSms` 和 `sendEmail`，分别发送站内信、短信和邮件给已解析的用户收件人；需要一次投递多个渠道时使用 `sendToUsers` 传入多个 `NotificationChannel`。验证码等未登录安全场景使用 `send(NotificationSendRequest.direct(...))`，直接地址可以携带一个或多个短信/邮件渠道。所有请求的渠道可用性、单渠道/多渠道校验和网关转换都在 `NotificationService.send(...)` 内统一完成，不再由业务调用方依赖 `NotificationGateway`。

### 模板名称和敏感参数

模板除了 `templateGroupCode` 外必须维护 `templateName`，管理端列表和版本历史优先展示模板名称，编码用于稳定调用。模板参数 Schema 使用标准 `properties` 节点声明变量，项目扩展 `sensitive: true` 标识敏感字段：

管理端的新增和草稿编辑使用独立页面，不在模板列表弹窗中编辑。编辑入口按渠道打开：已有草稿直接回填，没有草稿时只把当前发布或历史版本加载到页面内存，点击保存时才创建草稿。保存可以选择“保存为草稿”或“保存且发布”；同一模板渠道最多保留一个草稿。历史版本只读，不在历史列表提供操作列。

模板编辑页按渠道展示字段并在保存、预览时只提交当前渠道适用的内容；后端模板策略也会校验这组约束：站内信使用标题和纯文本正文；短信使用纯文本正文和供应商模板编码；邮件使用邮件主题、纯文本正文、HTML 正文和供应商模板编码。切换渠道后，不适用的字段会清空，接口也会拒绝短信标题、站内信供应商编码等无效配置。

```json
{
  "properties": {
    "code": { "type": "string", "sensitive": true },
    "userName": { "type": "string" }
  }
}
```

调用方必须将 `code` 放入 `sensitiveParameter("code", code)`，而 `userName` 放入普通 `parameter("userName", userName)`。通知 Gateway 会在模板渲染前校验两个参数集合与模板声明完全匹配；敏感参数及由其渲染出的标题、正文继续以密文保存，模板管理页同时展示敏感参数名称。

## 公共请求

`NotificationSendRequest` 是业务侧不可变请求，包含 `requestId`、`idempotencyKey`、`purpose`、渠道、用户收件人、受限直接地址、模板组、非敏感参数、敏感参数、业务弱引用和站内跳转链接。通知模块内部将其转换为底层 `NotificationRequest`，再由 `NotificationGateway` 执行幂等、偏好、模板和安全校验。普通参数禁止出现验证码、密码、Token 等敏感字段；敏感参数和外部地址由通知模块使用 AES-GCM 加密后才落库，缺少密钥时入队失败。

用途和渠道分离：用途使用 `NotificationPurpose`，渠道使用 `NotificationChannel`。安全用途不能由普通偏好关闭；普通用途默认使用 `IN_APP`，用户偏好只影响可选渠道。

### 验证码安全契约

验证码只在生成和调用 Provider 的短暂内存中以明文存在。Redis 仅保存基于
`SECURITY_VERIFICATION_CODE_HMAC_KEY` 的 HMAC-SHA256 摘要，并使用
`SECURITY_VERIFICATION_CODE_MAX_ATTEMPTS` 限制校验次数；成功、过期、超限或投递失败都会清理摘要和尝试计数。相同渠道、地址和有效期窗口通过
`setIfAbsent` 与稳定幂等键去重，禁止自动重试 `UNKNOWN` Task。Request、Task、Delivery、日志、指标和 API 响应均不得包含验证码明文。

### 链接白名单

站内消息链接默认只允许 `/login`、`/security/authentication/`、`/oa/`、`/workflow/`、`/notification/`、
`/notification-center/`、`/system/` 和 `/file/`；系统设置引导会将白名单保存到
`spectra_core.sys_config` 的 `notification.allowed-link-prefixes`。Gateway 对外部 URL、协议相对 URL、反斜杠、路径穿越和编码后的 `..` 一律拒绝，并对未命中白名单的相对路径 fail-closed。

## 消息中心 API

当前用户 ID 始终从认证上下文取得，Self API 不接收 `userId`，Service 层的查询、已读和删除条件均包含收件人和软删除条件。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/notification/list` | 当前用户分页查询；支持 `purpose`、`is_read`、关键词和时间参数 |
| GET | `/notification/{id}` | 当前用户消息详情 |
| GET | `/notification/unread-count` | 当前用户未读数 |
| PUT | `/notification/{id}/read` | 标记当前用户的一条消息已读 |
| PUT | `/notification/read-all` | 当前用户全部已读 |
| DELETE | `/notification/{id}` | 删除当前用户的一条消息 |
| POST | `/notification/batch-delete` | 仅删除当前用户拥有的批量 ID |
| GET/PUT | `/notification-center/preferences` | 用途 × 渠道偏好矩阵 |

## 调用方迁移

Security 验证码、OA 的会议/公告/文档/请假/采购/报销/合同提醒以及 Workflow 待办与审批结果均通过公共 `NotificationService`，并使用稳定幂等键。通知模块的管理查询、受控发送和快捷服务实现仍在内部使用 `NotificationGateway`，业务模块不得绕过快捷服务直接组装底层请求。Core 中旧的通知 Entity、Mapper、Service、Controller 和 Mapper XML 已移除；旧 `spectra_core.sys_notification` 与 `sys_notification_setting` 仅存在于离线迁移脚本，当前 V1 运行库不再保留。

当前干净基线的通知运行表由 Flyway V1 创建，模板生命周期唯一约束由 Flyway V2 补充；旧 Core 通知表不再进入目标结构。模板数据状态调整直接在当前数据库执行，不通过迁移脚本写入业务数据；`docs/sql/spectra_notification/建表.sql` 作为最终结构审查参考，运行时读写只使用 `spectra_notification`。

## 核心能力与运行边界

统一通知模块包含单元回归、验证码安全契约、免打扰跨午夜/用户时区规则、Self API 用户 A/B 认证上下文与偏好绑定、管理端角色矩阵、Service 隔离契约、数据范围/受众边界、链接白名单、低基数指标、健康检查、敏感密文清理和真实 PostgreSQL 事务/并发基线。未登录访问通知 Self API 返回 `401 用户未登录`；`codex-notify-*` 测试账号覆盖登录、Bearer Token、Token 刷新/登出、消息列表/详情/未读/已读/混合批量删除隔离、偏好隔离及 ROLE_USER/ROLE_AUDIT/ROLE_DEV_OPS 管理端矩阵。浏览器验收覆盖铃铛、抽屉、分类筛选、详情、已读、删除和偏好保存/恢复。

通知中心运维链路覆盖 UNKNOWN 人工确认和受控重试、模板管理、受控发送 Preview/Apply、内置 MOCK、阿里云/腾讯云/SMTP Provider、回执幂等、脱敏运维页面和 Provider 沙箱验收。完整链路为模板 → 受众预览 → Gateway → Task → Provider → Delivery → 运维页面；配置、API 和实现分别以本页、API 总览、配置清单和源码为准。
