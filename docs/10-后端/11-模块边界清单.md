# 01 号任务：模块边界清单

> 本清单是 1.0.0 基线的架构盘点与实施记录，不改变 API、数据库结构或业务行为。盘点对象为 `spectra-admin` 后端，系统按单租户、非 SaaS 运行。安全能力已完成从独立 starter 模块向 `common`、`framework` 和 `core` 的合并。

## 使用规则

- 当前路径是事实证据，不直接等同于最终归属；最终归属以 [[12-能力归属矩阵]] 为准。
- 本清单记录模块、包、依赖、配置和重复能力；安全模块合并已完成，其他未完成项仍按对应批次推进。
- `spectra-launch` 是组合根；`spectra-core` 是必选系统核心，并内置统一通知与文件上传；OA、Workflow 是可选业务能力，未来 ERP 也按同一方式接入。
- 技术基础设施不因为 core 必选就全部放进 core：Web、Redis、MyBatis、加密和安全技术实现保留在 framework；core 只拥有系统必需的业务编排和领域能力。
- Flowable schema 中的 `tenant_id_` 等字段是引擎兼容字段，本清单不把它们当成应用租户能力。

## Maven 模块树

```text
spectra-admin
├── spectra-config                         配置资源，无 Java 主代码
├── spectra-common                         公共类型与跨模块契约（保留已登记的历史技术桥接）
├── spectra-framework                      Web/MVC/Redis/MyBatis/加密等技术基础设施
├── spectra-launch                         Spring Boot 组合根
└── spectra-modules
    ├── spectra-core                       必选系统核心（含通知、文件上传）
    ├── spectra-workflow                   可选流程引擎
    └── spectra-oa                         可选 OA
```

Maven 聚合关系为：根项目聚合 `spectra-config`、`spectra-common`、`spectra-framework`、`spectra-launch` 和 `spectra-modules`；`spectra-modules` 聚合五个业务模块。安全能力随 `spectra-common`、`spectra-framework` 和 `spectra-core` 发布，不再单独聚合或发布 starter。

## 包域盘点

| 模块 | 当前一级包域 | 盘点结论 |
|---|---|---|
| common | `annotation`、`base`、`constant`、`dto`、`exception`、`scheduler`、`utils` 等 | `scheduler` 是跨模块契约候选；`base`/`utils` 需要按是否依赖 Spring、数据库和业务语义拆分 |
| framework | `config`、`mvc`、`redis`、`cache`、`exception`、`encryption` 等 | 技术基础设施候选，不能持有业务 Entity/Mapper/Service |
| framework security | `framework.configure.security` 下的 `autoconfiguration`、`configuration`、`filter`、`holder`、`redis`、`strategy` 等 | Spring Security 运行机制、过滤器、Session/Token/验证码 Redis 适配归 framework；安全用户、认证用例、授权和安全审计领域归 core；公共端口归 common |
| core | `audit`、`common`、`scheduler`、`security`、`system`、`user` | `audit`、`security`、`user`、`system`、`scheduler` 是 core 必选能力；`common` 子包需拆分重复基础设施 |
| core.notification | `configuration`、`controller`、`dispatch`、`health`、`javabean`、`mapper`、`observability`、`provider`、`sender`、`service`、`strategy`、`utils` 等 | Core 内置通知领域闭环；通过 common.notification 向外提供稳定端口 |
| core.upload | `api`、`configure`、`controller`、`health`、`javabean`、`mapper`、`properties`、`service`、`storage`、`validation` | Core 内置文件能力；通过 common.port.file 和 common.port.audit 提供跨域端口，健康检查实现统一协议 |
| workflow | `configuration`、`controller`、`javabean`、`mapper`、`service` | 流程引擎领域保持独立；OA 通过 workflow 端口交互 |
| OA | `application`、`asset`、`calendar`、`contact`、`contract`、`document`、`leave`、`meeting`、`notice`、`purchase`、`reimbursement`、`report`、`supply`、`support`、`workbench` | 全部属于可选 OA；对 core 的用户/组织/调度引用需通过稳定公共契约收敛 |

## 自动配置与运行配置

- `spectra-launch` 的启动入口和 Flyway 装配属于组合根。
- Security 的 Spring Boot 自动配置属于 `spectra-framework`，通过 `FrameworkModule` 显式注册；它可以提供技术 Bean，但不得通过组件扫描把业务实现隐式注入 core。统一 Log 技术切面和业务编排属于 `spectra-core`。
- Core 通过自己的 `AutoConfiguration.imports` 注册唯一 Core 入口，入口扫描 `com.devops00.spectra.core` 下全部核心子域；Workflow、OA 由 `spectra.modules.<name>.enabled` 控制，缺省保持启用。`spectra.notification.enabled` 只控制通知业务功能，不控制 Core 装配。`spectra-launch` 在上下文创建阶段校验 OA/Workflow 的必需 adapter，Core 始终装配。
- `spectra-config` 集中 `application-*.yml` 和 Flyway 资源；02-Task 1 已对源码、配置、POM 和运行时依赖树复核，未发现 Nacos、Spring Cloud、Eureka、Consul、Zookeeper 或远程配置中心生效项；02-Task 2/3 和本次 Task 4 已将清理结论固化为持续门禁，不需要删除当前不存在的组件。
- Redis 的 Token、Session、验证码、防重放和登录失败锁定仍由安全模块维护，并继续遵守安全 Redis fail-closed 约束。
- 本任务不处理租户配置；应用层不允许新增租户注册、租户切换、租户管理员、租户数据源、租户级缓存 key 或租户 API 参数。
