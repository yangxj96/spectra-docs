# 01 号任务：能力归属矩阵

> 这份矩阵回答“代码最终应该属于哪里”，并记录前置整理的实施状态。所有结论基于模块目录、Maven 依赖、包引用、Bean 角色和现有测试证据；B00、B02、B03、B04、B05 已实施，B01 和 B06 的剩余范围继续按调用证据推进。

## 目标分层

```text
spectra-launch                 组合根：显式装配必选/可选模块
├── spectra-core                必选系统核心：系统启动后不可缺少的业务能力
├── spectra-oa                  可选 OA 业务
├── spectra-workflow            可选流程业务
├── spectra-notification        可选通知业务
├── spectra-upload              可选文件业务
└── spectra-erp                 未来可选 ERP 业务

spectra-starter                 技术启动器：Security/Log 机制与自动配置
spectra-framework               技术基础设施：Web/MVC/Redis/MyBatis/加密
spectra-common                  纯 Java 公共契约：类型、端口、错误码、上下文
spectra-config                  配置资源
```

归属原则：core 拥有系统核心业务，但不拥有所有技术代码；可选模块拥有自己的领域闭环；公共层只能提供无业务实现的契约；launch 负责装配而不是业务编排。

## core 候选范围

以下能力属于“系统启动后没有就不成立”的 core 候选，后续代码整理不得误移到 optional module：

| core 子域 | 应包含 | 不应包含 |
|---|---|---|
| `core.security.authentication` | 认证身份、密码、登录 Provider 选择、Session 生命周期策略 | Spring Security 过滤器底层机制、Redis 序列化细节 |
| `core.security.authorization` | Role、Permission、RoleAssignment、Access/Grant Boundary、授权变更 | 前端菜单展示实现、具体 OA/ERP 业务权限 |
| `core.user` | User、用户生命周期、基础角色关系、用户查询端口 | OA 通讯录的业务视图、通知偏好 |
| `core.system` | Department、Region、Dict、Menu、系统配置和基础系统字典 | OA 资产/采购/合同分类 |
| `core.scheduler` | 调度定义、执行、LOOP 会话和运维管理 | 通知发送、上传清理、OA 合同提醒的业务实现；它们只能注册自己的任务 |
| `core.security.audit` | 安全审计查询/归档/指标、统一审计编排 | 邮件通知、文件存储、Flowable 审批审计的具体业务记录 |
| `core.system.health` / `core.observability` | `CoreHealthRegistry`、`CoreHealthAggregator`、系统健康聚合、服务监控、告警和管理 API | 模块底层连接检查；模块只贡献 common contributor |

## 重复能力与保留决策

| 能力 | 当前证据 | 重复状态 | 最终保留方式 |
|---|---|---|---|
| 健康检查 | `core/scheduler/health/SchedulerHealthIndicator`、`notification/health/NotificationHealthIndicator`、`upload/health/FileStorageHealthIndicator` | 3 个模块各有实现，属于“实现分散”而非三套业务 API | 保留模块专属检查实现；统一 contributor 状态模型、Actuator 适配和 core 聚合 API |
| 通知 Provider 单渠道校验 | `NotificationProviderAdminController` 的 `POST /notification/admin/providers/{channel}/health`、`NotificationProviderRuntime` | 不是系统健康聚合的重复入口，而是配置变更后的发送前置门禁和管理端即时校验 | 保留通知模块内部运维能力；结果只用于 Provider 状态、发送阻断和脱敏配置展示，不接入第二套系统健康聚合 |
| 操作日志 | common `Audit`/`AuditService`、core `AuditAspect`、`CoreAuditService`、`OperationLogOutbox*`、`OperationLogService` | 技术收集、统一编排、事务 outbox 和最终落库均在必选 core 内闭环 | 不再重复；安全与普通事件共享字段和脱敏协议，但可靠性语义不同 | `@Audit` 是唯一业务注解；普通操作事件在当前事务写 outbox，worker 按租约、重试和死信状态幂等落 `sys_log` |
| 安全审计 | `SecurityAuditWriter`/`SecurityAuditEvent` + core security audit repository/controller/outbox/archive worker | 与普通操作日志事件模型割裂，但可靠性语义不同；安全变更外部动作还需要可靠投递 | 统一事件字段和脱敏；安全事实保持同步落库、失败阻断，变更 outbox 按租约/重试/死信投递，归档必须校验后再置 `VERIFIED` |
| 调度契约 | common `common.scheduler` + core scheduler 实现 | 契约和实现边界需要冻结 | 接口/值对象留 common；执行器、持久化、管理 API、健康归 core |
| 用户/组织读取 | OA 多处直接引用 core Entity/Mapper/Service | 不是重复实现，是不稳定跨模块依赖 | core 提供稳定端口/查询模型，OA 迁移调用方 |
| 安全归档适配 | `common.port.audit` + upload 中 `SecurityAuditArchiveConfiguration` | 归档后端与文件能力耦合 | common 定义写入、读取、存在性和完整性校验端口；upload 只提供对象存储适配器，core 只持有 manifest/状态机和业务编排 |

## 迁移处理方式登记

本节把盘点对象归入五种处理方式，并保留已经完成的端口抽取和重复实现清理结论。

| 处理方式 | 适用对象 | 当前决定 | 判断依据 |
|---|---|---|---|
| 无需移动 | `spectra-core` 的 security/user/system/scheduler 核心领域；Notification、Upload、Workflow、OA 各自的领域 Entity/Mapper/Service/Controller；framework/starter 的技术机制；launch 和 config | 保持当前模块，补边界门禁 | 当前位置与目标职责一致；移动会扩大影响面而不能改善边界 |
| 直接移动 | common 中已确认依赖 Spring MVC、MyBatis、验证码、加密、文件存储或具体调度实现的类 | 按实际依赖移入 framework、starter、core 或对应可选模块 | 类的实现依赖和业务用途可以明确判断，迁移后不需要引入新业务抽象 |
| 抽取公共端口 | core→notification、OA→core 内部实现、可选模块之间的内部类引用、健康检查和安全/审计交界 | 先定义无业务实现的 Facade/Port/Contributor，再迁移调用方 | 调用方需要能力，但不应依赖提供方的 Entity、Mapper 或实现类 |
| 删除重复实现 | 旧 ULog 业务记录链路、`spectra-log-*` 模块、重复的健康聚合/协议适配、确认无调用方的旧包装器 | 先完成统一入口和等价性测试，再删除旧实现 | 删除必须有调用图、API/数据库行为对比和回滚点；安全审计不能因“去重”而降级 |
| 延期评估 | common/utils 中用途不明确的工具、core/common 零散辅助类、未来 ERP | 完成使用图、启动验证和 1.0.0 稳定后再决定 | 当前证据不足，立即移动会造成无意义的 API/包路径扰动 |

### 批次执行门槛

- B01 任何类在移动前必须有“当前调用方 → 目标模块 → 测试”记录；只凭包名判断不得执行。
- B02/B03/B06 不允许用组件扫描、静态单例、反射字符串或空实现掩盖缺少的可选模块；未装配且能力被声明为必需时必须明确失败。
- B04 只统一协议、聚合和对外响应，不把 Notification、Upload、Workflow 的专属健康逻辑复制到 core。
- B05 的“删除重复实现”仅针对普通操作日志的重复入口；SecurityAudit 的同步写入、失败阻断、安全变更 outbox 和归档完整性门禁必须保留。
- B07 在 1.0.0 稳定前不进行大范围工具包重命名、包路径清洗或 ERP 预留实现。

## 迁移登记模板

后续每次实际搬迁、抽取或删除必须补充以下记录，并在对应任务计划中引用本矩阵行：

| 字段 | 要求 |
|---|---|
| 对象 | 类、包、Bean、资源或 Maven 依赖的精确路径 |
| 当前归属 | 当前模块和职责证据 |
| 目标归属 | core/common/framework/starter/optional/launch |
| 依赖方 | 直接调用方、配置导入方、数据库或外部适配方 |
| 处理方式 | 保留、移动、抽取端口、删除重复、延期评估 |
| API/数据库影响 | 必须明确“无变化”或列出同步项；本前置任务默认无变化 |
| 测试范围 | 单元、模块集成、架构、启动、故障注入或人工验收 |
| 回滚点 | 文件/依赖/配置的可恢复边界 |

## 冻结结论

1. core 是系统必选业务核心，但不是所有技术代码的垃圾桶。
2. common 必须向纯 Java 公共契约收敛；当前 common 的技术/数据库/业务混入已登记为 B01。
3. core 不得依赖 Notification、OA、Workflow、Upload 或未来 ERP 的业务实现；当前生产依赖和架构测试均未发现 Core 指向这些业务包的直接依赖。
4. 健康检查、日志和安全审计不能按“全部搬进 core”处理：协议/编排统一，模块专属实现和可靠性边界按矩阵保留。
5. 本系统是单租户非 SaaS；任何后续设计如果引入 tenant context、租户切换或租户级隔离，均视为越界变更。
6. 重复基础能力清理后，通用 `PageFrom`、响应包装、`RedisKey` 抽象、调度契约和通用异常继续归 common；Core-only 的 `RedisCacheKey` 归 `spectra-core/common`，安全 Redis key 归 security-base，Upload 专属异常只留在 upload，在线用户会话视图只由 security-base 提供。
