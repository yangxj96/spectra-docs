# 内置角色接口与页面矩阵

> 源码盘点基准：API 契约 `1.0.0`；扫描后端全部 55 个 REST Controller、331 个 Java 方法映射；扫描 Web Router 的 84 条注册路由。API 表以 Controller 类路径和方法路径合并，调用时加 `/api`。门禁摘录自 Controller 方法/类级 `@PreAuthorize`；方法级注解优先。

## 判读规则

- `✓`：角色满足该行的 Controller 门禁。`✓*`：角色拥有对应 Permission grant，但运行时仍须通过 RoleAssignment Access Boundary、对象归属和 Service 校验。Admin/Audit 的业务 `RULES` 默认没有部门 Boundary，此类请求默认被拒绝或查询为空；给 Assignment 配置有效部门规则后才开放规则范围内数据。
- `✓ SELF`：`ROLE_USER` 的本人权限；服务端以认证主体限制资源。
- `✓ 登录†`：Controller 没有方法/类级 `@PreAuthorize`；`SecurityConfiguration` 的 Filter 默认要求认证，业务服务还可能加校验。匿名公开入口以 `permitAll()` 或 Filter 白名单为准。
- `permitAll()` 对匿名及登录用户开放，但验证码、初始化令牌、Refresh Cookie、回调签名和幂等等业务条件仍生效；`isAuthenticated()` 只表示已登录，不扩大资源范围。
- `hasRole('ROLE_DEV_OPS')` 是角色直检，不继承给 Admin/Audit；`ROLE_DEV_OPS` 对 `hasPermission` 走 Root 通配授权。Admin/Audit/User 的计算合并直授 grant 与系统自动补齐的 `ROLE_USER` grant。
- 前端页面角色由 V8 角色菜单、`meta.requiredMenu`、`meta.requiredPermissions` 和 `meta.requiredAnyPermissions` 共同决定。菜单可见不代表业务数据可读；API 表展示服务端门禁。

### 页面结论

- Admin 默认可见系统管理、OA/Workflow 与 Dashboard/Calendar 菜单；不含 Root 运维、示例和授权方案菜单。创建/编辑等子页面仍检查具体 Permission；用户列表/详情、在线用户、部门树和成员候选还按目标 Permission 的 Assignment Boundary 过滤，缺少有效部门规则时不显示越界数据。
- Audit 默认可见只读审计、元数据、OA/Workflow 与 Dashboard/Calendar；需要写权限的用户、角色、组织、授权方案表单不可进入。审计页面可见不代表可读取高风险审计记录。
- User 仅见 Dashboard、Calendar 菜单及本人资料/通知等通用入口；Calendar 新建页仍检查 `oa:calendar:create` 且只操作本人数据。
- Root 当前基线包含全部 52 个注册菜单叶子；初始化状态、Break-glass、审计及敏感值脱敏约束仍生效。

## 运行时数据范围及安全边界

| 角色 | 默认权限与 Access Boundary | 仍生效的运行时校验 |
|---|---|---|
| `ROLE_DEV_OPS` | Root 通配授权、`GLOBAL` | Root 治理、Break-glass、敏感值脱敏、Session、安全 Redis fail-closed 和审计约束 |
| `ROLE_ADMIN_SYSTEM` | 66 项直接 Permission grant，并继承 `ROLE_USER` 的 13 项；本地验收 Assignment 有 21 个 `NONE` Boundary。需要 `RULES` 的 grant 无默认部门规则 | 用户列表/详情、更新、重置密码、生命周期、在线会话、部门树、成员候选、onboarding 和导入均再次校验相应 Permission Boundary；对象外请求 fail-closed；OA/Workflow 数据依赖部门归属、组织成员关系、状态机和对象权限 |
| `ROLE_AUDIT` | 27 项直接 Permission grant，并继承 `ROLE_USER` 的 13 项；本地验收 Assignment 有 10 个 `NONE` Boundary，业务 `RULES` 默认无部门规则 | Audit page/detail/export 统一排除高风险事件（Root/Break-glass 除外）；用户、部门和业务读 API 按各自 Permission 的部门规则及用户成员范围过滤；Audit 不授予业务写入，但继承 `ROLE_USER` 的本人日历 CRUD |
| `ROLE_USER` | 自动补齐 13 项本人权限，所有个人 Boundary 为 `SELF` | 个人账户、通知设置/收件箱、日历和 Workflow Instance 按认证主体限制；修改其他 user/owner ID 不扩大范围 |

本地浏览器验收另为测试账户 `authz_admin_20260928` 配置了 D09、D10 两个部门的授权 Boundary，以验证范围交集；该临时验收 Assignment 不属于内置角色默认值。此时管理员用户列表仅返回主/关联部门在 D09、D10 范围内的用户，部门树仅返回这两个部门及其祖先，Root 用户详情和密码重置均返回 404；负向密码重置后仍可使用原凭据登录 Root。普通用户测试账户仅有 `ROLE_USER`，即使加入 D09 与 D10，仍只看到 `Dashboard`、`OACalendar`，直接访问 `/system/user` 被路由送往 401；本人日历按 `SELF` 过滤，用户列表和部门树 API 均返回 403。默认 Audit 测试账户未配置业务 `RULES`，用户/部门 API 同样 fail-closed，而审计日志分页 API 返回 200（本次数据共 3,130 条非高风险可见事件）；角色菜单数量仍为 28，菜单可见不代表 API Boundary 已具备可用数据范围。测试产生的普通用户和审计员临时日历记录均已删除并确认查询为零。

### 盘点覆盖范围

1. 后端清点包含全部 55 个 REST Controller 类，331 个映射方法；每行对应一组 HTTP method + path handler。相同路径不会重复计数，API 契约版本由 `Api-Version: 1.0.0` 请求头约束。
2. 每个 API 行链接到 Controller 方法源码并列出生效的类/方法 `@PreAuthorize`。未声明时列明 Spring Security Filter 的默认认证约束；对象可见性、数据范围、资源所有者、状态、事务、签名和幂等仍由 Service 及 Filter 校验。
3. 前端按静态 Router 注册配置列出 84 条路由，包括公开入口、通用入口和有独立 URL 的子页。菜单角色列不替代页面内 `v-permission`；按钮条件须与后端 API guard 一起看。
4. API 准入符合不等于任一业务请求必然返回成功：改密状态、用户生命周期、短时 Preview Token、版本头、验证码、回调 HMAC 等专属契约条件照常生效。
