# 接口加解密方案

> 当前实现：RSA-OAEP + AES-256-GCM 请求/响应加密、Redis nonce 防重放、运行时密钥管理和 Web 客户端接入。
>
> 基于 RSA + AES-GCM 混合加密的前后端接口数据加解密方案。

## 加密协议

```
请求加密：AES-256-GCM 随机密钥加密请求体 → RSA-OAEP 公钥加密 AES 密钥
响应加密：AES-256-GCM 随机密钥加密响应体 → RSA-OAEP 公钥加密 AES 密钥 → RSA 私钥签名
```

## 加密数据格式

```json
{
  "data": "AES-GCM 加密后的 Base64 密文",
  "key": "RSA-OAEP 加密后的 AES 密钥 (Base64)",
  "iv": "AES-GCM 初始化向量 (Hex)",
  "nonce": "随机数 (Base64)",
  "timestamp": 1234567890,
  "signature": "RSA 签名 (Base64；permitAll 匿名接口在登录前可省略)"
}
```

请求信封的 `data`、`key`、`iv`、`nonce` 和 `timestamp` 始终必需。已经完成客户端私钥获取的请求还必须携带 `signature`；显式声明为 `permitAll()` 的匿名接口允许登录前省略客户端签名，以便浏览器在尚未登录、无法获取客户端私钥时完成密码/短信/邮箱认证。匿名请求仍必须通过服务端私钥解密、时间戳窗口和安全 Redis nonce 防重放校验，其他权限接口继续强制客户端签名。

## 响应处理流程

```
Controller 返回业务数据
  → ResponseEncryptAdvice (@Order HIGHEST_PRECEDENCE)
    → AES-GCM 加密数据 → RSA 加密 AES 密钥 → RSA 签名
    → 返回 {data, key, iv, nonce, timestamp, signature} Map
  → ResponseModifyAdvice (@Order HIGHEST_PRECEDENCE + 1)
    → 包装为 R.success(加密Map)
    → 最终: {code:200, msg:"success", data: {data:"...", key:"...", ...}}
```

## 请求处理流程

```
HTTP 请求到达
  → MessageConverter 准备反序列化
  → RequestDecryptAdvice.beforeBodyRead()
    → 检查是否为加密请求（含 data + key + iv 字段）
    → permitAll 匿名接口可跳过客户端验签；其他接口执行 RSA 验签
    → RSA 私钥解密 AES 密钥 → AES-GCM 解密 data
    → 返回解密后的 body 供后续反序列化
  → Controller 收到正常的 DTO
```

## 配置

接口加解密开关仍是非敏感的 `sys_config.crypto.enabled`；RSA、通知保护和安全签名密钥统一存储在专用密钥版本表中，通过后端 API 按需获取。首次系统初始化完成时生成并发布这些内部密钥，但接口加解密默认保持关闭：

```
sys_config 表：
└── crypto.enabled              = true/false（加解密总开关）

spectra_security.sec_secret_version：
├── crypto.server.public-key
├── crypto.server.private-key
├── crypto.client.public-key
├── crypto.client.private-key
├── notification.address-encryption-key
├── notification.sensitive-payload-key
├── security.verification-code-hmac
├── security.authorization-change-token-hmac
├── security.request-integrity-hmac
└── security.csrf-signing-key
```

Web 前端不再配置加解密环境变量：启动阶段由 `GET /api/system/bootstrap` 获取系统上下文，并由 `GET /system/crypto/config` 获取当前开关和服务端公钥；RSA 密钥版本由“密钥管理”页面和首次系统初始化服务统一维护。短信、邮件等第三方 Provider 凭据不在初始化时虚构生成，仍由运维人员在密钥管理页面导入或创建版本。

## 实现组成

### 核心加密链路

- `CryptoKeyManager`：通过 `RuntimeSecretProvider` 读取当前启用的 RSA 密钥，通过 `SystemConfigValueProvider` 读取非敏感开关；数据库密文由唯一部署根密钥保护。
- `ResponseEncryptAdvice`：注入 `CryptoKeyManager`，按运行时 `isEnabled()` 判断是否加密响应。
- `RequestDecryptAdvice`：注入 `CryptoKeyManager`，按运行时 `isEnabled()` 解密请求。
- `SMProperties` 已移除，旧 yml 密钥配置已清理。

### 客户端与异常处理

- `@Encrypt` 提供细粒度加密控制。
- 前端已获取客户端私钥后由 `encryptRequest` 生成 RSA 签名，`verifySignature` 与后端算法参数保持一致；登录前的 `permitAll` 请求由 `encryptBodyWithoutSign` 生成不带签名的加密信封。
- 加密失败抛出 `EncryptException`；空请求体直接返回 `null`；`encryptRequest` 接受 `unknown` 并在内部序列化。

### 防重放与密钥管理

- `RequestDecryptAdvice` 使用 ±5 分钟时间窗口和 Redis nonce 去重，拒绝重放请求。
- Web 加密初始化仍通过 `GET /system/crypto/config` 和 `GET /system/crypto/keypair/client-private` 获取必要数据；首次系统初始化负责生成内部密钥，生成后的发布、轮换、导入、导出和退役统一通过 `ROLE_DEV_OPS` 专属的 `/security/secrets/**`。开关查询和修改使用同一前缀下的 `/settings`、`/settings/crypto`，这两个响应保持明文以支持协议切换。
- `RequestDecryptAdvice` 优先检查 `X-Encrypted` 请求头，再判断请求结构。
- 后端和 Web 已覆盖密钥运行时、版本发布、导入导出、控制器角色门禁、API 路由和页面关键交互测试；管理响应只包含脱敏元数据。

## 运行时密钥管理：统一密钥表

> 当前实现：RSA、通知保护密钥和安全签名密钥存储在 `spectra_security.sec_secret_version`，数据库只保存由唯一部署根密钥保护的 AES-GCM 密文。

### 背景

方案一存在的安全问题：
- 前端 `.env` 中硬编码 RSA 私钥，通过 `VITE_` 前缀编译进 JS bundle，DevTools 可直接获取
- 密钥轮换需改 yml + 重启服务 + 重新构建前端
- 前后端共享同一对密钥，签名无身份证明价值

统一密钥方案改进：
- 后端密钥存入专用 `spectra_security` 表，前端只按需获得 Web 加密初始化数据
- 前端不持有持久化私钥，仅在内存中缓存，刷新即失效
- 密钥轮换通过密钥管理页面创建、审核、发布并刷新运行态，无需重启；部署根密钥变更必须重新部署

### 密钥编码

| code | 用途 | API 暴露 |
|---|---|---|---|
| `crypto.enabled` | 加解密总开关 | `GET /system/crypto/config` |
| `crypto.server.public-key` | 服务端公钥（前端加密请求） | `GET /system/crypto/config` |
| `crypto.server.private-key` | 服务端私钥（后端解密请求） | 不暴露 |
| `crypto.client.public-key` | 客户端公钥（后端加密响应） | 不暴露 |
| `crypto.client.private-key` | 客户端私钥（前端解密响应） | `GET /system/crypto/keypair/client-private` |

### 架构对比

| 方面 | 旧配置入口 | 统一密钥管理 |
|---|---|---|
| 私钥存储 | 前端 JS bundle 明文 | 仅浏览器内存 |
| 密钥轮换 | 改部署配置并重启 | 页面创建/审核/发布版本后刷新运行态 |
| 加密开关 | yml 中 `spectra.system.sm.enabled` | `sys_config.crypto.enabled` |
| 服务端私钥 | yml 明文 | `sec_secret_version` 根密钥保护密文 |
| 性能 | 启动时一次性解析 | 启动加载到内存，请求时零开销 |

### CryptoKeyManager 设计

**位置**：`spectra-framework/web/crypto/CryptoKeyManager.java`

**核心设计**：framework 依赖 `RuntimeSecretProvider` 读取统一密钥端口，使用不可变运行时值；唯一数据库根密钥只从部署环境注入，根密钥变化必须重新部署。

```
CryptoKeyManager
├── @PostConstruct init() → 从统一密钥运行时读取密钥到内存
├── isEnabled() → 检查 crypto.enabled + 密钥完整性
├── getServerPublicKey() → 返回内存缓存的 PublicKey
├── getServerPrivateKey() → 返回内存缓存的 PrivateKey
├── getClientPublicKey() → 返回内存缓存的 PublicKey
├── getClientPrivateKey() → 返回内存缓存的 PrivateKey
├── getServerPublicKeyBase64() → 返回 Base64 字符串
├── getClientPrivateKeyBase64() → 返回 Base64 字符串
└── refresh() → 重新读取支持热加载的当前版本
```

**线程安全方案**：

```java
private record CryptoKeys(
    PublicKey serverPub, PrivateKey serverPri,
    PublicKey clientPub, PrivateKey clientPri
) {}
private volatile CryptoKeys keys;  // 原子替换，无部分更新窗口
```

**降级策略**：
- 统一密钥缺失、根密钥无效或数据库不可用 → 密钥相关能力返回不可用并 fail-closed
- `crypto.enabled=false` 时不启用接口加解密；不会因为密钥读取失败静默切换为明文

### 密钥数据流

```
启动时：
  sec_secret_version (DB) → RuntimeSecretProvider → CryptoKeyManager.init() → 内存缓存

请求时：
  ResponseEncryptAdvice → cryptoKeyManager.getClientPublicKey() → 内存（微秒级）
  RequestDecryptAdvice → cryptoKeyManager.getServerPrivateKey() → 内存（微秒级）

密钥轮换：
管理员在密钥管理页面发布 → SecretManagementController → cryptoKeyManager.refresh()
    → 从统一密钥运行时重载 → 原子替换
```

### CryptoController API 变更

| 端点 | 方法 | 认证 | 说明 |
|---|---|---|---|
| `GET /system/crypto/config` | 新增 | 无 | 返回 `{enabled, serverPublicKey}`，前端初始化调用 |
| `GET /system/crypto/keypair/server-public` | 保留 | 无 | 返回服务端公钥 |
| `GET /system/crypto/keypair/client-private` | 新增 | 需登录 | 返回客户端私钥；临时密码会话也允许调用，用于完成首次密码修改时的加密通信 |
| `GET /security/secrets/settings` | 新增 | `ROLE_DEV_OPS` | 查询接口加解密开关、密钥就绪状态和运行态；响应保持明文 |
| `POST /security/secrets/settings/crypto` | 新增 | `ROLE_DEV_OPS` | 修改接口加解密开关；启用前校验四个 RSA 密钥，响应保持明文 |
| `POST /security/secrets/{code}/versions` | 新增 | `ROLE_DEV_OPS` | 创建待启用版本；密钥值只写入专用密文表 |
| `POST /security/secrets/{code}/versions/{versionId}/publish` | 新增 | `ROLE_DEV_OPS` | 显式发布并退役旧版本 |
| `POST /security/secrets/export`、`/import` | 新增 | `ROLE_DEV_OPS` | 使用一次性口令加密导出/导入；导入始终待启用 |
| `POST /security/secrets/refresh` | 新增 | `ROLE_DEV_OPS` | 刷新支持热加载的运行态 |

### 前端初始化时序

```
应用启动
  → GET /system/crypto/config → { enabled: true, serverPublicKey: "..." }
    → enabled=false → 全局跳过加解密
    → enabled=true → 缓存 serverPublicKey → 后续请求加密可用

用户登录
  → POST /security/authentication/login  (@Encrypt(false)，明文响应)
  → GET /system/crypto/keypair/client-private (带 Token)
    → 缓存 clientPrivateKey → 后续响应解密可用
```

首次系统初始化完成时会先生成并发布 10 个内部密钥，并将 `crypto.enabled` 写为 `false`；DEV_OPS 登录后在“密钥管理”页面确认运行态，再通过接口加解密开关启用通信保护。

临时密码登录时，Token 会被限制在密码修改流程内，但仍允许获取客户端私钥、读取个人信息和加载必要的页面上下文；完成密码修改后旧会话会被撤销。客户端私钥接口只要求已登录，不要求 `security:crypto:manage`，因为它是所有启用接口加密的 Web 客户端都必须完成的通信初始化步骤，不属于密钥生成或刷新管理操作。

### 实现核对清单

| 能力 | 当前实现 |
|---|---|
| 根密钥 | `SPECTRA_SECURITY_SECRET_MASTER_KEY`，仅部署环境注入，Base64 解码后为 32 字节 |
| 数据保护 | `SecretValueCipher` 使用 AES-256-GCM，密钥编码作为 AAD，数据库只保存 nonce 和密文 |
| 运行时加载 | `RuntimeSecretProvider` 读取当前 ACTIVE 版本；`CryptoKeyManager` 在初始化和显式刷新时原子替换内存快照 |
| Web 初始化 | `CryptoController` 仅保留 config 和 client-private 两个通信初始化接口，不提供生成、轮换管理入口 |
| 管理页面 | `secret-management-api.ts` 和“密钥管理”页面提供三分类版本管理、发布、退役、导入导出和运行态刷新 |
| 迁移 | `ApplicationSecretMigrationCommand`、`BusinessSecretMigrationCommand`、`SecuritySecretMigrationCommand` 只允许显式调用，运行时不自动读取旧入口 |

### 风险分析

| 风险等级 | 问题 | 处理方式 |
|---|---|---|
| 高 | 循环依赖（Framework 不能直接依赖 Core） | Framework 只依赖 `spectra-common` 的 `RuntimeSecretProvider` 端口 |
| 高 | 启动时数据库或密钥版本不可用 | 加解密状态为 `UNAVAILABLE`，请求链路保持 fail-closed，不静默返回明文 |
| 中 | 线程安全（refresh 期间部分更新） | 不可变 wrapper + volatile 原子替换 |
| 中 | `enabled=true` 但密钥缺失 | `isEnabled()` 附加密钥完整性检查 |
| 低 | 密钥变更竞态（请求加密用旧 key，后端解密用新 key） | v1 接受，不做处理 |
| 低 | 前端登录前 POST 响应加密 | 登录前端点已豁免，不受影响 |

### 实现核对清单

#### 核心运行时改动

- `CryptoKeyManager` 通过 `RuntimeSecretProvider` 读取统一密钥版本，使用不可变快照和原子替换，不直接依赖 `sys_config` 或旧环境密钥。
- `ResponseEncryptAdvice`、`RequestDecryptAdvice` 共用管理器的 `DISABLED`、`READY`、`UNAVAILABLE` 状态。
- `CryptoController` 不再提供生成或刷新密钥管理端点；生成、发布和刷新归“密钥管理”专属 API。

#### API 与客户端改动

- Web 端通过 `crypto-api.ts` 获取通信初始化数据，通过 `secret-management-api.ts` 管理版本和传输包。
- 管理页面只展示定义、状态、版本、摘要和时间，不回显明文；导入后统一显示待启用状态。
- `ROLE_DEV_OPS` 是密钥管理页面和接口的唯一授权角色；通信初始化接口按其自身的公共/登录约束运行。

#### 配置与验证

- 已删除迁移后的 RSA、通知保护和安全 HMAC 环境绑定；保留的根密钥模板不包含实际值。
- 覆盖运行时、服务版本、导入导出、控制器门禁、API 路径和页面交互的专项测试，并执行前端类型检查和 lint。
