# 后端模块边界

`spectra-admin` 是运行在单个 Spring Boot 进程中的多模块后端。`spectra-launch` 负责启动和模块装配，`spectra-core` 提供系统核心能力，`spectra-workflow` 和 `spectra-oa` 提供可选业务能力，`spectra-framework` 提供技术基础设施，`spectra-common` 提供跨模块契约，`spectra-config` 提供配置资源。

系统当前采用单租户模型，不提供应用级租户上下文、租户切换、租户数据源或租户 API 参数。Flowable 表中的 `tenant_id_` 等字段属于引擎数据结构，不代表 Spectra 的租户能力。

## 模块结构

```text
spectra-admin
├── spectra-config
├── spectra-common
├── spectra-framework
├── spectra-launch
└── spectra-modules
    ├── spectra-core
    ├── spectra-workflow
    └── spectra-oa
```

Maven 根项目聚合 `spectra-config`、`spectra-common`、`spectra-framework`、`spectra-launch` 和 `spectra-modules`。`spectra-modules` 再聚合 `spectra-core`、`spectra-workflow` 和 `spectra-oa`。

## 模块职责

### spectra-config

路径：`spectra-admin/spectra-config/`

该模块只包含运行配置资源和数据库迁移资源，不包含 Java 业务代码。`application-dev.yml` 和 `application-prod.yml` 位于 `src/main/resources`，Flyway 迁移位于同一资源模块的数据库迁移目录。配置资源通过 `spectra-launch` 的 classpath 加载。

### spectra-common

路径：`spectra-admin/spectra-common/`，包根：`com.devops00.spectra.common`

该模块提供不依赖业务实现的公共类型和跨模块契约，主要包括：

- `common.port`：文件、安全、审计、Quartz 等跨模块端口。
- `common.security`：认证上下文、授权快照、安全策略和密码策略契约。
- `common.health`：依赖健康贡献者、健康结果和健康快照协议。
- `common.audit`：审计注解、审计事件和脱敏契约。
- `common.event`：上传完成等跨模块事件数据。
- `common.foundation`：只依赖 JDK 的集合、字符串、树和基础对象能力。
- 通用 DTO、VO、异常、常量和 API 注解。

生产代码不在 `spectra-common` 中实现 Spring Web、MyBatis、PostgreSQL、Redis 或具体业务存储适配。公共契约可以被业务模块和技术基础设施依赖，但不引用 `spectra-core`、`spectra-workflow` 或 `spectra-oa` 的实现类。

### spectra-framework

路径：`spectra-admin/spectra-framework/`，包根：`com.devops00.spectra.framework`

该模块承载平台级技术能力：

- `framework.web`：MVC、统一响应、异常处理、请求关联、请求参数和加解密适配。
- `framework.security`：Spring Security、Token、Session、安全 Redis、登录失败限制、限流和授权技术适配。
- `framework.serialization`：Jackson、MapStruct 和时间类型转换。
- `framework.captcha`：验证码配置、类型、生成器和验证码 Web 适配。
- `framework.cache`：通用缓存和 Redis 配置。
- `framework.persistence`：MyBatis-Plus、持久化基类、分页、数据库类型处理器和数据权限拦截器。
- `framework.properties`：`spectra.system` 配置绑定。
- `framework.health`：数据源、Redis 和 Actuator 健康适配。

`FrameworkModule` 是 framework 的装配入口，通过组件扫描发现自身技术组件。该模块依赖 `spectra-common`，不依赖业务模块，不持有业务 Entity、Mapper 或 Service。

### spectra-core

路径：`spectra-admin/spectra-modules/spectra-core/`，包根：`com.devops00.spectra.core`

`spectra-core` 是系统核心业务模块，负责：

- 用户、认证、角色、权限、组织和授权治理。
- 系统配置、菜单、字典、区域、服务监控和系统初始化。
- Quartz 调度管理、Job/Trigger 管理和执行历史。
- 统一审计、操作日志和安全审计归档编排。
- 统一通知的模板、请求、任务、投递、渠道健康和清理。
- 文件上传、文件资产、文件引用、分片任务和存储后端编排。
- Core 内部的健康注册、健康聚合和运行状态汇总。

Core 可以依赖 `spectra-common` 和 `spectra-framework`，不依赖 OA 或 Workflow 的业务实现。Core 对外提供的跨模块能力通过 `common.port` 或明确的公共服务契约表达。

### spectra-workflow

路径：`spectra-admin/spectra-modules/spectra-workflow/`，包根：`com.devops00.spectra.workflow`

该模块负责 Flowable 流程定义、流程部署、流程实例、任务、审批回调和工作流健康检查。Flowable 的引擎适配、Mapper、Service 和 Controller 保持在本模块内；OA 通过工作流端口使用流程能力，不引用 Workflow 内部持久化实现。

### spectra-oa

路径：`spectra-admin/spectra-modules/spectra-oa/`，包根：`com.devops00.spectra.oa`

该模块负责办公自动化业务，包括申请、请假、协同、报销、采购、资产、考勤、日历、通讯录、合同、文档、会议、公告和报表。OA 依赖 Core 提供的用户、组织、文件、通知和公共系统能力；文件引用和工作流交互通过明确端口完成。

### spectra-launch

路径：`spectra-admin/spectra-launch/`，包根：`com.devops00.spectra.launch`

该模块是 Spring Boot 组合根，包含启动类、模块装配和启动校验。它直接加载 `spectra-config`，装配 Core，并按 `spectra.modules.workflow.enabled` 和 `spectra.modules.oa.enabled` 装配可选业务模块。

`spectra-launch` 不包含 Controller、Entity、Mapper、Repository 或业务 Service，不承载业务规则，也不通过隐藏扫描发现业务模块。

## 依赖方向

```text
spectra-launch
    ├── spectra-modules
    │   ├── spectra-core
    │   ├── spectra-workflow
    │   └── spectra-oa
    └── spectra-config

spectra-core / spectra-workflow / spectra-oa
    ├── spectra-framework
    └── spectra-common

spectra-framework
    └── spectra-common
```

依赖边界如下：

- `spectra-common` 不依赖任何业务模块。
- `spectra-framework` 不依赖 Core、OA 或 Workflow。
- Core 不依赖 OA 或 Workflow 的内部实现。
- OA 和 Workflow 不依赖 `spectra-launch`。
- `spectra-launch` 只负责组合和启动，不向下层提供业务实现。
- 跨模块调用使用公共端口、Facade 或事件，不直接引用其他模块的内部 Entity、Mapper 和实现类。

## 包边界

### 公共契约和技术实现

公共契约位于 `spectra-common`，包括文件、审计、安全、健康和 Quartz 的跨模块接口及值对象。Spring Web、Spring Security、Redis、MyBatis-Plus、数据库处理器、验证码生成器和 Actuator 适配位于 `spectra-framework`。

### Core 业务域

Core 的一级业务包包括 `security`、`user`、`system`、`scheduler`、`audit`、`notification`、`upload` 和 `common`。其中 `common` 只放 Core 内部需要的业务协调代码；技术基础设施仍由 framework 提供。

### 可选业务域

Workflow 的流程引擎实现位于 `spectra-workflow`，OA 的各业务域位于 `spectra-oa`。可选模块的装配开关只控制对应业务模块，不改变 Core 的必选核心能力。

## 自动配置和健康检查

- Framework 通过自身装配入口注册 Web、安全、缓存、持久化、序列化、验证码和健康技术组件。
- Core 通过 Core 自动配置入口扫描 Core 业务包并注册系统、通知、上传、调度和健康组件。
- Workflow 和 OA 通过各自模块入口装配，模块开关由 `spectra.modules.*.enabled` 控制。
- Core 健康聚合由 `CoreHealthRegistry` 和 `CoreHealthAggregator` 负责。
- 当前健康贡献者包括 framework 的数据源和 Redis 贡献者、Core 的 `NotificationHealthIndicator`、`QuartzSchedulerHealthIndicator`、`FileStorageHealthIndicator`，以及 Workflow 的 `FlowableHealthContributor`。
- `ActuatorHealthContributorAdapter` 将统一健康协议接入 Actuator；Core 的服务监控读取统一健康快照，不把外部依赖故障转换成可用状态。

## 配置和数据边界

启动配置位于 `spectra-config`，`spectra.*` 属性由 framework 或具体业务模块绑定。系统运行时业务配置保存在 `spectra_core.sys_config`，不与 YAML 绑定对象混用。安全 Redis、数据库、S3 和 Flowable 的存储边界由各自模块实现和健康贡献者负责。

## 验证入口

模块包边界、依赖方向、禁止的反向依赖和健康组件由 `scripts/check-module-boundaries.sh` 检查。Java 编译、测试、格式和静态分析使用 `spectra-admin/mvnw` 以及项目的 mise 环境；具体命令见 [[../../开发指南/01-常见命令]]。
