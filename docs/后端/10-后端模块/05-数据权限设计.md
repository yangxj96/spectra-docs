# 数据权限设计

> Permission-aware 数据权限过滤框架，基于 MyBatis-Plus DataPermissionInterceptor 自动注入 WHERE 条件。
> 当前实现从 `AuthorizationSnapshot` 读取同一 Permission 的 Access Boundary；缺失 Permission、Boundary、资源策略或当前用户时 fail-closed，手动绕过必须经过受控执行器。
>
> 模块：`spectra-common` + `spectra-framework` + `spectra-core`

## Permission Scope 模式

`AuthorizationSnapshot` 为每个 Permission 独立提供 `NONE`、`ALL`、`SELF`、`RULES` Boundary。运行时不包含
`DataScopeType` 枚举、用户/角色 Scope 表和 DTO；`@DataScope` 只负责声明资源的读、写、导出
Permission 及归属字段，运行时范围事实来自目标授权表。`NONE` 拒绝全部数据，`ALL` 不增加数据范围限制。

内置角色的默认授权通过 V8 收口；升级已有环境时，迁移按角色有效 Permission 与目录允许的 Scope 模式核对活动 Assignment Boundary。缺少 `RULES` 部门规则不能自动补成全部门、`ALL` 或 Grant Boundary；被撤销或目录不再支持的 Permission Boundary 必须撤销。导入仍使用旧 Scope 模型的业务库时，依据 [[../../部署运维/08-安全迁移盘点手册]] 逐条人工映射，不进行隐式范围扩大。

## 四个内置角色的默认数据范围

| 角色 | Role Permission 默认范围 | 用户 RoleAssignment 初始 Access Boundary | 实际效果 |
|---|---|---|---|
| `ROLE_DEV_OPS` | Root 隐式 `*`；权限集不以 RolePermission 关系为事实来源 | Root 受 RootAuthorizationPolicy 管理，使用 `GLOBAL` | 全系统范围仍经过 Root 名额、最后 Root、Break-glass、审计、字段脱敏和受控绕过校验 |
| `ROLE_ADMIN_SYSTEM` | 系统目录 Permission 只使用 Catalog 允许的 `NONE`；用户、组织、OA 和 Workflow Permission 使用 `RULES` | V8 只建立合法 `NONE` 边界；不建立部门 RULES | 目录类授权可以使用；业务读写在管理员 Assignment 显式加入有效部门规则前为零范围/拒绝；不得把 `NONE` 或缺失规则解释成 `ALL` |
| `ROLE_AUDIT` | 审计、元数据 Permission 使用 Catalog 允许的 `NONE` / 审计专用查询策略；跨模块业务只读 Permission 使用 `RULES` | V8 只建立合法 `NONE` 边界；不建立部门 RULES | 审计策略可读取非高风险审计事件；业务记录在配置部门规则前为空；高风险安全审计事件仍只给 Root / Break-glass。审计角色继承 `ROLE_USER` 的本人日历 CRUD，除此之外不授予业务写入 |
| `ROLE_USER` | 每个基础 Permission 仅允许 `SELF` | 创建、编辑和导入账号时，自动为 13 个基础 Permission 分别生成 `SELF` | 所有个人资料、消息、日历和本人发起流程均以当前主体过滤，不能读取或改写他人资源 |

`ROLE_ADMIN_SYSTEM` 和 `ROLE_AUDIT` 的角色 Permission 是能力上限，不是用户范围。只有 `allowed_scope_modes` 接受该模式、Grant Boundary 允许被授予且 Preview/Apply 成功时，RoleAssignment 才能增加 `RULES` 范围。`RULES` 范围还要与用户的主部门/关联部门成员集求交；配置部门但用户不属于相应部门时仍不可访问。多角色用户按同一 Permission 的活动 Assignment 规则合并，绝不跨 Permission 合并 Scope。

本次开发数据库的浏览器验收用户在未配置 RULES 时，Admin 仅获得 21 个有效 `NONE` 直接 Permission（另加 13 个 `ROLE_USER` 权限），Audit 仅获得 10 个有效 `NONE` / 审计直接 Permission（另加 13 个 `ROLE_USER` 权限）。这些数量用于说明 fail-closed 的实际效果，不是固定角色授予总数；用户配置 RULES 后会因边界变化而改变。菜单仍按角色的菜单关系生成，因此可见页面与可访问数据是两层判断：例如 Audit 的用户/部门菜单可以显示，但缺少对应部门 Boundary 时用户页 API 返回 403、部门树 API 返回 403；不可依赖隐藏菜单代替后端授权。

## 设计规则

| 规则 | 说明 |
|---|---|
| Permission-specific | 每个 Permission 独立读取自己的 Access Boundary；不同 Permission 的 Scope 禁止先 UNION 后重组 |
| Assignment-preserving | 多个 Assignment 只在同一 Permission 内 OR 合并，Grant Boundary 不得替代 Access Boundary |
| GLOBAL 仅超管赋予 | `ALL` 只能由统一 Root/授权治理链路赋予，普通管理员默认无 `ALL` |
| SYS_ 表不自动拦截 | SYS_ 前缀表不由 `@DataScope` 自动注入条件；这不代表 API 可以越过 Access Boundary。用户分页/详情/在线会话、部门树/成员候选、用户 onboarding 与批量导入在 Core 服务中按对应 Permission 手动校验数据范围 |
| 无 `@DataScope` 不自动拦截 | Entity 上无 `@DataScope` 注解的表不注入 WHERE；相关 API 必须在 Service 明确执行 Permission 和对象范围检查，或只开放给有效 `ALL`/Root Boundary |
| fail-closed | 已标注实体但无法取得当前用户、Permission、Boundary 或有效范围时拒绝执行；空 Boundary/空部门生成恒假条件 |
| 写读分离 | `readPermission`、`writePermission`、`exportPermission` 必须显式登记；写入和导出不得借用查询权限 |
| IDOR/批量/导出 | 详情、更新、删除、批量和导出调用 `ResourceAuthorizationGuard`，ScopeQuery 必须由服务端从资源事实构造 |
| 手动扩展 | 仅允许 `ROLE_DEV_OPS` 或显式通配权限通过 `DataScopeExecutor.withoutScope(...)` 在单个 lambda 作用域内绕过；业务请求不得默认使用 |
| 写入归属 | `MetaObjectHandlerImpl` 对声明 `departmentId` 的实体自动填充当前用户部门；会议服务同时强制发起人和部门归属 |

### 用户部门成员范围

每个 Permission 的 `RULES` 部门集合与当前用户的部门成员集合求交。成员集合包含 `sys_user.primary_department_id` 和有效的 `sys_user_department_membership` 关联部门。启用包含下级时，授权部门和成员部门分别通过 `sys_department_closure` 扩展，再按部门集合求交。同一 Permission 的多个 Assignment 逐个使用该成员集合计算，结果按既有 Assignment 规则合并；不同 Permission 的范围不合并。

SQL 数据范围过滤与资源级授权检查使用相同的用户部门成员集合和判断规则。成员集合为空时，`RULES` 的部门结构分支不允许访问部门数据；部门成员查询无法确认时按 fail-closed 处理。`ALL` 和 `SELF` 保持原语义；`@DataScope.Relation` 声明的用户关系维度继续按原规则判断，部门成员集合只约束结构部门分支。

Core 的 `sys_user`、`sys_department` 不属于自动 `@DataScope` 实体，因此对应 Service 必须使用当前 `AuthorizationSnapshot` 再次执行对象级范围约束：用户列表按 `user:read` 的 `SELF` 或授权部门过滤主部门及有效关联部门；用户详情、更新、重置密码、生命周期变更按各自 Permission 检查目标用户；在线会话按 `session:read` 过滤目标用户；部门树按 `department:read` 过滤节点并仅保留呈现授权节点所需的祖先；部门成员候选同时校验 `department:read` 和 `user:read`。用户创建、部门变更及批量导入还必须保证目标主/关联部门在各自 `user:create` / `user:update` Boundary 内。缺少当前主体或快照时均不得放行。

### 部门合并与部分拆分

部门合并将活动 RoleAssignment 的访问和授权 `RULES` 部门引用映射到新部门，并将未删除授权方案中的对应部门编码映射到新部门。已停用方案仍会更新；已撤销 Assignment 和已删除方案保持不变。映射产生重复部门规则时按现有约束去重。预览分别汇总访问范围和授权范围的影响，并标示有效范围变化或扩大。

部分拆分不修改 RoleAssignment 边界或授权方案模板，只调整所选成员的主/关联部门关系。`RULES` 范围据此按用户成员部门集合和授权部门集合重新计算，`ALL` 与 `SELF` 的语义不变。

## 二维过滤模型

```
结构维度（部门归属）                   关系维度（多对多关联）
─────────────────                   ─────────────────
SELECT * FROM oa_meeting            SELECT * FROM oa_meeting
WHERE (                              WHERE (
    department_id IN (dept_ids)         ...
    OR created_by = current_user        OR id IN (
)                                           SELECT meeting_id FROM oa_meeting_participant
    ┌─ DEPT → 本部门                        WHERE user_id = ?
    ├─ DEPT_AND_CHILDREN → 本+子部门      )
    ├─ SELF → created_by              )
    └─ CUSTOM → 指定目标
```

## `@DataScope` 注解

```java
@Documented
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
public @interface DataScope {

    String readPermission() default "";
    String writePermission() default "";
    String exportPermission() default "";

    /**
     * 结构维度过滤字段名，默认 department_id
     */
    String column() default "department_id";

    /**
     * SELF 范围的归属字段，默认 created_by；明细表可指定 user_id
     */
    String ownerColumn() default "created_by";

    /**
     * 是否忽略（SYS_ 表等）
     */
    boolean ignore() default false;

    /**
     * 关系维度——关联表
     */
    Relation[] relations() default {};

    @interface Relation {
        String schema() default "";           // 关联表 schema
        String table();                    // 关联表名
        String joinColumn();              // 关联表的外键字段
        String userColumn() default "user_id"; // 关联表的用户ID字段
        String mainColumn() default "id"; // 主表用于 IN 匹配的列
        String departmentColumn() default ""; // 关联表的部门归属列
    }
}
```

### 使用示例

```java
// 仅结构维度
@DataScope(readPermission = "oa:asset:read", writePermission = "oa:asset:update")
public class Asset extends BaseEntity { }

// 部门范围使用 department_id，本人范围使用 user_id
@DataScope(readPermission = "oa:meeting:read", writePermission = "oa:meeting:update",
        column = "department_id", ownerColumn = "user_id")
public class MeetingParticipant extends BaseEntity { }

// 结构 + 参会人关系
@DataScope(readPermission = "oa:meeting:read", writePermission = "oa:meeting:update", relations = {
    @DataScope.Relation(
        schema = "spectra_oa",
        table = "oa_meeting_participant",
        joinColumn = "meeting_id",
        userColumn = "user_id"
    )
})
public class Meeting extends BaseEntity { }

// 跨表关联（会议纪要通过 meeting_id 而非 id 匹配）
@DataScope(column = "department_id", relations = {
    @DataScope.Relation(
        table = "oa_meeting_participant",
        joinColumn = "meeting_id",
        userColumn = "user_id",
        mainColumn = "meeting_id"
    )
})
public class MeetingRecord extends BaseEntity { }
```

| Entity | 表名 | 结构维度 | 关系维度 |
|---|---|---|---|

| Application | `oa_application` | `oa:application:read/update`；`department_id` | 无 |
| Calendar | `oa_calendar` | `oa:calendar:read/update`；`owner_id`/`department_id` | 无 |
| Contract | `oa_contract` | `oa:contract:read/update`；`department_id`/`owner_id` | 无 |
| Document/Folder | `oa_document*` | `oa:document:read/update`；部门/所有者 | Folder 通过文档 Permission |
| Notice | `oa_notice` | `oa:notice:read/update`；`department_id` | 无 |
| Meeting/Participant/Record | `oa_meeting*` | `oa:meeting:read/update`；`department_id` | participant.user_id；Record meeting_id |
| Leave/Attendance | `oa_leave_*` | `oa:leave:read/update`；部门/用户 | 无 |
| Purchase/Receipt/Supply | `oa_purchase*`/`oa_supply_item` | `oa:purchase:read/update`；部门 | Receipt 明细通过父表部门关联 |
| Reimbursement/Item | `oa_reimbursement*` | `oa:reimbursement:read/update`；`department_id` | 无 |

组织通讯录复用 Core 用户/部门数据范围，部门统计复用各来源业务实体的数据范围；两者不再维护独立 OA 实体。

## 核心流程

```
请求开始
  │
  └→ DataScopeContextFilter 建立 ThreadLocal 请求上下文
       └→ 首条受保护 SQL 通过 AuthorizationSnapshotProvider.load(userId)
            └→ JdbcAuthorizationSnapshotLoader 读取 Assignment/Permission/Access Boundary
                 └→ 同一请求复用授权上下文，结束时清理

请求任意 SQL
  │
  └→ DataScopeInnerInterceptor.getSqlSegment()
       ├─ 受控 bypass → return null（仅系统运维 lambda）
       ├─ ALL Boundary → return null（该 Permission 不需要结构过滤）
       ├─ NONE Boundary → 恒假条件（拒绝该 Permission 的全部数据）
       ├─ 缺少用户/Permission/Boundary → 恒假或抛 DataScopeViolationException
       ├─ 无 @DataScope → return null
       └─ ScopeSqlPolicy 生成 WHERE：
            ├─ RULES：column IN (department_ids)，下级部门使用 sys_department_closure
            ├─ SELF：ownerColumn = subjectId
            ├─ 关系维度：mainColumn IN (SELECT joinColumn ...)
            └─ 同一 Permission 的多个 Boundary OR 连接
```
