# Spectra 后端 spectra 配置说明

本文说明后端配置文件中的 `spectra:` 配置树。这里的配置属于后端应用启动配置或运行时绑定配置，不等同于数据库中的 `spectra_core.sys_config`，也不等同于前端的 `VITE_*` 配置。

配置值的基本规则：

- `${NAME:default}` 表示优先读取环境变量 `NAME`；环境变量没有值时使用 `default`。
- `${NAME}` 没有默认值，通常表示该配置在对应功能装配或启动时必须由环境注入。
- 空默认值不是可用密钥。尤其是 `SPECTRA_SECURITY_SECRET_MASTER_KEY`，未配置时密钥保护相关能力必须保持不可用。
- 本页只展示变量名和安全占位符，不记录密码、Token、私钥、证书或本机配置值。
- 本页的 YAML 配置通常在应用启动时绑定；修改后是否需要重启，以对应配置类和运行时能力为准。数据库中的运行时系统配置另有说明。

## 完整配置结构

下面是当前配置树的脱敏版。环境变量占位符和固定契约保持原样，示例不包含真实凭据。

~~~yaml
spectra:
  security:
    secret:
      master-key: ${SPECTRA_SECURITY_SECRET_MASTER_KEY:}
    verification-code-max-attempts: ${SECURITY_VERIFICATION_CODE_MAX_ATTEMPTS:5}
    # 默认开发服务使用 HTTPS，因此刷新 Cookie 默认启用 Secure 并使用 __Host- Cookie。
    refresh-cookie-name: ${SPECTRA_SECURITY_REFRESH_COOKIE_NAME:__Host-spectra-refresh}
    refresh-cookie-secure: ${SPECTRA_SECURITY_REFRESH_COOKIE_SECURE:true}
    allow-insecure-refresh-cookie: ${SPECTRA_SECURITY_ALLOW_INSECURE_REFRESH_COOKIE:false}
    refresh-cookie-same-site: ${SPECTRA_SECURITY_REFRESH_COOKIE_SAME_SITE:Strict}
    refresh-cookie-same-site-none-allowed: ${SPECTRA_SECURITY_REFRESH_COOKIE_SAME_SITE_NONE_ALLOWED:false}
    refresh-cookie-path: ${SPECTRA_SECURITY_REFRESH_COOKIE_PATH:/}
    refresh-cookie-domain: ${SPECTRA_SECURITY_REFRESH_COOKIE_DOMAIN:}
    csrf-cookie-name: ${SPECTRA_SECURITY_CSRF_COOKIE_NAME:XSRF-TOKEN}
    csrf-header-name: ${SPECTRA_SECURITY_CSRF_HEADER_NAME:X-XSRF-TOKEN}
    crypto-request-max-body-bytes: ${SPECTRA_SECURITY_CRYPTO_REQUEST_MAX_BODY_BYTES:1048576}
    crypto-replay-window-seconds: ${SPECTRA_SECURITY_CRYPTO_REPLAY_WINDOW_SECONDS:300}
    redis:
      namespace: "sec:"
      fail-closed: true
      worker-batch-size: ${SPECTRA_SECURITY_REDIS_WORKER_BATCH_SIZE:100}
    audit-archive-backend: ${SPECTRA_SECURITY_AUDIT_ARCHIVE_BACKEND:PENDING}
  system:
    base-dir: files
    cors:
      required: ${SPECTRA_CORS_REQUIRED:false}
      origin-patterns: ${SPECTRA_CORS_ORIGIN_ALLOWLIST:https://localhost:5173,https://127.0.0.1:5173,https://localhost:5174,https://127.0.0.1:5174}
  kaptcha:
    type: math
    verify: false
  file:
    upload:
      local:
        storage-root: ${spectra.system.base-dir}/uploads
        staging-root: ${spectra.system.base-dir}/temp
      s3:
        endpoint: ${S3_ENDPOINT}
        accessKey: ${S3_ACCESS_KEY}
        secretKey: ${S3_SECRET_KEY}
        bucket: ${S3_BUCKET}
        archive-bucket: ${S3_SECURITY_AUDIT_ARCHIVE_BUCKET:}
        archive-prefix: ${S3_SECURITY_AUDIT_ARCHIVE_PREFIX:security-audit/}
        region: ${S3_REGION}
      default-storage: s3
      chunk-size: 8388608
      min-chunk-size: 5242880
      max-chunk-size: 67108864
      max-parts: 10000
      parallelism: 3
      task-ttl: 24h
      idle-timeout: 2h
      record-retention: 7d
      orphan-retention: 7d
      presign-ttl: 15m
  notification:
    enabled: true
    allowed-link-prefixes: /login,/security/authentication/,/oa/,/workflow/,/notification/,/notification-center/,/system/,/file/
    worker:
      fixed-delay-ms: 5000
      processing-timeout-seconds: 300
      retry-base-delay-seconds: 5
    cleanup:
      enabled: true
      fixed-delay-ms: 3600000
      batch-size: 100
      retention-seconds: 86400
  scheduler:
    quartz:
      enabled: true
      table-prefix: spectra_quartz.QRTZ_
      clustered: true
      jdbc-store: true
      job-store-class: org.springframework.scheduling.quartz.LocalDataSourceJobStore
      thread-count: 10
      history-retention-days: 90
      history-cleanup-batch-size: 500
      history-running-timeout: 24h
      database-retry-interval: 10s
~~~

## spectra.security

### 密钥、验证码和 Cookie

| 配置路径 | 类型 | 默认值/环境变量 | 作用 | 生效时机 | 约束和失败行为 |
|---|---|---|---|---|---|
| `spectra.security.secret.master-key` | Base64 字符串 | `SPECTRA_SECURITY_SECRET_MASTER_KEY`，默认空 | 保护数据库中安全密钥版本的根密钥 | 启动/密钥访问 | Base64 解码后必须正好 32 字节；空值或非法值不能用于密钥读写，相关能力必须 fail-closed |
| `spectra.security.verification-code-max-attempts` | 整数 | `SECURITY_VERIFICATION_CODE_MAX_ATTEMPTS`，默认 `5` | 限制同一验证码窗口内的最大校验次数 | 启动时校验 | 必须为正数；超过次数后验证码窗口应被拒绝，不能通过普通缓存绕过安全 Redis |
| `spectra.security.refresh-cookie-name` | 字符串 | `SPECTRA_SECURITY_REFRESH_COOKIE_NAME`，默认 `__Host-spectra-refresh` | Refresh Token Cookie 名称 | 启动时 | HTTPS 默认使用 `__Host-` 前缀；使用该前缀时 Domain 必须为空、Path 必须为 `/` |
| `spectra.security.refresh-cookie-secure` | 布尔值 | `SPECTRA_SECURITY_REFRESH_COOKIE_SECURE`，默认 `true` | 是否给 Refresh Cookie 添加 Secure 属性 | 启动时 | HTTPS 开发和生产应保持 true；关闭会降低 Cookie 传输保护 |
| `spectra.security.allow-insecure-refresh-cookie` | 布尔值 | `SPECTRA_SECURITY_ALLOW_INSECURE_REFRESH_COOKIE`，默认 `false` | 是否明确允许 HTTP 隔离开发环境使用不安全 Refresh Cookie | 启动时 | 只允许用于明确隔离的 HTTP 开发环境；生产不得打开 |
| `spectra.security.refresh-cookie-same-site` | 枚举 | `SPECTRA_SECURITY_REFRESH_COOKIE_SAME_SITE`，默认 `Strict` | Refresh Cookie 的 SameSite 策略 | 启动时 | 默认 Strict；切换到 None 需要同时满足 HTTPS、精确 Origin 和 CSRF 评审 |
| `spectra.security.refresh-cookie-same-site-none-allowed` | 布尔值 | `SPECTRA_SECURITY_REFRESH_COOKIE_SAME_SITE_NONE_ALLOWED`，默认 `false` | 是否批准使用 SameSite=None | 启动时 | 默认拒绝；打开前必须确认跨站边界、代理 HTTPS、Origin 和 CSRF 防护 |
| `spectra.security.refresh-cookie-path` | 字符串 | `SPECTRA_SECURITY_REFRESH_COOKIE_PATH`，默认 `/` | Refresh Cookie 的 Path | 启动时 | 使用 `__Host-` Cookie 时必须为根路径 |
| `spectra.security.refresh-cookie-domain` | 字符串 | `SPECTRA_SECURITY_REFRESH_COOKIE_DOMAIN`，默认空 | Refresh Cookie 的 Domain | 启动时 | 使用 `__Host-` Cookie 时必须为空；不要为了跨站方便而扩大 Domain |
| `spectra.security.csrf-cookie-name` | 字符串 | `SPECTRA_SECURITY_CSRF_COOKIE_NAME`，默认 `XSRF-TOKEN` | 双提交 CSRF Cookie 名称 | 启动时 | 必须非空，且不能与 CSRF Header 名称相同 |
| `spectra.security.csrf-header-name` | 字符串 | `SPECTRA_SECURITY_CSRF_HEADER_NAME`，默认 `X-XSRF-TOKEN` | 双提交 CSRF Header 名称 | 启动时 | 必须非空，且不能与 CSRF Cookie 名称相同 |

### 请求加密和防重放

| 配置路径 | 类型 | 默认值/环境变量 | 作用 | 生效时机 | 约束和失败行为 |
|---|---|---|---|---|---|
| `spectra.security.crypto-request-max-body-bytes` | 整数，字节 | `SPECTRA_SECURITY_CRYPTO_REQUEST_MAX_BODY_BYTES`，默认 `1048576` | 加密 JSON 请求体的最大字节数 | 启动时校验 | 默认 1 MiB；允许范围为 1024 至 10485760；超限直接返回 400 |
| `spectra.security.crypto-replay-window-seconds` | 整数，秒 | `SPECTRA_SECURITY_CRYPTO_REPLAY_WINDOW_SECONDS`，默认 `300` | 限制加密请求 timestamp 和 nonce 的有效窗口 | 启动时校验 | 默认 300 秒，允许范围为 1 至 3600；nonce 必须由安全 Redis 原子消费 |

### 安全 Redis 和审计归档

| 配置路径 | 类型 | 默认值/环境变量 | 作用 | 生效时机 | 约束和失败行为 |
|---|---|---|---|---|---|
| `spectra.security.redis.namespace` | 字符串 | 固定 `sec:` | 安全 Redis key 的命名空间 | 启动时 | 固定安全契约，不允许改成普通缓存 namespace；Token、Session、验证码、防重放和登录失败锁定使用该空间 |
| `spectra.security.redis.fail-closed` | 布尔值 | 固定 `true` | 安全 Redis 不可用时是否阻断安全操作 | 运行时 | 固定为 true；连接失败、命令失败或无法确认状态时必须拒绝相关安全操作 |
| `spectra.security.redis.worker-batch-size` | 整数 | `SPECTRA_SECURITY_REDIS_WORKER_BATCH_SIZE`，默认 `100` | 安全 Redis worker 的单批处理边界 | 启动时校验 | 允许范围为 1 至 1000；只控制批次，不改变安全 Redis 的事实源语义 |
| `spectra.security.audit-archive-backend` | 枚举 | `SPECTRA_SECURITY_AUDIT_ARCHIVE_BACKEND`，默认 `PENDING` | 安全审计归档实现 | 启动/模块装配 | 开发可保持 PENDING；生产必须配置 S3_OBJECT_LOCK，并配套独立归档 bucket |
| `spectra.security.secret.master-key` 与归档配置 | 组合约束 | 见上表 | 保护密钥版本和安全审计归档 | 启动/运行时 | 根密钥、Redis 和归档后端分别有安全边界；普通文件 bucket 不能替代安全审计 Object Lock bucket |

安全 Redis 是 Token、Session、验证码、防重放和登录失败锁定的事实源。不能因为 Redis 暂时不可用而降级为本地缓存、跳过 nonce 消费或放行登录失败锁定。

## spectra.system

| 配置路径 | 类型 | 默认值 | 作用 | 生效时机 | 约束和失败行为 |
|---|---|---|---|---|---|
| `spectra.system.base-dir` | 路径字符串 | `files` | 后端相对运行目录的基础目录 | 启动时 | 本地上传目录和临时目录通过它派生；修改会改变文件落盘位置，迁移前需处理已有文件 |
| `spectra.system.cors.required` | 布尔值 | `SPECTRA_CORS_REQUIRED`，默认 `false` | 是否要求至少存在 CORS Origin | 启动时/请求处理 | 生产应为 true；开启后没有有效 allowlist 时不能正常启动或放行跨域请求 |
| `spectra.system.cors.origin-patterns` | 逗号分隔字符串 | `SPECTRA_CORS_ORIGIN_ALLOWLIST`，默认本机 HTTPS Origin | 精确允许的浏览器 Origin | 启动时 | 只允许精确 Origin，不使用 `*`；启用带凭证 Cookie 时必须与 HTTPS、CSRF 一起评审 |

开发环境默认允许 localhost/127.0.0.1 的 HTTPS 5173 和 5174 端口。生产环境必须注入实际 HTTPS Origin，不能把开发 Origin 直接复制到生产。

## spectra.kaptcha

| 配置路径 | 类型 | 默认值 | 作用 | 生效时机 | 约束和失败行为 |
|---|---|---|---|---|---|
| `spectra.kaptcha.type` | 枚举 | `math` | 验证码生成类型 | 启动时 | 当前使用数学题验证码；前后端展示和校验逻辑必须使用同一种类型 |
| `spectra.kaptcha.verify` | 布尔值 | `false` | 是否启用验证码校验 | 启动时/认证流程 | false 表示当前环境不执行验证码校验；生产是否开启必须结合登录和验证码策略验收，不能把开发默认当作生产安全策略 |

验证码的次数限制仍由 `spectra.security.verification-code-max-attempts` 控制；验证码存取和消费使用安全 Redis，不应通过关闭校验来解决 Redis 故障。

## spectra.file.upload

### 本地存储和 S3 配置

| 配置路径 | 类型 | 默认值/环境变量 | 作用 | 生效时机 | 约束和失败行为 |
|---|---|---|---|---|---|
| `spectra.file.upload.local.storage-root` | 路径 | `${spectra.system.base-dir}/uploads` | 本地文件最终存储目录 | 启动时 | 由 base-dir 派生；目录权限和磁盘空间必须可用 |
| `spectra.file.upload.local.staging-root` | 路径 | `${spectra.system.base-dir}/temp` | 分片和临时文件目录 | 启动时 | 与最终存储目录分离；清理任务不能误删最终文件 |
| `spectra.file.upload.s3.endpoint` | URL | `S3_ENDPOINT`，无默认值 | S3/MinIO 服务地址 | 启动/Provider 装配 | 需要按环境注入；不得把带凭据的 URL 写入文档或日志 |
| `spectra.file.upload.s3.accessKey` | 字符串 | `S3_ACCESS_KEY`，无默认值 | S3 访问标识 | 启动/Provider 装配 | 仅通过部署环境或 Secret 注入 |
| `spectra.file.upload.s3.secretKey` | 字符串 | `S3_SECRET_KEY`，无默认值 | S3 访问密钥 | 启动/Provider 装配 | 仅通过部署环境或 Secret 注入；禁止提交或输出 |
| `spectra.file.upload.s3.bucket` | 字符串 | `S3_BUCKET`，无默认值 | 普通文件上传 bucket | 启动/Provider 装配 | 普通文件 bucket 与安全审计 archive bucket 分离 |
| `spectra.file.upload.s3.archive-bucket` | 字符串 | `S3_SECURITY_AUDIT_ARCHIVE_BUCKET`，默认空 | 安全审计归档 bucket | 启动/归档 Provider 装配 | 使用 S3_OBJECT_LOCK 时必须配置独立 bucket；不能复用普通上传 bucket |
| `spectra.file.upload.s3.archive-prefix` | 字符串 | `S3_SECURITY_AUDIT_ARCHIVE_PREFIX`，默认 `security-audit/` | 安全审计归档对象前缀 | 启动/归档 Provider 装配 | 只影响归档对象组织，不替代 bucket 的 Object Lock 安全策略 |
| `spectra.file.upload.s3.region` | 字符串 | `S3_REGION`，无默认值 | S3 区域 | 启动/Provider 装配 | 需要与实际 Provider 一致 |

`default-storage: s3` 表示默认上传路径使用 S3。只有在明确选择本地存储的功能路径中，本地 storage-root 和 staging-root 才作为实际落盘位置；S3 Provider 配置缺失时不能静默切换到本地存储。

### 分片、并发和生命周期

| 配置路径 | 类型 | 默认值 | 作用 | 生效时机 | 约束和失败行为 |
|---|---|---|---|---|---|
| `spectra.file.upload.default-storage` | 枚举 | `s3` | 默认存储后端 | 启动时 | 当前默认 S3；切换存储后端前需确认历史文件读取和清理策略 |
| `spectra.file.upload.chunk-size` | 整数，字节 | `8388608`，8 MiB | 默认分片大小 | 启动时校验 | 必须是纯数字；不是 `DataSize` 字符串，不能写成 `8MB` |
| `spectra.file.upload.min-chunk-size` | 整数，字节 | `5242880`，5 MiB | 允许的最小分片大小 | 启动时校验 | 必须小于等于默认和最大分片大小 |
| `spectra.file.upload.max-chunk-size` | 整数，字节 | `67108864`，64 MiB | 允许的最大分片大小 | 启动时校验 | 必须大于等于最小分片大小；超出范围的请求应被拒绝 |
| `spectra.file.upload.max-parts` | 整数 | `10000` | 单个上传会话最多分片数 | 启动时校验/会话创建 | 防止异常分片数量消耗资源；需要与文件大小和分片范围一起评估 |
| `spectra.file.upload.parallelism` | 整数 | `3` | 上传或处理任务的并行度 | 运行时 | 并行度增大可能提高外部 Provider 和本机 IO 压力 |
| `spectra.file.upload.task-ttl` | 时长 | `24h` | 上传任务的最长有效时间 | 运行时清理 | 过期任务不能继续接受分片；清理需保持幂等 |
| `spectra.file.upload.idle-timeout` | 时长 | `2h` | 上传会话无活动的超时时间 | 运行时清理 | 超过空闲时间的会话进入清理流程，不能误删仍在活动的会话 |
| `spectra.file.upload.record-retention` | 时长 | `7d` | 上传记录保留时间 | 清理任务 | 影响审计和业务查询窗口；清理前必须确认记录不再被业务引用 |
| `spectra.file.upload.orphan-retention` | 时长 | `7d` | 孤儿文件保留时间 | 清理任务 | 用于处理数据库记录和对象存储状态不一致的中间文件；清理必须有明确归属判断 |
| `spectra.file.upload.presign-ttl` | 时长 | `15m` | S3 预签名 URL 有效期 | 请求时 | 有效期越长暴露窗口越大；过期 URL 必须失效，不应写入长期缓存 |

分片参数之间要同时满足：分片大小在最小/最大范围内、分片数不超过 max-parts、任务 TTL 大于正常上传耗时。上传清理不能替代安全 Redis，也不能把对象存储失败当作上传成功。

## spectra.notification

| 配置路径 | 类型 | 默认值 | 作用 | 生效时机 | 约束和失败行为 |
|---|---|---|---|---|---|
| `spectra.notification.enabled` | 布尔值 | `true` | 是否装配通知业务能力 | 启动/模块装配 | 这是 Core 通知子域开关，不等同于 OA/Workflow 模块装配开关 |
| `spectra.notification.allowed-link-prefixes` | 逗号分隔路径 | 当前配置的内部路径前缀 | 通知链接允许跳转的站内路径 | 启动时 | 只允许明确的站内前缀；新增前缀前要评估开放跳转和权限边界 |
| `spectra.notification.worker.fixed-delay-ms` | 整数，毫秒 | `5000` | 通知 worker 轮询间隔 | 运行时调度 | 影响消费延迟和数据库/Provider 压力 |
| `spectra.notification.worker.processing-timeout-seconds` | 整数，秒 | `300` | 单个投递处理的超时时间 | 运行时 | 超时不能直接报告成功；需按 Delivery 状态和重试策略处理 |
| `spectra.notification.worker.retry-base-delay-seconds` | 整数，秒 | `5` | 重试退避基础时间 | 运行时 | 只对明确可重试结果退避；不能对 UNKNOWN 结果无条件重试 |
| `spectra.notification.cleanup.enabled` | 布尔值 | `true` | 是否开启通知清理任务 | 启动/调度 | 关闭会导致历史数据持续增长，应有明确的维护窗口 |
| `spectra.notification.cleanup.fixed-delay-ms` | 整数，毫秒 | `3600000` | 通知清理轮询间隔 | 运行时调度 | 1 小时；调整时需评估批量和数据库负载 |
| `spectra.notification.cleanup.batch-size` | 整数 | `100` | 每轮清理的最大记录数 | 运行时 | 应为正数；批量过大会增加锁和事务时间 |
| `spectra.notification.cleanup.retention-seconds` | 整数，秒 | `86400` | 通知历史保留时长 | 清理任务 | 86400 秒即 24 小时；变更会影响用户历史查询范围 |

通知 Provider 的密钥不属于这段 YAML 的普通业务参数，应由密钥管理和部署 Secret 管理。Provider 健康检查失败、密钥缺失或安全状态不可用时，发送流程必须返回阻断状态，不能伪造成功。

## spectra.scheduler.quartz

| 配置路径 | 类型 | 默认值 | 作用 | 生效时机 | 约束和失败行为 |
|---|---|---|---|---|---|
| `spectra.scheduler.quartz.enabled` | 布尔值 | `true` | 是否启用 Quartz 生命周期 | 启动时 | 启用后仍必须通过 PostgreSQL 启动门禁；数据库不可用时不得执行 Job |
| `spectra.scheduler.quartz.table-prefix` | 字符串 | `spectra_quartz.QRTZ_` | Quartz 表前缀和 schema | 启动时 | 必须使用独立 `spectra_quartz` schema，不能混入业务表 |
| `spectra.scheduler.quartz.clustered` | 布尔值 | `true` | 是否启用 JDBC 集群协调 | 启动时 | 多实例部署必须保持一致；集群锁和运行状态以 Quartz 表为事实源 |
| `spectra.scheduler.quartz.jdbc-store` | 布尔值 | `true` | 是否使用持久化 JDBC JobStore | 启动时 | 必须保持 true；不使用 RAMJobStore，避免任务状态丢失 |
| `spectra.scheduler.quartz.job-store-class` | 类名 | `org.springframework.scheduling.quartz.LocalDataSourceJobStore` | JobStore 实现 | 启动时 | 必须与 DataSource、事务和 schema 配置匹配 |
| `spectra.scheduler.quartz.thread-count` | 整数 | `10` | Quartz 工作线程数 | 启动时 | 需要结合数据库连接池、任务耗时和 CPU 评估 |
| `spectra.scheduler.quartz.history-retention-days` | 整数，天 | `90` | 执行历史终态记录保留时间 | 清理任务 | 影响审计/运维查询窗口 |
| `spectra.scheduler.quartz.history-cleanup-batch-size` | 整数 | `500` | 每轮历史清理的最大行数 | 清理任务 | 应为正数；批量过大会放大数据库锁和事务压力 |
| `spectra.scheduler.quartz.history-running-timeout` | 时长 | `24h` | RUNNING 记录无完成回调时转 ABANDONED 的最长时间 | 运行时清理 | 不能小于正常任务最大执行窗口，否则会误判仍在运行的任务 |
| `spectra.scheduler.quartz.database-retry-interval` | 时长 | `10s` | Quartz 数据库不可用时的生命周期重试间隔 | 运行时 | 重试不能绕过数据库启动门禁；数据库不可用期间应保持未就绪 |

Quartz Cron Trigger 使用显式 IANA 时区，内置 Trigger 使用代码声明的 UTC 时区，不使用 JVM 默认时区。Quartz JobDetail、Trigger、集群锁和运行状态以 `spectra_quartz.QRTZ_*` 为事实源；执行观测和历史清理以 Core 的执行历史表为事实源。

## 配置修改检查清单

修改这段 `spectra:` 配置前，按下面顺序检查：

1. 确认修改的是 YAML 绑定配置，而不是需要通过系统设置页面维护的 `sys_config`。
2. 确认环境变量名、默认值、类型和单位没有变化；毫秒、秒、时长和字节不能混用。
3. 修改安全配置时，确认 HTTPS、精确 CORS、Cookie、CSRF、防重放和安全 Redis 仍然共同成立。
4. 修改文件上传配置时，确认本地目录权限、S3 Provider、普通 bucket、审计 archive bucket、分片范围和清理策略。
5. 修改通知或 Quartz 配置时，确认 worker/Job 的并发、批量、超时、重试和保留时间不会超过数据库或外部 Provider 能力。
6. 生产环境只通过 Secret/环境注入敏感值；不要把值写入 YAML、日志、工单、截图或生成的网站文档。
7. 修改后运行后端配置校验和对应测试；需要重启的配置必须完成滚动/重启验收。
