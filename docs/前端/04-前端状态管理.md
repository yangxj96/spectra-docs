# 前端状态管理

> 对应源码：`spectra-ui/src/plugin/store/`、`src/plugin/request/auth.ts`、`src/utils/route-utils.ts` 和通知、文件相关服务。

## Store 总览

Pinia 在 `src/plugin/store/index.ts` 创建，并注册 `pinia-plugin-persistedstate`。只有显式声明 `persist` 的 Store 才会持久化；当前 User Store 明确关闭持久化，Crypto Store 只选择性持久化两个字段。Store 的职责按“全局 UI、会话、协议、缓存、通知”划分：

| Store | ID | 负责内容 | 持久化 |
|---|---|---|---|
| `useAppStore` | `app` | 系统公开信息、初始化/引导状态、菜单、路由授权、侧边栏和水印 | 当前未声明 `persist`，刷新后由启动流程重新加载 |
| `useUserStore` | `user` | Access Token、登录状态和权限判断 | `persist: false`，Access Token 只在内存 |
| `useCryptoStore` | `crypto` | 加密开关、服务端公钥、客户端私钥 | 仅持久化开关和服务端公钥，客户端私钥不持久化 |
| `useDictStore` | `dict` | 字典组数据缓存和字典项查询 | 当前未声明 `persist`；请求由串行队列保护 |
| `useNotificationStore` | `notification` | 消息列表、未读数、用途筛选、已读和删除 | 未声明 `persist`，作为运行时状态使用 |
| `usePropsStore` | `props` | 页面属性类轻量状态 | 以源码实际使用为准，不存放 Token 或密钥 |

## App Store

`useAppStore` 是路由和布局的共享状态中心，主要字段包括：

- `system`：系统名称、简称、Logo、默认语言、时区和版权配置。
- `initialization`：系统是否完成初始化。
- `system_guide`、`system_guide_loaded`：系统设置引导是否必需及是否已查询。
- `bootstrap_loaded`：公开启动配置是否加载成功。
- `menus`：后端返回的完整菜单树。
- `currentMenus`：当前布局渲染的菜单节点。
- `authorizedRouteNames`：当前用户可访问的命名路由集合。
- `menusLoaded`、`isFetchingMenus`：菜单加载状态，防止重复加载。
- `unfold`、`watermark`：侧边栏展开和水印显示状态。

启动阶段由 `setBootstrap()` 写入系统和初始化状态；路由守卫加载菜单后直接更新菜单树和授权路由名。页面布局通过 `findMenuPath()` 生成面包屑，通过 `currentMenus` 生成侧边栏。

## User Store 与权限判断

Access Token 不写入 LocalStorage 或 Pinia 持久化状态，Refresh Token 由后端 HttpOnly Cookie 管理。`useUserStore().hasPermission()` 支持三种匹配方式：

```text
精确匹配：user:read      -> user:read
分段通配：user:*          -> user:read / user:update
全局通配：*               -> 任意权限
```

分段通配要求授权编码和目标编码的段数一致，角色名称不直接参与权限计算。`hasAllPermissions()` 用于 `v-permission="[...]"` 的全部满足场景；`v-permission.or` 用于任意满足场景。

权限存在两层：

1. 路由层通过 `requiredMenu` 和授权菜单树阻止未授权页面访问。
2. 页面层通过 `v-permission` 隐藏或禁用新增、编辑、删除、导出等操作。

最终权限仍由后端接口校验，前端隐藏按钮不能视为安全边界。

## Crypto Store

Crypto Store 的三个核心字段是：

| 字段 | 说明 |
|---|---|
| `enabled` | 是否启用接口加解密 |
| `server_public_key` | 用于加密请求中的临时 AES 密钥及验证服务端签名 |
| `client_private_key` | 用于解密响应和签名请求，只存在内存 |

登录后由安全接口初始化加密配置；路由首次加载菜单时，如果开关开启且客户端私钥为空，则调用 `fetchClientPrivateKey()` 完成密钥交换。退出登录或会话切换时不能复用旧用户的客户端私钥。

详细协议见 [[05-前端请求与安全通信]]。

## Dict Store

`useDictStore` 通过 `PQueue({ concurrency: 1 })` 串行执行字典请求：

- `getDictData(key)`：优先读取 `dicts[key]`，未命中时调用 `DictApi.getDataByTypeCode()`。
- `getDictItem(key, value)`：异步加载后查询字典项。
- `getDictItemSync(key, value)`：只读取已有缓存，不触发网络请求。

字典组件 `DictSelect` 和 `DictTag` 应优先使用 Store，不要在每个页面重复请求同一字典组。后端返回异常时 Store 返回空数组并记录错误，页面应根据业务需要显示空状态。

## Notification Store

Notification Store 管理消息中心的运行时状态：

- `fetchNotifications()` 支持页码、用途、已读状态、关键词和时间范围筛选。
- `refreshUnreadCount()` 更新头部铃铛的未读数。
- `markAsRead()`、`markAllAsRead()` 同步更新列表和未读数。
- `deleteNotification()`、`batchDelete()` 删除后同步移除本地记录，并扣减未读数。
- `currentPurpose` 和 `filteredNotifications` 负责用途过滤。

消息用途的展示标签、颜色和图标集中在 `notificationPurposeConfigs`，新增用途时要同步类型声明、API 契约和展示配置。

## 状态边界

- Token、客户端私钥、验证码和业务密钥不能写入持久化 Store或日志。
- 页面表单的临时值放在页面 `ref`/`reactive` 中，只有跨页面共享且有明确生命周期时才提升到 Store。
- 服务端事实优先：菜单、权限、通知未读数和上传会话不能只依赖本地缓存推断。
- 清除用户状态时同时清理菜单、授权路由、Token、客户端私钥、通知列表和与用户相关的缓存。
- 修改 Store 字段时，搜索其调用方和对应测试；Store 是路由守卫、布局和多个页面的共享依赖。
